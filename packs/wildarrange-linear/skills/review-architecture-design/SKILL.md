# 架构设计审查与确认

## 步骤一：确认输入和现有权威来源

读取项目规则、用户需求与已有设计文档的引用，仅搜索设计资料，不进行代码反向建模。记录来源路径、章节、图版本或图中节点名称。读取用户提供的图片、Mermaid、PDF 或文档；看不清、无法访问的部分列为缺失，不能凭名称猜图意。
先找已有明确确认的权威文档；存在多个当前版本或冲突时，展示冲突交用户裁决，不自行挑选一个覆盖。普通会话开始不自动重跑本流程。使用宿主提供的真实 WildArrange CLI 路径，不假定目标仓库有 bin/wildarrange.mjs。

## 步骤二：形成待审设计

已有设计时保留原文并审查；待审修订先在会话或已授权草稿中展示，不先覆盖已确认文档；无设计时，根据用户目标提出最小可用方案，说明模块职责、依赖方向、关键事实的唯一维护者及业务输入输出。信息不足以判断边界时先补充需求，不用一张全是“待确认”的模板冒充方案。
不强制五层架构或固定目录。小工具可以一个模块；拆分必须有独立职责或依赖边界的理由。区分提案与已确认设计，不生成实现代码。

## 步骤三：按五条标准逐项 Review

| 编号 | 标准 | 可驳回的设计问题 |
|---|---|---|
| A1 | 职责清晰 | 一个组件同时负责相互独立的业务、路由、状态或存储，未说明委托边界；编排组件只协调已有职责本身不构成违规 |
| A2 | 依赖明确 | 设计明确出现循环依赖、违反已声明层次的调用，或消费者可绕开公开入口访问内部职责 |
| A3 | 事实唯一 | 同一事实设计了多个独立可写维护者，或消费者自行维护副本；只读引用、标明来源且可重建的缓存不等同于第二权威 |
| A4 | 流程完整 | 已列出的核心业务或必要失败分支没有负责组件，输入输出在节点间不衔接 |
| A5 | 复杂度必要 | 多个组件重复负责同一功能，或新增层/模块没有对应需求和独立职责理由 |

每条输出 PASS、RETURN 或 INCONCLUSIVE。明确存在问题用 RETURN；没有说明依赖或归属等依据时用 INCONCLUSIVE，不把缺少说明当作已证明违规。总结果：任一 RETURN 则 RETURN；否则任一 INCONCLUSIVE 则 INCONCLUSIVE；只有全部 PASS 才 PASS。问题必须包含规则编号、来源路径和章节/图节点、原描述、影响、最短修改建议。不得伪造图片行号。新提案同样接受这五条审查。

输出可读表格及同义 JSON：scope=design_only、sources、decision、checks[{rule,decision,evidence,reason,requiredChange}]、authorityPath、confirmation=awaiting_user。报告是审查证据，不是第二份架构。PASS 只代表设计审查通过，不代表用户已批准，更不代表代码已符合。

## 步骤四：人工确认并确立唯一权威

向用户展示完整候选设计、审查表、与旧版的变化及建议权威路径。RETURN 或 INCONCLUSIVE 先修订/补证据；用户选择暂缓时保留未解决项，不标记为正式设计。只在五项通过且用户明确确认该具体版本后，更新同一权威文档的确认记录：设计版本、确认人、确认时间、对应会话/任务确认依据。
已有权威文件沿用原路径；没有时建议 doc/architecture.md。已占用但无关的文件不能覆盖。架构图片可以保留为其引用附件；只有一处持有当前设计和确认记录，其他位置只链接，不复制同样的规则。若唯一来源为不可编辑图片，用一份经确认的说明文档引用原图并承载缺失设计，不另画一份重复图。
文件写入仍遵守既有计划、范围与项目规则批准流程；Hook 拦截时报告阻塞并使用正式文档任务，不能绕过门禁。本 Skill 不提供或虚构 architecture approve 命令，也不建立第二套批准账本。

## 步骤五：交接与后续变更

向初始化/接管流程返回唯一权威路径、设计版本、五项结论、人工确认依据和未解决项。没有完成确认就返回 awaiting_user 或 blocked，不能宣布架构治理完成。
后续计划引用这份设计；改变职责、依赖或事实归属时，先提出设计差异，重走审查与确认，再更新原文档。纯文字修正无需冒充架构变更。
本阶段不将图转成代码规则，不自动挂到源码一致性检查，也不新增业务 Worker 的架构准入门禁。测试验证的是入口和流程连接，设计语义是否合格仍由 Agent 按证据审查、人类确认。
