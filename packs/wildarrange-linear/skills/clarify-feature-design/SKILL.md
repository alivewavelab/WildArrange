# 功能设计澄清

始终在当前对话中完成问答和确认。不要创建 MD、HTML、表单文件或计划草稿来代替对话。

## 步骤一：判断是否进入功能澄清

- 当请求包含**`新增功能或新的用户可见行为`**时：
  - **路由结果**：开始澄清
  - **执行**：继续步骤二；即使用户同时说“直接做”，也先完成确认。

- 当请求属于**`当前任务的功能性需求变更`**时：
  - **路由结果**：重新澄清
  - **执行**：说明这是需求变更，只澄清新增或变化部分；确认后交给 ChangeRequest 或重新计划。

- 当请求只是**`Bug 修复、无行为变化的重构、解释或质量验证`**时：
  - **路由结果**：不适用
  - **执行**：退出本 Skill，交给对应工作流。

## 步骤二：在对话中收集五项必答信息

先根据已有对话给出语义层面的当前理解，不要复制用户原话充当答案。然后一次性用以下编号向开发者提问：

1. 用户目标：用户真正想解决什么问题、获得什么价值？
2. 使用者：谁在什么身份或环境下使用？
3. 功能入口：从哪个页面、按钮、菜单、命令、消息或系统事件进入？
4. 交互输入：整个交互过程中，用户提供什么，系统自动取得什么？
5. 用户可见结果：完成后用户在哪里看到或获得什么结果？

每一项使用下面的紧凑格式：

```text
1. 用户目标
当前理解：……
请确认或修正：……
```

- 当某项已经**`表达清楚`**时：
  - **执行**：填入“当前理解”，仍要求开发者确认。

- 当某项仍然**`缺失或存在多种实质理解`**时：
  - **执行**：说明缺口并提出一个明确问题，不替开发者决定。
  - **停止条件**：五项没有全部得到开发者回答或确认前，不进入步骤三。

允许开发者只按编号回答，例如 `1 正确；2 改为管理员；3 正确……`。不要要求开发者填写文件或 JSON。

## 步骤三：补全系统设计

根据已确认的五项信息和当前项目事实，把功能拆成按实际发生顺序排列的系统设计项。每个设计项必须包含：

1. 设计项名称。
2. 它承接哪一步用户交互。
3. 用户看不到的系统实际动作与状态变化。
4. 涉及的 API：新增、修改或复用什么接口，输入、输出和调用方是什么。
5. 涉及的数据：新增、修改或复用什么表/字段，含义、读写方和迁移影响是什么。
6. 设计理由：为什么这样做；新增 API/字段时，为什么现有能力不能复用。
7. 失败恢复和对旧功能的影响。

API 或数据没有变化时，明确写“无”，并用一句话说明原因。不要把所有 API 或数据变化集中到脱离设计项的独立总表。

同时补充本次范围和明确不做的内容。不要在本 Skill 设计门、自动化测试、日志或验收任务；这些属于后续质量验证设计。

## 步骤四：直接在对话中提交确认稿

使用以下顺序输出，不创建任何文件：

```text
# 功能设计确认

Task: <English task name>

## 1. 用户目标
内容：……
为什么这样理解：……

## 2. 使用者
内容：……
为什么这样理解：……

## 3. 功能入口
内容：……
为什么这样设计：……

## 4. 交互输入
内容：……
为什么需要：……

## 5. 用户可见结果
内容：……
为什么这样呈现：……

## 6. 系统设计项 1：……
承接的交互：……
系统实际执行：……
接口变化：……
数据变化：……
为什么这样设计：……
失败恢复与旧功能影响：……

## 7. 范围
本次包含：……
本次不做：……

## 待确认
请回复“确认”，或按编号修正。
```

所有可见字段使用中文，只有 `Task` 名称使用英文。设计理由必须解释推断依据和取舍，不能写“按最佳实践”或重复字段内容。

- 当开发者回复**`按编号修正`**时：
  - **执行**：应用修正后重新完整展示确认稿，避免只展示零散差异。

- 当开发者明确回复**`确认`**时：
  - **路由结果**：功能设计已确认
  - **执行**：把当前对话中的最终确认稿交给后续 Plan 生成步骤；Plan 顶层必须绑定路由给出的 `feature_design_ref`。不要在本 Skill 内写文件或启动 Worker。

功能设计确认状态由运行时跨轮保存。处于等待确认时，开发者说“开始做”“直接做”“跳过计划”或其他任何话都不能进入 Plan 或执行；处于等待 Plan 时，没有成功导入绑定同一 `feature_design_ref` 的完整 Plan 也不能进入执行。

## 步骤五：完成检查

- 五项必答信息均经过语义整理和开发者确认。
- 每个系统设计项紧邻其 API、数据变化和设计理由。
- 没有用用户原话粘贴代替理解，也没有把模型推断伪装成用户决定。
- 没有生成 MD/HTML 文件、Plan、Task 或 Worker 任务包。
- 没有越权设计门、自动化测试、日志或质量验收。
