# 旧项目治理接管

## 步骤一：建立设计层面的权威架构

先用真实 CLI 的 prompts show --skill review-architecture-design 读取完整 Skill。有旧架构图/文档先审查，无设计则根据需求提出最小方案；通过 A1–A5 审查并获得用户对具体版本的确认后，返回唯一权威文档路径。未完成则报告待确认或缺失，不把模板生成当作设计获批。此环节只看设计，不对照代码，也不把后续仓库资产扫描当作图与代码一致性证明。

## 步骤二：冻结现状并扫描

读取项目规则、运行时提供的 CLI 位置，记录 Git HEAD、分支、脏文件、活动任务与 owner。不得覆盖已有任务或夹带未提交修改。使用真实安装的 wildarrange adoption inventory 获取验证资产；另用宿主只读搜索覆盖全部受版本管理源码、文档、旧计划表、数据定义和测试目录。列出扫描覆盖范围、忽略目录及未知项，不能声称路径匹配能自动理解全部旧事实。

## 步骤三：逐项映射已有事实

向用户展示一张来源到目标的清单：原路径与行号、原声明、现有唯一维护者、消费者、目标记录、需要迁移的动作、验证方法、未解决项。

- 旧计划的未完成事项转成正式任务；task.request.source 说明旧计划来源，task.request.evidenceRefs 保存路径与条目定位。原来的“已完成”仅作历史声明，复验前不得填 completed。
- gameId、buildId 等事实保留真实读写 owner；其他模块通过 owner 的入口访问。登记 owner 路径不等于复制业务值。出现双写者时创建重构任务，迁移消费者，测试后停用旧写入口。
- 测试登记到现有 Verification Registry 的 planDefaults；夹具登记原路径和消费者到同一 Registry.fixtures。不得复制夹具创建另一份当前真相，不得把夹具当作可执行测试。
- 不能确认的字段、消费者与旧完成结论保留为待核实任务，不自动丢弃或编造对应关系。

## 步骤四：建立迁移任务并确认

先调用 configure-project-review 完成执行与审查依赖。将归拢工作整理为正常语义计划，填入 responsibilityChanges、worker_command、允许路径、验收标准和来源 evidenceRefs；向用户说明将改哪个脚本、职责如何变化、谁唯一维护事实。仅导入计划不执行，按现有人工批准流程等待批准。

已有活动计划时补充或使用正式变更流程，不覆盖 tasks.json。接口或数据库字段需要变化时走现有变更确认，不能藏在“初始化”里执行。项目规则变更遵守项目本身的批准要求。

## 步骤五：分开登记与实际迁移

验证资产的逐卡批准、事务恢复及 Git 锚定调用 verification-governance Skill，沿用 adoption start/status/resume/recover。adoption finalized 只代表该登记事务完成。
真实代码归拢通过已批准任务执行：迁移消费者、收敛读写 owner、复用测试与夹具；Worker 提交后由独立 Review 按 R1–R5 及项目步骤审计。不手改账本、不把登记通过当业务正确。

## 步骤六：对账并交付

重新核对步骤三的每一项：给出正式任务/登记项引用、目标 owner、旧入口已停止维护的证据、消费者验证命令及实际结果。旧文档改为历史说明或指向唯一当前记录，经过许可才归档，不直接删除历史。
只在迁移任务通过 verifier、scope、Review、acceptance proof 和 checkpoint，且清单无未处理迁移项时报告接管完成。否则明确区分已扫描、已登记、已迁移、已验证及剩余阻塞。恢复时复用现有计划、Registry 和报告，不建第二套状态表。
