0. 先记住这 5 条铁律

铁律人话做错会怎样
先武装门，再干活用 config init --armed，计划里必须有真实的 verify_commands 和独立复核信号（如 review_commands）同义反复的「全绿」不证明任何事；现在验收证明会直接挡下来
worker 说完成 ≠ 真完成AI/子 Agent 的 DoneClaim 只是自称，要过 verify / scope / review / acceptance-proof / checkpoint半成品进仓库
判错用标注，别关开关annotate 只写意见，绝不改门；改门只能人显式改配置或计划一关门 = 失去质量控制
硬拦截要装到本机Cursor / Codex / Kimi 都要各自 adapter install；用 doctor 查装没装有人机器上 AI 自由改文件，边界形同虚设
每一条拦截/放行都能复查用 decisions、timeline、Dashboard 面板；FAIL 必须看到规则与证据出事后说不清「当时为什么放行」

1. 部署：从空项目到可以用

下面命令默认你已经在目标业务项目根目录。把 HELIX 换成你机器上 WildArrange 的 CLI 路径（本仓库开发态示例）：

export HELIX="/绝对路径/工作范式/bin/helix.mjs" # npm 安装用户可把 HELIX 换成: npx wildarrange # 或: npx @alivewavelab/wildarrange
1

初始化运行时目录

node "$HELIX" init git init # 建议；scope 门依赖 Git 看改动范围

你插什么

这步几乎不用插。只要确认你站在业务项目根，不是站在 WildArrange 框架仓库根（除非你在维护框架本身）。

怎么核对

出现 .helix/ 目录。没有报错就过。
2

生成并武装配置

node "$HELIX" config init --root --armed node "$HELIX" config baseline --reason "首次武装后的基线"

你插什么

打开根目录 helix.config.json，按需改：
  • qualityGates.lspDiagnostics.commands → 换成你项目真实的测试/类型检查（如 npm test）
  • agents.*.provider → 要给 BaiZe / Archivist 配外部模型时改这里
  • reporting.verbosity → 新手保持 "verbose"（默认）

怎么核对

node "$HELIX" doctor
看 sections.gateArming.armed 应为 true。
若是 false，按 findings 里的 next_action 补配置，别先跑任务。
3

装宿主硬拦截（三宿主示例见下一章）

node "$HELIX" adapter install --target all --mode local node "$HELIX" doctor # 再查 adapters 分项

你插什么

只装你实际用的宿主也可以： --target cursor / codex / kimi。
Cursor：打开项目时选受信任工作区。
Codex：在项目里用 /hooks trust 一次。
Kimi：按安装说明启用用户侧 plugin（CLI 不会静默改你的全局配置）。

怎么核对

doctor → sections.adapters.targets 里你要用的宿主显示 installed: true。
仍是 MISSING → 重新 install；规则文件若告警「不存在路径」，把绝对路径改成相对路径。
4

写计划并导入

cp 某处/plan.example.json ./plan.json # 编辑 plan.json，把要求换成你的（见第 3 章） node "$HELIX" plan --from ./plan.json

你插什么

整份 plan.json 就是你的需求声明：要改哪些路径、worker 干什么、怎么验收、怎么复核。详见第 3 章模板。

怎么核对

输出 ok: true 与 taskCount。若要求计划审批，先跑 approve 再 run。
5

跑第一个任务并审判门决策

node "$HELIX" run node "$HELIX" decisions --limit 20 node "$HELIX" decisions --annotatable # 只看该过你手的

你插什么

若 AI 在本机宿主里干活，你主要插的是对话里的产品要求；命令式跑则依赖计划里的 worker_command。卡住时把 decisions 三行原文贴给 AI 说「这条判错了」。

怎么核对

stderr 末尾有「门决策汇总」（verbose）。每条至少看：发生了什么 / 命中规则 / 证据路径。FAIL 的规则与证据不能为空。网页：node "$HELIX" serve 开 Dashboard。

2. 三宿主分别怎么装硬拦截（必做）

「硬拦截」= AI 动手改文件或跑危险命令前，必须先过 WildArrange 的范围/安全检查。软规则（mdc）只是提醒，不能替代。

Cursor

fail-closed
node "$HELIX" adapter install --target cursor --mode local

生成物：.cursor/hooks.json、.cursor/hooks/wildarrange-hook-bridge.mjs、软规则 .cursor/rules/wildarrange.mdc、slash 命令。

你要做：用 Cursor 以受信任工作区打开本项目。把 hooks 提交进 git（模板已例外放行 hooks；rules 默认仍本机）。

核验：在 Cursor 里故意让 AI 改 writable_paths 之外的文件 → 应被拒绝；或看 doctor adapters 显示 cursor installed。

Codex

hard hooks
node "$HELIX" adapter install --target codex --mode local

生成物：.codex/hooks.json（另有 .helix/adapters/codex/ 审计副本）。

你要做：在 Codex 会话里 /hooks review 并 trust 本项目 hooks。不 trust = 硬拦截不生效。

核验：doctor 显示 codex installed；越界编辑应被 hook 拦。

Kimi Code

hook fail-open
node "$HELIX" adapter install --target kimi

生成物：项目内 plugin 清单与 bridge（在 .helix/adapters/kimi/），按 README 手动启用用户侧 plugin。

你要知道：Kimi Hook 崩溃/超时默认放行，所以最终完成仍必须过 verifier 等主线门，别把 Hook 当唯一安全边界。

核验：doctor adapters 里 kimi installed；主线用 run 的门决策做终审。

团队场景：每人每台机器都要装一次 adapter。新人入职第一天先跑 doctor，看到本机 MISSING 立刻 install。不要假设「别人仓库里已经有 hooks」就等于你本机生效。

3. 写计划：每一字段怎么塞你自己的要求

计划是唯一「产品要求入口」。复制下面骨架改字即可（也可用仓库里 examples/fullstack-starter/plan.example.json）。

{ "title": "你的功能名", "objective": "一句话成功标准（给人看的）", "tasks": [ { "id": "T001", "subject": "这一单要交付什么", "description": "给你自己的 AI worker 的说明：背景、禁忌、参考文档", "writable_paths": ["src/foo/**", "doc/bar.md"], "worker_command": "……可选：命令式 worker；宿主里由人/AI 手工改文件时可省略……", "verify_commands": [ "node -e \"……必须能证明产物正确的真实命令……\"" ], "review_commands": [ "node -e \"……与 verify 不同角度的独立检查……\"" ], "standards_commands": [], "successCriteria": [ { "id": "C001", "title": "人话验收句", "status": "pending", "expectedEvidence": "verifier 会检查什么", "verifierCommandRefs": [0] } ] } ] }
字段塞你的要求时怎么写写错常见后果
writable_pathsAI 允许改的目录/文件白名单。越细则越安全。写太宽 → 误伤别的模块；写太窄 → 正当改动被 scope 拦
worker_command命令型自动化时用；在 Cursor/Codex 里人工让 AI 改文件，可省略或留简单 smoke。空 + trivial verify → 可能被判定 no-op
verify_commands必填且必须真实。测行为：读文件、跑测试、调脚本。禁止只写 true。全 trivial → acceptance-proof FAIL
review_commands强烈建议必填。给独立复核信号：风格、清单、二次断言。也可改用 standards_commands / 打开 LLM review / 启用质量门。无任何独立复核信号 → review_not_tautological FAIL，到不了 completed
successCriteria用人话写「什么叫好了」，并绑定到某条 verify 命令下标。不绑定证据 → criteria 不过关
description把业务禁忌、参考链接、禁用库写清楚——这是塞「产品要求」的主战场之一。太空 → AI 自由发挥
插入规范文档：在项目根放 AGENTS.md / CLAUDE.md，分类规范放 .cursor/rules/*.md（可带 globs）。这些会在 Hook / review 时注入。细节见第 6 章。

4. 跑任务：每个门干什么、你插什么、怎么核对

命令：

node "$HELIX" run # 跑下一个待办任务 node "$HELIX" status # 看 pending / completed / gateArming node "$HELIX" serve --host 127.0.0.1 --port 8765 # 网页看面板
门 它在查什么 你怎么插入要求 怎么核对对错
worker 执行改动 / 命令 计划里的 description + 宿主会话里的指令 + writable_paths 产物是否出现；ledger 有 worker 证据。自称完成不算数
verify 行为是否正确 verify_commands：换成你的测试、脚本、断言 decisions --gate verify。FAIL 应有 verify_failed + 失败命令/exit。绿了也要扫一眼命令是不是真测到了
scope 改动是否越界 writable_paths；越界需求走 ChangeRequest，不要偷偷加路径 FAIL 看 scope_violation 与越界路径列表。若路径本该允许 → 标 rule_wrong 并改计划
review 独立复核是否还有问题 review_commands / standards_commands / 质量门 /（可选）LLM review 证据路径指向 .helix/reports/reviews/…md。打开看各 lane。可标注（含 PASS）
acceptance-proof 能不能宣称完成的硬地板 确保 verify 非 trivial、review 有独立信号、successCriteria 齐 FAIL 看 proof_*（如 proof_review_not_tautological）。报告在 .helix/reports/acceptance/
checkpoint 落盘存档 一般不用插；失败返回重试而不是假完成 status 里任务变 completed；有 checkpoint 文件
例

一次「拦得对」的体验（故意无复核信号）

计划只有 verify_commands、没有 review_commands 且质量门也关：

node "$HELIX" run # 预期：acceptance-proof FAIL # 命中规则: proof_review_not_tautological — review 没有独立信号…

这就是框架在保你：别对着假绿灯签字。回去给任务补 review_commands（或武装质量门）再跑。

5. 看对错：命令行 + 网页面板 + 标注回路

A

每条决策三行（日常主力）

node "$HELIX" decisions --limit 30 node "$HELIX" decisions --task T001 node "$HELIX" decisions --gate verify node "$HELIX" decisions --annotatable node "$HELIX" decisions --format json

三行模板：

行含义你怎么判
发生了什么哪扇门、放行还是拦截和此刻业务动作是否对应
命中规则稳定 code + 原因规则本身不合理 → rule_wrong；这次特例 → case_wrong；分类标错 → mislabeled
证据报告文件路径点开看原文；空证据的 FAIL 要当事故对待（当前版本已尽量填满）
B

标注（告诉框架「这条错了」）

node "$HELIX" annotate --decision dec_xxx --category rule_wrong --reason "这条路径本应允许" node "$HELIX" annotate list node "$HELIX" annotate stats node "$HELIX" decisions stats

你插什么

分类必选；理由写给未来的自己和异步审查 Agent。不要在标注里改配置。

怎么核对

annotate stats 会按「规则 × 标注」聚合。同条规则反复 rule_wrong → 你再动手改计划/配置。标注路径有硬测试保证不写门开关。
C

统一时间线 + 可疑审查 + 体检

node "$HELIX" timeline --limit 40 node "$HELIX" timeline --task T001 node "$HELIX" review suspicious # 可选：有外部 LLM key 时给第二意见；无 key 也有确定性摘要 node "$HELIX" doctor node "$HELIX" state backup --reason "试用一周后"
D

网页面板（给懒得盯终端的人）

node "$HELIX" serve --host 127.0.0.1 --port 8765 # 浏览器打开 http://127.0.0.1:8765 # 非本机绑定必须设 HELIX_DASHBOARD_TOKEN

面板上看：最近决策三行、门触发统计、从未触发的门、门武装状态、锁持有者、并行 run 对账。只读，不能在网页上关门。

6. 把项目规范塞进 AI（持续生效）

你想约束什么放哪里何时生效
全局红线（密钥、禁止 force push…）根 AGENTS.md / CLAUDE.md会话开始、提交前注入
前端/后端/数据库专项.cursor/rules/*.md（可配 globs）或宿主对应规则目录改到匹配文件时动态注入
单次任务边界plan.json 的 writable_paths / description / verify / review本任务全程
团队命令与门面helix.config.json 的 qualityGates / adapters / reporting每次 run / review
改规范后建议：doctor 一眼 + 故意越界试一次硬拦截，确认「规则活着」。

7. 急救清单

现象先跑人怎么处理
任务永远到不了 completeddecisions --annotatable、decisions --gate acceptance-proof读 proof_* 原因；通常缺 review 信号或 verify 太假
绿灯但我怀疑假status（看 gateArming）、打开 review/acceptance 报告若门未武装：停工，先 config init --armed / 补 review_commands
AI 改到范围外被拦，但我觉得该改看 scope 决策的 deniedPaths走变更扩展，或改计划 writable_paths 后重新 import；可 annotate case_wrong
