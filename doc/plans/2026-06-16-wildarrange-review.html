WildArrange 是目前见过的 AI Agent 治理工具中，安全不变量最严格、证据链最完整 的一个。核心理念（worker 不能说完成就完成，必须独立验证+范围检查+复核+验收证明）贯彻得非常彻底，几乎没有可以绕过的路径。

主要风险在 Agent 执行层面：作为被 Agent 运行的工具，自身需要更健壮的自我保护，尤其是 shell:true 命令执行、config 注入、并行 Agent 生命周期这三块。

不变量实现能否绕过

弱项发现

  • Scope 的非 Git 降级路径：非 Git 项目使用文件 manifest 指纹，可以检测到文件增删改。但文件 manifest 不区分 "worker 改的" 和 "其他进程改的"。实际风险低（Agent 场景下通常是单进程），但理论上可被绕过。
  • Verifier 只看 exitCode=0：不分析 stdout/stderr 内容。如果 verify_commands 写了一个 `node -e "process.exit(0)"`，门就过了。governanceWarnings 标记了 trivial 命令，但不阻断。
  • 成功标准存在 legacy 默认值：如果任务不写 successCriteria，系统自动种子 3 个默认 criterion（happy path/edge/regression），每个都绑到所有 verifier 命令。这比没有强，但默认 criterion 是模板化的，可能不看实际业务。
  • Cursor adapter 是软约束：文档明确写了 "soft governance"。Codex 的 hard hook 依赖用户先 `/hooks` trust。

治理机制总结

Plan → Worker → Verifier → ScopeGuard → ReviewGate(13 lanes) → AcceptanceProof(8 checks) → Checkpoint
  ↑                                                                                            │
  └────────────────────────── retry (with ChangeRequest if scope fail) ─────────────────────────┘
              证据全部入 ledger（hash 链），可随时 verify。

4. Agent 执行问题分析 B

WildArrange 的独特之处：它是被 Agent 安装和运行的工具。Agent 可能会误用它、绕开它、甚至直接删掉 .helix/。以下分析从 "Agent 当作工具调用时" 的角度出发。

#问题严重度详情
1 shell:true 无沙箱 高 helix-gates:17-48 runCommand 使用 shell:true。当 Agent 调用 helix node execute --task T001 时，worker_command 在 shell 中执行。如果 plan.json 里的 worker_command 被篡改为 rm -rf /，没有沙箱兜底。建议：至少加一个 --dry-run 模式和命令白名单。
2 .helix/ 目录无完整性保护 高 Agent 可以直接删除 .helix/ledger.jsonl 或 .helix/team/tasks.json。ledger hash 链能检测篡改但无法阻止删除。建议：考虑 .helix/ 目录的定期备份或 Git 自动提交。
3 Plan.json 导入无签名校验 中 Agent 可能生成一个 verify_commands 为空的 plan.json，绕过导入时校验。实际测试了 empty verifier commands cannot complete 这个场景，但在 corrupt task state 后通过。不过运行时仍会被 rejectionReason 拦截。
4 config 可被 Agent 热修改 中 Agent 可以编辑 helix.config.json 关闭 commentChecker、关闭 review.llm.required 等。目前没有 config 文件自身的 hash 或签名保护。Agent 可能关掉质量门然后通过 checkpoint。
5 并行 Agent admission 依赖 task state lock 中 admit 过程中 task state 分步更新（prepareAdmission → finalizeAdmission），中间如果 Agent 并发操作 task state，虽然 finalizeAdmission 加了锁，但 prepareAdmission 阶段没有全局锁。helix-parallel-agents:305-380 里的 updateAdmissionTask 有锁，但 getAdmissionTask 无锁。
6 Agent 可以构造 hook payload 注入 中 hook run 接受 stdin JSON。Agent 可以伪造 hook_event_name 触发不匹配的注入点。虽然有基本的 payload 校验，但缺少 HMAC 签名。
7 Dashboard 的 POST token 默认空 中 当 host=127.0.0.1 时，loopback 的 POST 也需要 token（文档正确），但默认 token 为空字符串。Agent 在本地可以通过 localhost POST API 绕过 CLI 直接调 runNextTask。虽然这不算安全漏洞（本地信任边界），但 Agent 可能通过 fetch 直接操作 runtime。
8 并行 Agent 结果无人认领时会堆积 低 子 Agent 成功后进入 awaiting_user_acceptance。如果 Agent 忘记 parallel close 或 parallel admit，结果永远挂起。没有 TTL 或自动清理。
