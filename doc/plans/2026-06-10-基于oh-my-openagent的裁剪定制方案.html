基于 oh-my-openagent 的裁剪定制方案

2026-06-10 ｜ 替代「从零自研 HelixFlow 内核」｜ 底座：code-yeongyu/oh-my-openagent v4.8.1（前名 oh-my-opencode，2026-06-09 仍在活跃发版）
结论：成立，且比自研路线删掉了最重的一整层。
oh-my-openagent 已官方支持 opencode（终极版）+ Codex CLI（lazycodex 轻量版），Claude Code 支持在上游重构路线图上 —— 原 HelixFlow 方案里最贵的「跨产品适配器编译器」整层不用做了。 策略一句话：不 fork、纯做减法 + 三个自有插件补强（治理硬门 / 工作保险箱 / 复利自进化），全部定制放自己命名空间，升级即重装。
License 红线（SUL-1.0，已核实条款）：✅ 内部商用允许、✅ 内部修改允许（须声明修改）、❌ 禁止商业性再分发。 团队内部用没问题；不可把它打包进对外售卖的产品。最佳实践：完全不改上游源码，定制全走 overlay 插件 + 配置，连「修改声明」义务都规避掉。

一 · 四目标映射：底座给了什么，缺什么

目标底座已有（保留）缺口（自建补强）
1 流程短+治理强天然三级分流：日常直接 Sisyphus / 中等 Metis→Prometheus→Momus→Atlas / 专项 ULW·team —— 正好对应你们的 任务/模块/专项治理偏软：Momus 设计上倾向放行，无硬质量门、无 spec 契约、无部署 HITL → gate 插件
2 自进化Oracle（≥2 次失败的难调试顾问）、模型能力类别路由无复利闭环（无召回/沉淀）→ compound 插件：CE 双轨 schema（bug 轨 symptoms/root_cause）+ bug→自动回归检查
3 可插拔原生最强：disabled_hooks、JSONC 双作用域配置（用户 ~/.config > 项目 .opencode/）、agent/skill/MCP 即插即用基本零自建，裁剪=改配置
4 同步/共享/不覆盖/可追回opencode ctx.worktree 一等公民 + snapshot:true；opencode-worktree-session 插件 ≈ M1 蓝图vault 插件：补 merge 收口、重仓(Unity)画像（branch-per-task+LFS 锁）、快照推远端、产物模板、飞书同步

二 · 裁剪清单（减法）

裁掉 Hephaestus

唯一硬依赖 GPT-5.5 的 agent。若不想绑双供应商订阅，disabled 即可；其职责由 Sisyphus+Oracle 覆盖。

收敛 模型回退链

上游 fallback 链含 kimi/glm/minimax 等家族，按团队实际订阅收敛到 Claude（主）+ 必要的 fast/cheap 档（Librarian/Explore 用）。

默认关 ULW / team 模式

小团队日常用不到大编队，专项再开。关=配置，不删能力。

整层删除 跨产品适配器编译器

原自研方案最重的一层。Codex 用 lazycodex 轻量版、Claude Code 等上游重构；git 层 vault daemon 保持产品中立兜底（误用 Cursor 也不丢工作）。

三 · 自建补强（三个 overlay 插件，全部 helix-* 命名空间）

helix-gate 治理硬门

  • 用 opencode 54+ 生命周期 hook + permission 机制做强制门：test 未过不许 commit、review P0 未清不许 push、部署须人工放行（HITL）
  • 思路抄 spec-workflow-mcp：门=工具返回值，不靠 agent 自律

helix-vault 工作保险箱（原 M1，载体换了）

  • 在 opencode-worktree-session 模式上补：merge 收口编排、轻/重仓画像（Unity: branch-per-task + git lfs lock）、快照推远端 refs/helix/snapshots、在途总览+一键恢复
  • R1–R7 需求原封不动有效，实现从「自研内核」缩水为「一个插件」

helix-compound 复利自进化

  • 召回前置（session start grep docs/solutions/ frontmatter）+ 沉淀后置（双轨 schema）
  • debug 自进化：每个修复的 bug 自动生成回归检查；bug 轨召回让同类问题越修越快 —— 上轮评审 P0 在此落地

原调研不浪费

PipelineAtlas 全部转为三个插件的抄袭来源：gate←spec-workflow-mcp、compound←CE schema.yaml、vault←opencode-worktree-session；HelixFlow 9 阶段方案降级为治理设计参考。

四 · 日常流程形态（裁剪后）

任务级：Sisyphus 直干→helix-gate 硬门→vault 自动落袋
模块级：Metis 预审→Prometheus 计划→Momus 审计划→Atlas 编排执行→gate→compound 沉淀
专项级：再开 ULW/team→同上 + 多 agent 并行（vault worktree 隔离）

六 · 风险与对策

风险对策
上游演进快（196 个 release、改名过渡期），fork 必然脱节铁律：不改上游一行码；定制全在 helix-* 插件 + 配置 overlay，升级=重装
SUL-1.0 非开源协议，禁止商业再分发仅内部使用；任何对外交付的产品不内嵌它
Claude Code 支持是上游「期货」近期主力真用 opencode（习惯迁移成本认了）；vault daemon 产品中立兜底
治理强度依赖自建 gate 插件的完成度M2 排在 vault 之后立即做；未完成前用 opencode permission 配置先顶硬约束
