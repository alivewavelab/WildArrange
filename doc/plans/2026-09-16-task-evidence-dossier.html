历史方案：任务证据夹与文档事实审计

2026-09-16。已实施；现行行为以代码、README 和项目架构文档为准。

目标与权威记录

获准任务在 Worker 启动前生成证据夹。当前任务状态仍只由 .wildarrange/team/tasks.json 持有；证据夹只保留开工时的历史切片及已有报告链接，不回写当前事实。

计划批准 → 开工能力检查 → 建立任务证据夹 → Worker → Verify → Scope → Review（长期文档事实审计） → Acceptance proof → Checkpoint

节点输入输出

节点输入输出与失败
建档获批 Plan/Task、任务投影、批准记录.wildarrange/task-packets/<planId>/<taskId>/ 下的 baseline.json、README.md、research.md。重试不覆盖原始基线；失败不启动 Worker。
Worker 简报任务范围、Skill、证据夹路径提示长期文档只写当前有效事实；研究和过程证据放到任务资料，且不扩大 writable_paths。
审计实际改动的长期 Markdown/HTML 文档全文（排除任务历史目录）独立 Reviewer 返回 PASS/RETURN/INCONCLUSIVE。RETURN 提供文件、行号、原文、原因和整改；未 PASS 禁止 checkpoint。
导航Plan/Task ID链接现有 readiness、review、failure、acceptance、checkpoint 报告；没有文件即没有该证据。

准则与边界

D1：长期文档只写当前功能、结构、用法和限制；任务时间线、尝试、日志及未落地想法放在任务证据。D2：同一当前事实只在权威来源维护；已验证同步的翻译或生成视图可保留。D3：历史设计明确标为历史。日期、版本号或真实迁移说明不自动构成违规。

不新增任务状态表、批准入口、Hook 放行路径或 Worker 可写范围。旧任务不补造基线。验收覆盖生成、重试、待批准、开工失败、文档 RETURN 阻断和非文档任务不增加审查。

执行与恢复协议

  1. 导入计划、完成人工批准；无批准的 run 直接返回，不建资料夹、不启动 Worker。
  2. 开工检查确认 Worker/Reviewer/Skill 可用。失败保留 readiness 报告，不消耗任务 attempt。
  3. 线性与并行运行各自在 Worker 启动前调用同一个建档函数。它按 Plan ID / Task ID 校验路径，拒绝符号链接，并以原子写入创建 baseline。README 和 research 索引也只在缺失时创建。
  4. 同任务重试检查已存在 baseline 的身份，不刷新首次时点。开工建档写失败时 fail closed；并行模式进入原有 claim 恢复链。
  5. Worker 只修改原任务允许路径。Scope 用真实 changedPaths 定位长期文档；Review 输入是改后全文与实际差异，结构化响应须绑定输入摘要且引用逐行原文。
  6. 有 RETURN 或 INCONCLUSIVE 则 Review 失败、Acceptance proof 与 Checkpoint 不成立。整改后重跑同一任务审查；若需扩大已批准范围，走现有 ChangeRequest/计划修订。

审查的边界

默认检查项目根 Markdown，以及 doc/docs 下承载现行规范、架构和产品说明的 Markdown/HTML。任务历史目录（plans、reports、research、evidence、verification-archive）、运行态 .wildarrange、依赖目录不当作现行说明书。项目仍可通过现有 review.steps 加挂模块规则，内置 D1–D3 规则不能用同名配置覆盖。证据须覆盖每份实际改动的长期文档；无独立 Reviewer、缺 Skill、源文件中途变化或回复无法逐行验证均为 INCONCLUSIVE，不放行。
