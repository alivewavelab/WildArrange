待用户审核 · 未授权写实现

老项目验证治理接管实施计划

把已经批准的产品设计拆成 6 个可独立验收的工程批次；最后一次联调通过前，不向用户暴露半成品 adoption 入口。

日期：2026-09-02｜设计依据：2026-09-02-legacy-project-verification-onboarding-product-design.html｜目标仓库：WildArrange

1. 交付结果

输入

一个已经存在测试、CI、Hook、旧文档和历史任务的老项目。

像接手一间住了很多年的房子。

→

处理

只读扫描 → 生成证据卡 → Dashboard 逐项批准 → 可恢复地执行 → 两次 Git 锚定。

先清点、再签施工单、逐项施工验收。

→

输出

整理后的仓库、Registry、Bootstrap、Inventory，以及持续新鲜度黄灯。

交付新目录、总账、交接单和过期提醒。

核心目标

用户能看懂并逐项决定每个验证资产的新增、修改、合并、归档、删除或暂缓；WildArrange 只执行获批项。

机器负责查证和施工，人负责签字。

明确不做

不自动删除，不自动 commit/merge/push，不执行来源不明的验证脚本，不把 Runtime Gate 穷举当作承诺，不建立第二套测试运行历史数据库。

这不是无人值守的大扫除机器人。

2. 开工前的真实阻塞

目标入口目前与大量未提交 WIP 重叠

bin/wildarrange.mjs 当前是未跟踪文件；gateway.mjs、dashboard.mjs、dashboard-panels.mjs、doctor.mjs、status.mjs、security.mjs、Prompt Pack manifest/routes 和多份测试均已有修改。

施工入口已经有人摆着材料，不能假装是空房直接覆盖。

开工条件：用户或当前 WIP owner 明确确认“以当前文件内容为实现基线继续”，或者先由原 owner 收口这些改动。禁止 reset、checkout、stash、clean、批量还原或替用户提交。

3. 最短模块方案

新增 6 个真实 owner 文件；其余只改现有入口与文档。扫描事实放 Infra，原子动作放 Capabilities，流程状态放 Orchestration，用户操作放 Interface。

文件技术作用为什么不塞进现有大文件
src/infra/recovery-transaction.mjs通用 preimage/postimage、提交、回滚和启动对账原语。
统一准备施工前照片和还原工具。
security.mjs 的现有 archive API 保持原样，只把可复用底层动作抽出，避免冒充已经通用。
src/infra/verification-discovery.mjs确定性枚举验证资产、入口、静态消费者证据和未知项。
负责沿着电线找“这个开关连到哪里”。
不把仓库扫描混进 Dashboard 或 AI Skill；复用 dependency graph、Git diff、路径和规则扫描结果。
src/infra/verification-registry.mjs三文件 schema、规范化 digest、声明输入指纹和 freshness 比对。
负责账本格式和“账本是不是过期”的盖章规则。
doctor、status、生成器需要共享同一套算法，不能各算一遍。
src/capabilities/verification-governance.mjs暴露 scan、apply-card、generate-artifacts 三个可审计原子能力。
把盘点、单项施工、出交接单做成三台独立机器。
不在 capability 内决定流程推进；经 gateway 返回统一证据信封。
src/orchestration/adoption.mjs接管会话、卡片批准、stale、维护互斥、恢复和两次提交状态机。
像现场项目经理，决定下一步能不能开工。
不复用 task/admission 状态名，不改 delivery pipeline 的完成语义。
src/interface/adoption-panel.mjsDashboard ViewModel、卡片 HTML/JS 和 adoption API 输入校验。
把施工单翻译成用户看得懂、能签字的页面。
避免继续膨胀接近拆分线的 dashboard.mjs；界面不直接碰业务文件。

4. 数据合同先钉死

本机会话目录

.wildarrange/adoption/<sessionId>/ 下保存 session.json、scan.json、cards.json、approvals.json 与 transactions/<cardId>/。

所有 JSON 使用原子写；transaction 目录自包含 preimage、postimage、manifest 和诊断。

即使断电，施工日志和原始材料仍在同一个工具箱里。

正式文件定位

在已存在的 wildarrange.config.json 增加可选 verificationGovernance 段，只保存 registryPath / bootstrapPath / inventoryPath。路径由扫描建议、用户在变更卡中批准，不由 init 静默创建。

总开关箱只贴三张“账本放在哪里”的标签。

变更卡

固定字段：id/action/asset/path/owner/purpose/consumers/evidence/confidence/reason/afterState/maxConsequence/patch/verify/rollback/fingerprint/mappingLoss。

每张施工单都写清对象、理由、后果和退路。

动作与批准

卡片动作仅 adopt/change/merge/archive/delete/defer；决定仅 approved/rejected/deferred。消费者未知时，系统根本不生成 merge/delete 可批准动作。

证据不够时，不是把危险按钮变灰，而是不提供按钮。

状态合同

scanning → reviewing → ready → applying → awaiting_registry_commit → awaiting_final_commit → finalized 异常结果：needs_review | recovery_required | cancelled 卡片状态：pending | approved | rejected | deferred | stale

这些状态只属于 adoption 会话，不进入 task.status，不产生 task completed，不借用 approvePlan。

这是独立施工进度表，不去改公司的工单结算规则。

“adopt”写到哪里

旧资产获批后的精确落点后续怎么生效
行为测试 SuiteRegistry 的 planDefaults.verify_commands 投影；若目标仓库已有明确的 WildArrange 计划模板，卡片另外展示该模板的精确 patch。单一 Skill 创建/修订未来计划时，把候选复制进真实 task/plan 的 verify_commands；不偷偷改当前活动任务。
静态工程检查Registry 的 planDefaults.standards_commands；只有与当前 qualityGates 精确同义时，另生成 wildarrange.config.json patch 卡。计划命令走 standards lane；配置卡只有逐项获批后才改变现有 Gate。
独立复核入口Registry 的 planDefaults.review_commands。未来计划由 Skill 写入真实 review_commands，并拒绝与 verifier 同义反复。
Runtime Gate / HookRegistry 的 runtimeGates / hostHooks 目录项；只有存在真实 adapter 配置目标时才另出 patch 卡。保留原副作用前位置；不搬进任务命令，也不冒充完成证据。
现有字段无法承接Registry 的 deferred 清单和 Inventory 的盲区区块。持续可见，但不生成虚假字段、不阻塞其他正确接管项。

verificationGovernance 配置段只是三个正式文件的 locator，不承载验证门语义，因此不属于“伪造一个 Gate 字段”。

Registry 先保存全项目的标准工具箱；以后开新工单时，Skill 把需要的工具真实放进工单，而不是只在仓库里摆一个没人用的清单。

5. M0：先固定合同和测试夹具

M0｜只建测试骨架，不开放命令

  • 建立最小老项目 fixture：package scripts、直接 import、Runner glob、CI/Hook 静态入口、动态加载、重复脚本、旧文档、旧任务、符号链接逃逸。
  • 把卡片 schema、状态迁移、三文件 schemaVersion 和错误码先写成测试断言。
  • 固定“扫描零业务文件写入”“未知消费者不能删除/合并”“不运行发现到的命令”。

测试文件：test/verification-discovery.test.mjs、test/adoption-runtime.test.mjs 的首批失败用例。

退出条件：失败测试准确表达批准设计；没有 CLI、Dashboard 路由或发布入口。

先画验收红线，防止施工时把风险解释掉。

6. M1：只读扫描与可判对卡片

M1-1｜确定性发现

  1. 从 Git 跟踪文件、工作区新增文件和明确排除目录生成候选集合；排除 .git/、.wildarrange/、依赖缓存、构建产物和用户确认的 archive 根。
  2. 复用 dependency-graph.mjs 的词法 import；复用 git-diff.mjs 的 WIP 基线；用 path-match.mjs 做 glob/realpath 边界。
  3. 结构化解析 package JSON；对 CI YAML、shell/batch、Hook 配置只做入口级字符串和 token 证据，不宣称完整语义解析。
  4. 发现动态 import、变量拼接、eval、生成配置或未知 Runner 时标记 consumerUnknown=true。

退出条件：同一仓库重复扫描得到同序、同 ID、同 digest；扫描期间业务文件 byte-for-byte 不变。

盘点两次必须得到同一本清单，而且不能碰屋里的东西。

M1-2｜分类、映射和预览

  • 把证据转换为六类动作建议；证据只到线索级时强制 defer。
  • 映射到真实 verify_commands、standards_commands、现有精确 qualityGates、review_commands 或 adapter 建议。
  • 近似映射必须填 mappingLoss，给出拆分或 defer；不得静默选一个相似字段。
  • 旧文档/任务只有在存在明确后继真源且引用核验后才能建议 archive；Git 历史是全文历史库，Registry 只存结构化索引或 tombstone。

能力登记：gateway.mjs 新增 verification-governance-scan，结果 sideEffect 只能是运行态报告写入，业务文件副作用为零。

退出条件：每张卡完整回答“是什么、作用、谁使用、为什么处理、之后怎样、最大后果、怎么恢复”。M1 仍无公开入口。

清单不是只写“建议清理”，而是每项都能让人判对。

7. M2-0：先提炼通用恢复原语

M2-0｜只泛化底层，不改变既有归档和 admission

  • 从 security.mjs 抽出路径校验、preimage 复制、postimage digest、原子 manifest 更新和精确恢复的通用原语。
  • prepareArchiveRecoveryPackage 与 updateArchiveRecoveryPackage 保持公开签名、返回结构、kind: task_archive_recovery、manifest 位置和状态集合不变。
  • 不改 admission 的 owner/base/main fence，不改已 push 不得回滚，不改 recovery_required ownership。
  • adoption 使用独立 kind: adoption_change_recovery，不得写入 task archive 的业务字段。

测试：新增 test/recovery-transaction.test.mjs；扩充现有 task archive/state restore 测试，逐字段对比重构前后的 manifest 与返回值，并覆盖文件、目录、symlink、部分失败、重复恢复。

硬退出门：现有 archive/admission 回归测试全部通过后，M2-1 才能开始。

先把通用保险箱造好，但不能顺手改变旧保险箱的钥匙。

8. M2-1：审批、互斥、Apply 与恢复

Dashboard 唯一写入口

新增只读 GET /api/adoption/session 和受保护的 POST /api/adoption/decision、/apply、/reconcile、/cancel。全部复用现有 Host、Origin、token、payload size 和 ID 校验。

删除、合并、AGENTS/CI/build/Hook/Runtime/测试策略变化只能逐卡批准；普通 adopt/change 才允许同风险批次批准。

只有一个签字台，而且拆线路必须一张一张签。

现场指纹

批准记录绑定卡片规范化 digest、目标 path preimage digest、HEAD、WIP path set 和消费者证据 digest。Apply 前任一项变化则该卡进入 stale。

施工前再看一次门牌、现场照片和签字单是否还是同一套。

维护互斥

开始 Apply 前短暂获取全局 task lock，只检查无活动 run/admission 并原子登记 maintenance marker，随后释放；实际执行持独立 adoption lock。日常 run/admission 看到 marker 后返回明确“接管维护中”，不等待 15 秒超时。

先在总前台挂“维护中”，再用施工队自己的钥匙工作。

逐卡事务

一次只执行一张 approved 卡：prepare → apply exact paths → run approved isolated verifier → write postimage → commit card；失败只回滚本卡。恢复失败立即停止并保留 marker、transaction 和恢复指令。

一间一间验收，哪间出问题只恢复哪间。

测试：test/adoption-runtime.test.mjs 覆盖并发 start、活动 task/admission、stale、越界路径、symlink、验证失败、回滚失败、断电点故障注入、resume 幂等；test/adoption-dashboard.test.mjs 覆盖授权、跨站请求、非法 ID、逐卡批准和页面文案。

退出条件：任意注入中断后，adoption status/resume 能由磁盘确定唯一下一步；失败时没有越界写、没有错误清 maintenance marker。

9. M3：三文件、Git 锚定与持续消费

M3-1｜Registry → commit A → Bootstrap/Inventory → commit B

  1. 所有获批卡完成后生成 Registry 和获批的 config locator 变更，进入 awaiting_registry_commit。
  2. 用户自行 commit；reconcile 验证 HEAD 确实包含 Registry 与 locator，记为 baselineRef=commit A。
  3. 生成 Bootstrap 与 Inventory。Inventory 保存 Registry digest、Bootstrap digest、声明输入 path 清单和 discoveryUniverseFingerprint，排除 Inventory 自身与 archive 内容。
  4. 进入 awaiting_final_commit；用户自行 commit B。reconcile 验证 HEAD 包含两文件且声明输入未漂移后才 finalized。

第一张收据证明总账已经落地，第二张收据证明交接单也正式入库。

Freshness 消费点

doctor 新增独立容错的 registryFreshness 分项；status 读取同一 Infra 结果摘要；Inventory 生成器和 Skill 显式检查也消费 Registry。漂移只亮黄灯和给下一步，不自动扫描、不阻断日常 run。

账本过期会亮灯提醒，但不会突然锁住正常工作。

单一 Skill

新增 packs/wildarrange-linear/skills/verification-governance.md，同步 manifest、routes、tool-contract 与安装测试。Skill 只能显式调用产品命令；Hook 不得静默全仓扫描。

Skill 是会带路的项目经理，不是躲在门后的自动清洁工。

命令行为何时公开

12. AGENTS 特别批准项

本计划本身不修改 AGENTS；实现前需要用户单独明确批准

现状：根目录约定没有 adoption、verification discovery、registry freshness 和 recovery transaction 的真实 owner；src/capabilities/AGENTS.md 的 gateway 注册名清单也没有新能力。

为什么现有栏目无法完整容纳：它们能说明五区原则，却不能告诉维护者“接管状态归谁、三文件算法归谁、网关真实注册了什么”。实现完成后不登记会让架构文档与代码事实分叉。

拟改范围：仅在根 AGENTS.md 目录表新增上述 6 个 owner 行；在 src/capabilities/AGENTS.md 更新 gateway 注册名。除非实现发现新的不可容纳约束，不改其他 AGENTS，不改 schema，不放宽依赖白名单。

更短替代：把代码塞进现有 security.mjs、dashboard.mjs 或不登记 owner；前者混合事务/界面职责并逼近文件拆分线，后者违反“架构事实必须登记”，均不采用。

影响：只增加职责说明和真实能力名，不削弱 verifier/scope/review/acceptance-proof/checkpoint，不改变长期 Agent 白名单。

新建六个部门工位，需要更新楼层导览，但不改公司规章和审批制度。

15. 人工验收剧本
