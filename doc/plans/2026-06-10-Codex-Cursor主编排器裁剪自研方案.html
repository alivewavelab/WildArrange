Codex / Cursor 主编排器裁剪自研方案

2026-06-10 ｜ 只适配 Codex + Cursor；无法跨工具统一的能力后续做单独 adapter
一句话：我们要学 oh-my-openagent 的“主编排闭环”，不是学它的全家桶。
它最强的地方不是多工具适配，而是有一个主编排器集中做：规划、拆任务、分派编码、项目状态管理、测试、循环修复、质疑式验收、长任务续跑。我们可以用 Codex / Cursor 做主入口，再用 skills 拉起外部 Agent 协同：Codex 子代理、Kimi Code、DeepSeek CLI、opencode team 工具都只是 worker。

一 · 重新定义 oh-my-openagent 的强项

表层能力真正强点我们怎么借
11 个 Agent / 神话角色不是重点。重点是角色被主编排器统一调度，而不是用户手动切人。我们保留“规划 / 编码 / 审查 / 调试 / 测试”职能，不保留复杂角色命名。
Team Mode共享任务板 + 消息队列 + 成员状态 + 回执，不是神秘能力。先做 .helix/team/ 的 Markdown/JSON 消息板，够用后再接实时 adapter。
ulw-loop / start-work长任务靠状态文件和 Stop hook 续跑，不靠模型记忆。做 .helix/work.json + ledger.jsonl，Codex 可用 hook，Cursor 用 CLI/daemon 兜底。
review/debug gate实现完成不算完成，必须被独立视角质疑、运行、复现、修复。做 helix-gate：review、debug、test 都是硬门。

二 · 我们的核心架构

主编排器
Codex / Cursor→ 计划与任务板
.helix/plan.md→ 消息板
.helix/team/→ 外部 Agent Workers→ 回执 + 证据
ledger.jsonl→ 质疑式验收
review/debug/test gate

主编排器只保留一个

默认是 Codex；Cursor 是第二入口。主编排器负责目标理解、拆任务、分派、收回执、判断是否继续、最终交付。

Worker 可以很多

Kimi Code、DeepSeek CLI、Codex 子代理、opencode team member 都只是 worker。它们不拥有项目真相，只交付回执。

消息板先用文件

不用一开始做复杂实时系统。.md 消息 + .json 状态足够支撑协作，后面再接 opencode 的实时消息。

证据账本是硬中心

每个 worker 的结果必须写入：改了什么、跑了什么、证据在哪、风险是什么。没有证据不算完成。

三 · 最小消息板设计

.helix/
  work.json                 # 当前主编排状态：目标、阶段、活跃 worker、是否阻塞
  plan.md                   # 主计划：TODO / 验收标准 / Final Verification
  ledger.jsonl              # 每条证据一行 JSONL
  team/
    members.json            # codex / cursor / kimi / deepseek / opencode-worker
    tasks.md                # 共享任务板：pending / claimed / done / blocked
    inbox/
      kimi/
        2026-06-10T153000Z-task.md
      deepseek/
        2026-06-10T153100Z-review.md
    outbox/
      kimi/
        2026-06-10T154200Z-result.md
    processed/
对象作用为什么不用一开始做复杂
tasks.md所有 worker 看到同一个任务板，claim 后执行。Markdown 人也能看，Agent 也能读。
inbox/outbox主编排器给 worker 发任务，worker 回结果。文件就是最简单可靠的 mailbox。
ledger.jsonl不可篡改风格的执行证据流。以后可直接接 review gate / restore / 飞书同步。
work.json机器读状态：当前跑到哪里，哪些 worker 未回。Codex hook 和 Cursor daemon 都能读。

四 · Worker 适配顺序

优先级Worker接入方式用途
P0Codex 子代理multi_agent_v1.spawn_agent，prompt 自包含。最快验证主编排模型。
P0Cursor先共享 .helix/ 状态与规则；复杂 hook 后续单独 adapter。第二主入口，保证团队成员不被 Codex 绑定。
P1Kimi Code通过 skill/CLI 拉起，读 inbox，写 outbox。长上下文、中文理解、低成本编码/审查。
P1DeepSeek CLI直接代码型 worker，输入任务文件，输出结果文件。便宜的实现/改写 worker。
P2opencode Team Mode借 team_send_message / team_task_create；先参考，不作为主依赖。如果要实时协作，再接它。

五 · 产品路线改写

M1：主编排器 + 文件消息板

先做 Codex 主入口、.helix/work.json、tasks.md、inbox/outbox、ledger.jsonl。目标：能分派一个任务给外部 worker 并收回证据。

M2：工作保险箱

把 checkpoint / restore / merge 收口接到同一套 ledger。目标：任何 worker 做的事都不会丢。

M3：质疑式验收

review/debug/test gate 一等化。目标：实现完成后自动被质疑、运行、复现、修复。

M4：Cursor + 外部 Agent adapter

Cursor、Kimi、DeepSeek、opencode 都走单独 adapter。能通用的走 .helix/ 文件协议，不能通用的后补。

六 · 当前判断

你的理解是对的：我们可以简单实现一个“md 消息板”。
先不要把精力放在多工具完美适配，也不要复刻 oh-my-openagent 的复杂 Team Mode。第一性原理是：主编排器需要一个可靠的任务板、消息通道、证据账本和验收门。只要这四件事成立，Kimi、DeepSeek、Codex 子代理、Cursor、opencode 都可以逐步接进来。
