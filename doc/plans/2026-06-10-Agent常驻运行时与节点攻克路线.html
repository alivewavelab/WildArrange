Agent 常驻运行时与节点攻克路线

2026-06-10 ｜ 基于 oh-my-openagent 官方文档 + 源码阅读 + 图 1 六原则
核心判断：常驻的不是“模型大脑”，而是 Agent Runtime。
API 模型本身是无状态请求；能常驻的是本地进程、会话句柄、任务队列、消息板、状态文件、上下文缓存和工具连接。项目初始化时可以创建一组长期存在的 Agent Runtime，但每次调用模型仍要把当前任务、记忆、工具权限和消息上下文喂进去。也就是说：常驻进程 + 持久状态 + 可恢复会话，而不是把 GPT / Kimi / DeepSeek 变成一直醒着的进程。

一 · 常驻 Agent 能不能做

层级能否常驻含义我们怎么做
模型 API不能真正常驻每次都是请求/响应；上下文需要重新传或引用线程/会话。用 agent_id + thread_id + memory_refs 记录状态。
本地 worker 进程可以例如 Kimi Code CLI、DeepSeek CLI、opencode、Codex 子进程、MCP server。由 helix-agent-runtime 拉起、保活、重启。
任务/消息/证据状态必须常驻这是系统真相。进程死了也能从这里恢复。落在 .helix/：work、team、ledger、memory。
工具连接可以MCP、LSP、AST、git、浏览器、测试服务等。按 Agent Profile 装载工具，不让所有 Agent 都背全量工具。

五 · 图 1 六原则如何落地

Specialization

每个 Agent 只做一类事。Sisyphus 不写所有代码，Atlas 不做深度架构，Oracle 默认只读。

Trust But Verify

所有 worker 结果必须经过独立验证。实现者的 DoneClaim 不能直接变完成。

Wisdom Accumulation

每个任务结束后沉淀 learnings / decisions / issues / verification，下一个任务自动注入相关经验。

Model Optimization

昂贵模型用在计划、裁决、疑难；便宜模型做搜索、git、小任务。路由由 category 决定，不由用户手选。

Category System

主编排器只说“visual-engineering / quick / deep”，路由层再选 Gemini / DeepSeek / GPT。

Session Continuity

用 .helix/work.json 和 ledger.jsonl 恢复中断状态，不依赖聊天窗口还活着。

六 · 节点攻克顺序

阶段攻克对象交付物验证标准
1Sisyphus 主编排器提示词、工具边界、技能清单、状态读写协议。能把一个用户目标拆成计划，并路由到正确 Agent。
2Atlas 执行器任务板、执行循环、worker 分派、回执格式。能执行一个计划中的第一个 checkbox，并写 ledger。
3Hephaestus / Oracle深度实现 + 只读质疑两个核心 worker。同一任务实现与验证分离。
4Librarian / Explore文档检索、代码检索、上下文包生成。能给计划和实现阶段提供可引用上下文。
5Metis / Momus计划 gap check 与 plan gate。不完整计划会被打回。
6Dynamic Agentscategory routing：visual / quick / deep / writing / git。同一任务按类别走不同模型。
7路由与门IntentGate、ReviewGate、DebugGate、TestGate。未验证成果无法进入完成状态。
8全流程串联init → plan → work → verify → wisdom → resume。中断后可恢复；完成后有证据链。

七 · 会话丢失恢复 loop

新 Codex / Cursor 会话启动→ 读取 .helix/work.json→ 读取 context 快照→ 读取未完成 tasks + ledger→ Sisyphus 恢复当前工作
丢失场景恢复依据系统行为
用户误关 Codex / Cursorwork.json + sessions/active.json新会话自动提示“检测到未完成工作”，恢复主编排入口。
用户删除对话，模型不知道snapshots/context.md + tasks.md + ledger.jsonl不依赖聊天记录，按最近上下文快照和证据账本继续。
Worker 做到一半没回team/inbox、outbox、任务状态Atlas 标记 stale worker，重发任务或改派其它模型。
上下文快照过旧ledger.jsonl 重放根据最后证据事件重建当前阶段，必要时让 Oracle 做恢复审查。

设计原则

不把完整聊天当主记忆。每次关键阶段切换、worker 完成、gate 通过、用户变更目标时，写一次 context.md 快照。聊天摘录只做兜底证据，避免历史噪音污染模型判断。

八 · 状态写入机制：不是每句聊天都进 JSON

事件谁写写到哪里是否需要模型判断
生成/更新计划Sisyphus / Prometheusplans/*.md、work.json需要，属于语义决策。
任务分派Atlasteam/tasks.md、sessions/active.json少量需要，主要是确定性写入。
Worker 回执Worker adapterteam/outbox/**、ledger.jsonl不需要持续监视，worker 完成时提交结构化回执。
代码 diff 产生Runtime / git watcherledger.jsonl、checkpoint ref不需要模型，先记录文件和 diff 摘要。
用户明确变更目标Sisyphuschanges/open.md、snapshots/context.md需要，判断变更级别和影响面。
Gate 通过/失败Gate 工具ledger.jsonl、work.json检查本身尽量确定性；失败解释可让模型补充。

关键点

需要常驻的是 Runtime / watcher / hook，不是一个一直读聊天的模型。模型只在“需要语义判断”的节点被调用；其余状态写入由工具完成。

九 · 临时加功能 / 设计问题变更 loop

用户临时加功能 / 发现设计问题→ Sisyphus 判断变更级别→ Metis 查影响面→ Prometheus 更新计划/规格→ Momus 审变更→ Atlas 重排任务
变更类型进入哪个 loop允许谁改验收条件
小功能追加，不影响架构Plan DeltaSisyphus + Atlas新增任务有验收标准，原任务不被覆盖。
发现设计不合理Design DeltaPrometheus + visual-engineering + Oracle设计决策写入 changes/decisions.md，相关实现任务重排。
需求目标变化Spec DeltaSisyphus + Prometheus + Momus旧目标与新目标差异明确；受影响任务全部标记。
实现中发现技术不可行Architecture DeltaOracle + Metis + Sisyphus必须有运行证据或代码证据；不能靠 worker 口头说“不行”。

对齐 OMO 的做法

OMO 里 Prometheus 负责计划、Metis 找遗漏、Momus 审计划、Atlas 重排执行。我们要补的是“变更不是打断，而是 delta”。任何临时需求都先进 .helix/changes/open.md，经影响分析后再合入计划。

十 · ScopeGuard：计划外写入门控

Worker 尝试写文件→ PreWrite/隔离工作区记录意图→ 对照 task scope→ 允许 / 隔离 / 拒绝→ 触发 ChangeRequest
场景门控动作触发路由
写入文件在当前任务 writable_paths 内允许写入，记录到 ledger。继续 Atlas 执行 loop。
写入文件超出范围，但只是测试/文档证据允许到 .helix/artifacts 或任务专属 evidence 目录。Atlas 后续审查是否纳入正式变更。
写入计划外业务代码在可控工具层直接拒绝；若来自外部 CLI，则留在隔离 worktree，禁止 merge/admit。生成 ChangeRequest，交给 Sisyphus。
Worker 发现必须改计划才能完成不得直接改生产代码扩大范围；写 changes/open.md。Sisyphus → Metis 影响分析 → Prometheus 更新计划 → Momus 审核。
用户口头追加功能暂停相关任务完成判定，记录目标变更。Sisyphus 判断小改/设计变更/规格变更/架构变更。

能不能“锁死无法入盘”

在 Codex 自己的写文件工具里可以做 PreToolUse/permission 拦截；但外部 CLI 或 Cursor 直接写磁盘时，很难靠模型阻止 OS 写入。更可靠的做法是：worker 默认在隔离 worktree 或任务沙盒写，ScopeGuard 在“进入主工作区 / merge / checkpoint admit”时硬拦。也就是不一定阻止落到临时盘，但必须阻止进入正式成果。

十一 · 代码实现 loop：先线性复刻，再并行增强

先纠偏

worker 提交代码后，默认不是 Prometheus 再去问用户“这次完成了啥”。Prometheus / Metis / Momus 主要工作在计划前：Prometheus 访谈并写计划，Metis 找计划遗漏，Momus 审计划是否可执行。代码完成后的主循环由 Atlas 接管：收 worker 回执、读 diff、派独立 verifier、失败则重试，必要时升级给 Sisyphus 或用户。

Atlas 读计划任务→ 派发 worker→ Worker 改代码 + 回执→ Atlas 收 diff / evidence→ 独立 Verifier 审核→ PASS checkpoint/ FAIL retry
节点谁负责输入输出失败时
任务开始Atlasplan、task scope、开发规范、验收标准结构化任务包：目标、允许文件、禁止事项、验证命令。上下文不足则回到 Sisyphus / Prometheus 补计划。
代码实现Hephaestus / deep / quick worker任务包 + 相关上下文代码 diff、测试尝试、DoneClaim、风险说明。不能直接扩大范围；只能发 ChangeRequest。
状态回传Worker adapterworker 回执、changed files、命令输出team/outbox、ledger.jsonl、任务状态。回执不完整则任务保持 in_progress 或 failed。
独立验证Verifier：Oracle / deep reviewer / QA executor原目标、约束、diff、完整文件、运行方式、规范PASS / FAIL + 证据。FAIL 退回原 worker；同一问题多轮失败再升级。
入盘 checkpointAtlas + Gateverifier PASS、测试证据、scope 检查checkpoint / 可提交成果 / wisdom。没有 PASS 不允许进入完成态。

多 Agent 什么时候一起上

第一阶段不要一开始就每个小任务拉满多 Agent。最短可行版本是“一个 worker + 一个独立 verifier”。当任务是 P0/P1、跨模块、架构性、UI/安全/数据风险高，才进入并行审核：Goal Verifier、QA Executor、Code Reviewer、Security Auditor、Context Miner 同时跑；任何主审核 FAIL，整个 loop FAIL。

我们按 OMO 100% 抄的部分

抄它的运行秩序：计划与执行分离；worker 不自证完成；完成先写任务状态和消息；lead/Atlas 读任务板做 closure 判断；worker 完成后立刻派外部 verifier；verifier 未 PASS 不做 checkpoint；失败回退原任务并附具体失败证据；连续失败再问用户。

不照抄的部分

不照抄 OpenCode Ultimate 的工具表面。Codex Light 官方明确没有完整 agent orchestration 和 team_* tools，所以我们在 Codex / Cursor 上要自研轻量 Runtime、消息板、任务状态和 gate，而不是假装这些工具已经存在。

十二 · 代码实现中的规范注入与验收复核

Atlas 分派代码任务→ 注入开发规范 + 上下文包→ Hephaestus / deep worker 实现→ 自动测试 + LSP/AST→ Oracle / ReviewGate 质疑→ TestGate + Wisdom
注入内容注入节点来源作用
全局开发规范Sisyphus 会话启动 + Atlas 分派前AGENTS.md、CLAUDE.md、doc/agent-standards/**所有任务默认遵守。
任务上下文包Atlas 分派 worker 前plan、相关文件、接口契约、历史决策降低 worker 猜测，避免乱翻无关文档。
领域专项规范Category 路由时frontend/backend/database/privacy 等分流文档只给相关 worker 注入，避免上下文膨胀。
验收标准ReviewGate / TestGateplan TODO、需求 delta、用户补充约束复核不是泛泛 review，而是逐条对照要求。
Gate检查什么不通过怎么办
StandardsGate是否违反项目规范、目录约定、命名、架构边界。退回实现 worker，附具体规范引用。
SpecGate是否完成用户目标、临时变更和验收标准。回到 Atlas 重排或补实现。
ReviewGate正确性、安全、维护性、回归影响。未解决 P0/P1 不得进入测试完成。
TestGate测试是否实际运行，主路径和边界是否有证据。补测试/补运行证据，不能只说“不报错”。
WisdomGate是否沉淀 bug、决策、踩坑和复用建议。完成前写入 wisdom/ 或 ledger。

关键点

开发规范不是塞给最后验收节点才看，而是三次注入：会话启动建立底线、Atlas 分派时形成任务上下文包、ReviewGate/TestGate 按同一套规范逐条复核。

十三 · 路由机制：关键词只是入口，不是唯一判断

信号例子作用实现方式
关键词“加功能”、“修 bug”、“设计不对”、“跑测试”、“发版”快速猜测意图。.helix/router/rules.yml 维护少量高价值词表。
行为事件写计划外文件、测试失败、review P1、worker BLOCKED比关键词更可靠。hook / watcher / gate 产生结构化事件。
文件范围改了 src/api/**、schema/**、*.unity判断领域与风险。对照 writable_paths、领域 globs、不可合并文件规则。
当前阶段plan 阶段、work 阶段、review 阶段、deploy 阶段同一句话在不同阶段意义不同。读取 work.json.stage。
用户显式指令“先别做”、“这是需求变更”、“直接继续”最高优先级。Sisyphus 写入 changes/open.md 或更新状态。

是否需要 sh 脚本自动触发

可以有，但不应该只有 sh。最小实现是 CLI/hook 触发：Codex 用插件 hook；Cursor 用本地 CLI/daemon；git 用 pre-commit/pre-push；文件变更用 watcher。sh 脚本适合做兼容层，不适合做全部治理逻辑。

十四 · 工作空间隔离与正式成果入云

同一项目→ 每个用户一个 workspace→ 每个任务一个 branch/worktree→ 本地 Gate 通过→ PR / 云端正式成果
层级拦截点目标
本地工作空间ScopeGuard / watcher / task sandbox不让计划外内容进入当前任务成果。
本地合并merge/admit gate不让未验证 worker 结果进入主工作区。
Git 边界pre-commit / pre-push / PR check不让未通过治理门的变更进入远端。
云端正式成果PR review / CI / owner approve主要负责人最终放行。

原则

不鼓励两个工具同时写同一个工作空间。Codex、Cursor、Kimi、DeepSeek 可以都安装治理系统，但同一任务应该只由一个主编排器持有写权限。其它工具作为 worker 或 reviewer，通过消息板和隔离空间协作。

十五 · 用户身份与 workspace 创建

识别来源优先级优点问题
GitHub 登录账号最高团队协作语义最好，能和 PR/权限对应。可能未登录或 token 失效。
Git config email/name第二本地总能读到，和 commit 关联。多人共机或配置错误时不可靠。
首次启动录入 user_id兜底明确、稳定、离线可用。多一步，但只需一次。
helix user init
  1. 尝试读取 GitHub: gh api user / gh auth status
  2. 失败则读取 git config user.email / user.name
  3. 仍不可信则提示录入 user_id
  4. 写入 ~/.helix/identity.json
  5. 在项目写入 .helix/users/{user_id}.json
  6. 创建 workspace: .helix/workspaces/{user_id}/ 或 ../{repo}.helix-{user_id}/
用户空间内容用途
.helix/users/{user_id}.json身份、权限、默认模型、可用工具、GitHub 映射。
.helix/workspaces/{user_id}/该用户的本地状态、任务锁、临时证据。
branch: helix/{user_id}/{task}远端可见的隔离工作分支。
refs/helix/snapshots/{user_id}/{task}防丢快照，不污染主分支。

验证与权限

初始化时做三步验证：身份可读、workspace 可写、git remote 可访问。不能确认 GitHub 身份时仍可本地工作，但进入 PR/云端正式成果前必须重新确认 GitHub 身份。

十六 · 质疑审核依据：不是纯 prompt

依据层来源用途
用户目标plan / spec / changes / 用户最近确认判断“是不是做了用户要的事”。
开发规范AGENTS.md、CLAUDE.md、doc/agent-standards/**判断目录、架构、代码风格、测试要求是否违规。
任务边界tasks.md、writable_paths、work.json判断 worker 有没有计划外扩张。
代码事实git diff、changed files、完整文件内容、AST/LSP 结果判断实现是否正确、是否引入回归。
运行证据test output、browser screenshot、curl、tmux、日志、复现步骤判断“真的跑过”，不是只说不报错。
历史经验wisdom/、ledger.jsonl、过往 bug 轨判断是否踩过同类坑、是否需要回归检查。

Prompt 的位置

prompt 只定义“怎么审”：拆目标、逐条对照、找边界、提出反例、要求证据。prompt 不是证据本身。没有 diff、运行证据、规范引用和 ledger 的审核，只能算意见，不能过 Gate。

十七 · 协同小黑板与远端唯一凭证

本地 .helix/team→ 周期同步远端→ GitHub / Git 平台→ PR / check / commit SHA→ 正式成果凭证
层级是否可信说明
本地小黑板临时可信给当前用户/当前工具恢复和协作，不代表正式成果。
远端小黑板团队可信通过 GitHub/Git 远端同步，供不同用户和工具拉取。
PR / commit / check run正式可信唯一可审计凭证。最终以远端提交、PR 审批、CI/Gate 状态为准。
同步方式适用阶段取舍
周期 git fetch / git pull --rebaseM1最简单，无服务端依赖。适合小团队。
远端 refs：refs/helix/team/*M1/M2不污染主分支，适合状态和快照。
PR comments / checksM2适合审核结果、Gate 状态、正式交接。
Webhook / 服务端同步后续实时性更好，但不是第一版必须。

拉取频率

默认不是每秒轮询。可以按事件 + 低频轮询：会话启动立即拉一次；用户要继续任务时拉一次；worker 提交结果后推一次；后台每 1-5 分钟拉一次，失败退避。小团队先用这个足够。

十八 · OMO 证据与我们的裁剪边界

结论OMO 证据我们的落点
计划与执行分离官方 orchestration 文档写明 @plan → /start-work，Prometheus 计划，Atlas 执行。先做线性：Sisyphus/Prometheus 出计划，Atlas 单任务执行。
Momus / Metis 主要审计划官方文档：Metis 是 gap analyzer；Momus 用 clarity、verification、context、big picture 审计划。不要把 Momus 当代码 reviewer。代码后审核走 Oracle / QA / ReviewGate。
worker 完成后要独立验证refactor skill 的 team loop：worker completion 后立刻派 external verifier；未 PASS 不 checkpoint；FAIL 后 retry；三轮失败再问用户。我们实现 DoneClaim → VerifyTask → PASS/FAIL → retry/checkpoint。
Team Mode 是状态机，不是聊天群team mode 有 state.json、inboxes、tasks/{id}.json，成员必须 team_task_update 和 team_send_message。我们的“小黑板”必须是 md 给人看 + json/jsonl 给机器判定。
Codex 不能直接获得 Ultimate 能力官方 Installation 文档写 Codex Light 只有 portable components，没有 agent orchestration 和 team_* tools。Codex/Cursor 适配层自研轻量 Runtime，先跑通 M1。

十九 · 关键取舍

先不要一上来做“真常驻多 Agent 集群”。
最短可行版本是：项目初始化生成 Agent Registry；主编排器按需拉起 worker；所有 worker 通过文件消息板和 ledger 回传结果；Runtime 负责保活和恢复。这样既能模拟常驻团队，又不会被某个 CLI/插件能力绑死。
