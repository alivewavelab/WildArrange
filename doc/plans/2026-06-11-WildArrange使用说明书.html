WildArrange 使用说明书

这份说明书只讲怎么用，不讲模型 key、provider、baseUrl 等配置细节。你可以把 WildArrange 理解成项目里的“流程主管”：它不替你写所有代码，但会把需求拆成计划、执行、验证、范围检查、复核、checkpoint，并把证据留下来。

当前可用状态

可以开始试用。当前已经具备线性治理闭环、跨会话恢复、路由、skill 匹配、验收门、失败返工、并行子 Agent 最小闭环和 npm 发布预检。

边界也要清楚：现在不是 Codex marketplace 式一键插件，而是 npm CLI + project adapter。Codex/Cursor 能通过项目内规则和 hook 配置接入；更深层的宿主私有后台 Agent API 属于后续 adapter 增强。

一、第一次安装后怎么试

第 1 步

进入你的测试项目

建议先找一个空项目或低风险项目，不要一上来放到重要生产仓库。

cd /path/to/test-project
第 2 步

初始化运行时

这会创建 .helix/，里面存任务、账本、报告、上下文和恢复信息。

npx @alivewavelab/wildarrange@latest init
第 3 步

安装 adapter

Codex/Cursor 会得到项目级规则或 hook 配置。新会话时，模型能读取恢复上下文和项目规则。

npx @alivewavelab/wildarrange@latest adapter install

二、新开 Codex 会话怎么用

1

打开同一项目

新会话必须在同一个 workspace，否则读不到 .helix/ 状态。

2

先让它恢复

第一句话建议让 Codex 读取 WildArrange 状态。

3

先计划

不要直接说“做完”。让它先路由、拆任务、写验收标准。

4

再执行

执行时必须有 writable_paths 和 verify_commands。

5

看 gate

完成不是 Agent 说了算，要看 verifier、scope、review、checkpoint。

6

验收后收尾

确认通过后再 summary、关闭并行 Agent 结果。

新会话第一句话模板

请先读取本项目 WildArrange 状态，执行 resume/status，确认当前计划、下一步任务、失败项和未关闭的并行 Agent 结果。不要直接改代码。

如果 Codex 没自动读状态

node ./bin/helix.mjs resume
node ./bin/helix.mjs status
node ./bin/helix.mjs continuation check

三、怎么激发不同 Agent

WildArrange 的核心不是让用户记 Agent 名字，而是让用户说清阶段和目标。路由会决定该加载哪些 Agent / Skill。你可以用下面这些说法提高命中率。

你想要的效果推荐说法通常激发注意
需求澄清 / 产品方向 “先不要写代码，先澄清目标、用户路径、范围取舍和验收标准。” Jiuwei、ProductIntentReviewer、UserJourneyMapper、AcceptanceDesigner 适合新功能、大功能、体验不确定的问题。
架构 / 计划 “先做计划，拆成可验证任务，每个任务写 writable_paths 和 verify_commands。” Jiuwei、DiJiang、wa-plan、wa-architect 这是防止后面做歪的关键步骤。
编码执行 “按当前计划执行下一个 pending 任务，完成后必须跑 verifier、scope、review、checkpoint。” YingLong、ZhuRong、programming、debugging 不要让 worker 自己宣布完成。
质疑式验收 “不要相信 worker 的完成声明，请按目标、范围、测试、项目规范做复核。” BaiZe、LuanNiao、QiongQi、review-work、wa-review 适合完成前、合并前、发布前。
UI / 视觉 “这是 Web UI 任务，请按用户体验、空状态、交互反馈和视觉 QA 处理。” visual-engineering、frontend-ui-ux、visual-qa 完成后最好补截图或浏览器验证。
快速调研 “先快速调研，不要改文件，只给结论、证据和建议路径。” Kui、Taotie、ultraresearch 适合不确定问题，不适合直接落代码。

四、日常工作流

计划

先把任务变成计划

一切治理都围绕计划文件和任务状态。没有计划，后面 gate 很难判断完成。

node ./bin/helix.mjs route --text "做一个网页版提醒事项 App"
node ./bin/helix.mjs plan --from plan.json
执行

跑下一个任务

让 WildArrange 执行 pending 任务，自动进入 verifier/scope/review/checkpoint。

node ./bin/helix.mjs run
node ./bin/helix.mjs status
总结

完成后生成恢复摘要

便于新会话、误关窗口、换 Agent 后继续。

node ./bin/helix.mjs summary
node ./bin/helix.mjs resume

五、怎么判断它有没有走对

检查项命令你要看什么
当前整体状态node ./bin/helix.mjs status是否有 pending / failed / review_blocked；下一步是什么。
恢复上下文node ./bin/helix.mjs resume新会话要读到计划、失败、下一步、最近结论。
路由是否正确node ./bin/helix.mjs route --text "..."route、category、primaryAgent、skills 是否符合直觉。
Skill 是否加载对node ./bin/helix.mjs skills match --text "..." --stage planmatched 里的 skill 和 reasons 是否合理。
注入点是否正确node ./bin/helix.mjs injection show --point before_review --agent BaiZe --task T001tools、markdown、skills 是否加载完整。
任务为什么没完成node ./bin/helix.mjs task get --task T001last_failure、verifyResult、scopeResult、reviewResult。

六、Debug 技巧

路由不准

先不要改代码。让 Agent 输出 route 和 skill matcher 证据。

node ./bin/helix.mjs route --text "你的需求"
node ./bin/helix.mjs skills match --text "你的需求" --stage plan

如果经常不准，再让 ArchivistRouter 生成关键词建议，审核后接受。

任务卡住

不要让 Agent 猜。直接看任务对象和失败报告。

node ./bin/helix.mjs task get --task T001
node ./bin/helix.mjs changes list
node ./bin/helix.mjs status

验收不过

验收不过通常是 verifier、scope、review 或 successCriteria 缺证据。不要清空 verify_commands。

node ./bin/helix.mjs node verify --task T001
node ./bin/helix.mjs node scope --task T001
node ./bin/helix.mjs node review --task T001

七、并行 Agent 怎么试

第一版并行 Agent 适合“计划已拆好，多个 worker 可分头做”的场景。不要用它处理还没澄清的大需求。

node ./bin/helix.mjs parallel run --max-agents 2 --task T001,T002 --agent ZhuRong --command "..."
node ./bin/helix.mjs parallel status --run <runId>
node ./bin/helix.mjs parallel admit --run <runId> --task T001
node ./bin/helix.mjs parallel close --run <runId> --task T001 --reason user_accepted

关键原则：子 Agent 的成果只是候选成果。只有 parallel admit 通过 writable_paths、verifier、scope、review、acceptance proof 和 checkpoint 后，才算进入主线。

八、最推荐的试用脚本

你可以开一个新 Codex 会话，在测试项目里按下面顺序试：

  1. 让 Codex 先执行 resume/status，确认 WildArrange 状态。
  2. 告诉它：“做一个网页版提醒事项 App，先计划，不要直接写代码。”
  3. 要求它产出 plan.json，每个任务必须有 writable_paths 和 verify_commands。
  4. 执行 plan --from plan.json 和 run。
  5. 如果失败，让它读取 task get 和失败报告，不允许删除 verifier。
  6. 完成后执行 summary，关闭会话，再开新会话执行 resume 看是否能接上。

给新会话的完整提示词

这是一个已安装 WildArrange 的项目。请先执行 resume/status，读取 .helix 的当前状态。
我要做一个网页版提醒事项 App。先不要写代码。
请先路由需求、匹配 skill、拆 plan.json。
每个任务必须包含 writable_paths、verify_commands、successCriteria。
计划确认后，再按 WildArrange 的 run/verify/scope/review/checkpoint 闭环执行。
如果失败，请读取 task get 和失败报告，不要削弱验收门。

九、常见误区

误区正确做法
让 worker 说“完成了”就算完成必须看 checkpoint 和 acceptance proof。
为了过关清空 verify_commands这是绕过验收门，WildArrange 应阻断。
计划外写文件后再补解释应该触发 scope / ChangeRequest，再由主编排审核。
新会话直接继续写代码先 resume/status，确认当前任务和失败状态。
大需求直接并行多个 Agent先 ideate / design / plan，拆清楚后再并行 worker。

十、一句话判断

如果你能做到：新会话先恢复、需求先计划、执行有验证、失败能定位、完成有 checkpoint、并行成果要 admission，那么 WildArrange 就已经进入可用状态。
