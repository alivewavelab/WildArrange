WildArrange 架构优化最终执行计划

版本：2026-08-30 · 状态：方案已锁定，尚未修改生产代码

最终执行版 四个里程碑 先修可信度 按职责归位 无数字评分门禁
一句人话：先修四个会让治理结果不可信的漏洞，再把项目初始化放回产品层，然后收拢重复钥匙和恢复工具，最后让 Windows 测试重新可信并接受独立复验。不是推倒重建，也不为了分数制造新架构。

一、执行对象、目标和底线

人话

WildArrange 的地基是健康的。本轮不是换房子，而是修门锁、统一钥匙、把急救箱放回正确房间，并确保 Windows 上的报警器真的能响。

专业边界

保留五区依赖、gateway 统一信封、delivery pipeline、全局任务锁、acceptance proof、checkpoint 和 ledger hash 链。只处理已有代码证据证明的缺陷、重复 owner 和职责错位。

锁定的执行树

  • 该工作树已经包含尚未提交的 project-init 变更；执行时必须保留，不得用 D 盘主树覆盖。
  • 开始前记录分支、HEAD 和 git status，把现有修改作为基线，不回滚、不重置。
  • 交付不是达到某个分数，而是：已证明根因消除、P0/P1 修复、必要回归通过、独立复验如实评分。

二、里程碑总览

M0 锁定现场记录当前工作树、已知失败和必须保留能力。
M1 修可信度Git argv、blockedBy、Hook deny、Dashboard token。
M2 初始化归位project-init 从 Infra 回到 Interface 产品用例。
M3 收编 owner完成顺序、bridge、recovery、路径守卫与死代码。
M4 恢复绿线Windows 回归、全量验收、包体检查和独立复验。

依赖顺序：M1 → M3 中的 patchAlreadyApplied；M2 使用当前工作树里的 project-init 基线；M4 必须在前三个里程碑完成后执行。

三、M0：锁定现场，不让两棵树串台

目标：所有后续修改都建立在同一个可追溯现场上
  1. 记录当前分支、HEAD、未提交文件和 project-init 已有改动。
  2. 记录四个缺陷的当前复现证据，以及 Windows 测试基线。
  3. 写下必须保留的产品能力：五区、完成门顺序、任务所有权、回滚恢复、gateway 的 command 与 command-safety。
  4. 把高级测试排除项写进执行说明：不新增 Fuzz、属性测试、大组合矩阵、soak、额外 E2E、Golden/快照、哈希门禁或新测试框架。

完成证据：一份基线记录，能回答“在哪棵树改、改前是什么状态、哪些能力不能丢”。

停止条件：如果当前 project-init 改动来源不明或执行树与计划路径不一致，先停止，不进入 M1。

四、M1：先修四个真实产品缺陷

M1.1 Git 改用 argv 参数数组

人话：不再把一整句 shell 黑话交给 Windows 猜。

  1. 在命令执行层提供明确的 file + args 入口，并保留超时、输出截断和 spawn 失败协议。
  2. 把 git-diff.mjs、git-worktree.mjs、agent-spawn.mjs 和 admission 中的 Git 调用迁移到统一入口。
  3. 删除对应的 POSIX shellEscape 与 Git shell 拼接；普通非 Git shell 命令不借机全仓重构。
  4. 路径比较统一采用规范化后的 / 语义，不把 Windows 分隔符写死在断言里。

验收：Windows 上 collectGitChangedPaths() 返回 available:true；changed-only 与 zone test 能选出真实文件和测试。

M1.2 blockedBy 不能被点名绕过

人话：前置工作没完成，点名后续任务也不能让它偷跑。

  1. 由 task-board.isTaskRunnable() 唯一判断任务是否可运行。
  2. 线性运行、显式 node、并行默认选择和 parallel run --task 全部复用。
  3. 拒绝必须发生在创建 run、claim 或启动 Agent 之前，并返回 blocker。

验收：显式选择被阻塞任务时明确失败，且没有 run、claim、Agent 副作用。

M1.3 Hook deny 与提示开关解耦

人话：关掉提示文字，不能顺手把门锁拆掉。

  1. pre_tool_use.enabled 只控制 additionalContext。
  2. preflight 已给出 deny 时，始终输出宿主 deny 协议。
  3. Kimi Hook 崩溃或宿主超时继续遵守既定 fail-open 合同；最终安全仍由 delivery pipeline 收口。

验收：提示关闭后，越界写入和高危命令仍被 Hook 拒绝；Kimi fail-open 文档与行为不被改写。

M1.4 Dashboard token 不进入页面

人话：门禁密码不能印在欢迎页里。

  1. 服务端渲染 HTML 不再携带 token。
  2. 非 loopback 页面和 API 使用明确认证；不把 token 放进可匿名获取的 GET 响应。
  3. 请求 body 超限后立即停止累计，返回明确的 413 类错误。

验收：未认证请求拿不到 token；页面源码、响应体均无 token；正确认证后的现有功能保持可用。

M1 关口

  • 四个缺陷各补一个能复现真实问题的必要回归测试。
  • 运行直接受影响测试和 dependency boundary。
  • 任何安全语义回退、CLI 行为丢失或现有 project-init 改动被覆盖，都不得进入 M2。

五、M2：把 project-init 放回产品层

目标：决定创建哪些治理文档的代码，由产品接口层负责
  1. 把 PROJECT_DOCUMENT_TEMPLATES 与 initProjectDocuments() 从 infra/runtime-bootstrap.mjs 迁到 interface/project-init.mjs。
  2. Infra 只保留目录、原子写入、ledger 等技术原语；bootstrap 只负责编排初始化顺序。
  3. 模板源文件使用 AGENTS.template.md，生成目标仍是项目根 AGENTS.md，避免模板被 Agent 当成现行规范。
  4. 保留既定行为：只创建缺失文件、不覆盖已有内容、architecture.md 按需、progress.md 仅作人类视图。
  5. 任务与 BUG 的机器真相源继续是 .helix/team/tasks.json，不建立第二份任务数据库。
  6. 同步根/分区 AGENTS.md、doc/project-architecture.md、模块映射、产品总图和 CLI 帮助。

验收：project-document-init.test.mjs 覆盖首次生成、已有文件跳过、可选 architecture 和重复执行幂等；npm run check:arch 通过。

停止条件：如果迁移需要覆盖用户已有项目文件，或让 Infra 反向依赖 Interface，立即停止并修正归属。

六、M3：把重复钥匙交给唯一负责人

步骤做什么为什么验收边界
M3.1
失败判定		 合并完全相同的 shouldFailTask / shouldFailAdmission。 同一个决定不能维护两份。 只共享纯判断；各流程的状态推进和错误返回继续留在原流程。
M3.2
完成提交顺序		 抽取窄范围的完成提交原语，唯一保证 ledger → wisdom → digest → canonical persist。 三处同步修改容易漂移。 不造万能 finalizeCompletion()；claim 清理、rollback 删除、workflow summary 和返回结构仍由各流程负责。
M3.3
Bridge 核心		 提取 Kimi/Cursor 共用的 stdin、项目发现、spawn、输出收集与协议骨架。 第三个宿主不应复制第三份约 90 行模板。 timeout/failure policy 显式参数化；Cursor 子进程 fail-closed 第二保险保留，Kimi 无自毁定时器明确标注为宿主 fail-open 合同。
M3.4
Admission recovery		 把 rollback plan 路径、持久化、读取、删除、生成、执行和 patchAlreadyApplied 搬入 admission-recovery.mjs。 事务状态机与恢复工具具有不同变化原因，且已有接盘 owner。 admit → claim → apply → gates → commit/rollback 主事务不拆；patchAlreadyApplied 必须使用 M1 的 argv Git 入口。
M3.5
路径守卫		 把 admission 与 adapters 的两份 assertInsideRoot 收编到 infra/path-match.mjs。 相同的越界判断应有一个 owner。 共用判断语义，调用方可保留自己的错误文案；normalizeProposedFiles* 留在 admission 输入合同。
M3.6
死代码		 删除已确认无调用方、无合同的局部函数，例如 uniqueStrings。 清掉真实垃圾，不碰挂牌能力。 command 与 command-safety gateway 注册项、测试、文档和底层实现全部保留。

Route matcher 默认决定

本轮默认不强行合并严格 route 匹配与模糊 Skill 推荐。它们服务不同业务目的；只有人类明确确认“同一 signal 必须同义”时，才共享 matcher。这样不阻塞 M3，也不擅自改变路由行为。

M3 验收：相关单元测试、admission 中断/回滚必要回归、adapter 测试、dependency boundary 和 npm run check:arch 通过；完成状态、恢复状态、Hook 宿主合同与 gateway 注册表不变。

七、M4：恢复 Windows 绿线并独立复验

目标：测试结果重新值得相信，而不是把红灯涂成绿灯
  1. 路径断言改为归一化语义比较，不硬编码 POSIX 路径。
  2. chmod 用例只在 Windows 不存在对应权限语义时 skip，并写清理由；不能用 skip 隐藏实现错误。
  3. 先运行各里程碑直接影响的测试，再运行标准 npm test。
  4. 运行 npm run check:arch，确认五区边界、模块映射和总图一致。
  5. 运行 npm 包体 dry run，确认发布内容、模板和用户文档正确。
  6. 对同一工作树执行独立 architecture-code-review，三项分别如实评分，不计算综合分，不回填目标数字。

完成证据：测试命令、通过/失败/skip 数、失败分类、包体清单、架构校验和独立复验三件套全部留档。

停止条件：若仍有 Windows 失败，必须区分产品缺陷、测试假设和环境限制；不得把未解决失败描述为全绿。

八、每个里程碑的交付节奏

阶段执行者必须交付进入下一阶段前

实现最小代码修改和与复杂度匹配的基础单元/必要回归不得顺手开展无关清理
自验真实命令、输出摘要、失败与限制直接影响测试通过

放行本里程碑结果和下一里程碑输入人类可随时要求停在当前里程碑

九、明确不做

  • 不设置 98/98/97 或其他数字评分门禁。
  • 不因为文件超过 700、1000 或 2000 行机械拆分；admission 只搬已有独立 recovery owner 的部分。
  • 不删除 gateway 的 command、command-safety，也不删除底层生产安全检查。
  • 不统一业务语义不同的 route matcher 与 Skill matcher。
  • 不新建万能工具箱、插件系统、第二套状态机或第二份任务真相源。
  • 不通过放宽 dependency boundary、跳过真实失败或删除测试来换取绿色结果。
  • 不扩张未经人类确认的高级测试和额外门禁。

十、最终完成定义

  1. 四个已证实缺陷均有最小回归证据并完成修复。
  2. project-init 归属 Interface，非覆盖、幂等、可选 architecture 等产品合同保持不变。
  3. 完成提交顺序、bridge 公共机制、admission recovery 和路径守卫各有唯一清晰 owner。
  4. gateway 的 command 与 command-safety 能力完整保留。
  5. Windows changed-path、zone test、dependency boundary 和默认测试提供可信信号。
  6. 架构、README、CLI 帮助、模块映射和产品总图与实现一致。
  7. 独立 Review 按同一工作树如实给出三项分数；若仍有扣分，只处理具有真实后果和清晰收益的问题。
