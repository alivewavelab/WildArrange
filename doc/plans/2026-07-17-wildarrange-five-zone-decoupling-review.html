WildArrange 五区解耦重构对齐方案

日期：2026-07-17 ｜ 输入：全量源码、测试、项目文档与 Cursor 重构稿

结论：接受“五区”作为目标架构，但不能只靠能力网关和目录搬迁。建议采用五区 + 严格单向依赖 + 共享交付流水线，先冻结行为与公共契约，再逐段迁移。

一、当前系统到底在做什么

WildArrange 不是普通任务执行器，而是一套本地 Agent 治理运行时。核心价值不是“让 worker 跑起来”，而是“worker 不能自证完成，所有成果必须经过独立验证并留下可恢复证据”。

输入

→
执行

→
交付门
verify → scope → review → proof
→
状态决策
retry / checkpoint / admission
→

线性运行时

plan → task → worker → verifier → retry/checkpoint，运行返回状态与任务持久状态有明确区别。

并行 Agent

提供 spawn、隔离目录、worktree、结果收集、patch admission、回滚与用户验收生命周期。

AI 编排

完成请求路由、Skill 匹配、上下文注入、Archivist 路由建议、可选 LLM review 与记忆摘要。

治理与恢复

通过 hash ledger、配置基线、运行态备份、doctor、hook 和 adapter 维持可审计、可恢复的执行秩序。

在允许本地端口监听的环境中，95/95 通过。测试覆盖面广，但尚未覆盖 CLI 入口语法。

当前有 27 个已跟踪文件修改、7 个未跟踪文件。重构前必须先明确并保护这批在途成果。

关键判断：“测试全绿”与“产品入口可运行”目前同时为真和假——模块测试全绿，但 CLI 语法损坏。Phase 0 必须先补 CLI smoke test，否则重构中的回归无法被可靠发现。

三、对原重构稿的判断

正确：五区能表达职责

Interface、Orchestration、AI、Capabilities、Infrastructure 是合理的目标地图，也适合逐步迁移。

不足：网关会隐藏依赖

通用 invokeCapability() 如果没有类型化契约、效应声明和静态注册表，会退化为 service locator：调用看似统一，真实耦合只是藏起来。

不足：原文件归区仍有反向依赖

review-gate、acceptance proof、memory digest、hook result 等含有领域或 AI 语义，不能简单归入底层。否则 Capability/Infra 会反向 import Orchestration/AI。

缺口：线性与并行交付门会继续漂移

“新增检查无需改编排层”只有在交付门本身数据驱动时才成立。应先把两条路径共用的交付判断抽成唯一流水线。

四、修正后的五区

区域只负责什么建议模块不能做什么
1. Interface把 CLI、HTTP、Codex/Cursor/Hook 宿主输入翻译为用例调用CLI、dashboard、adapters、host-hook adapter；旧 src/wildarrange-core.mjs 保留兼容出口不决定任务状态，不直接拼交付门
2. Orchestration用例流程和任务状态的唯一所有者linear runtime、delivery pipeline、parallel runtime、plan service、task board、workflow、change governance、hook service、failure policy不实现 shell、git、LLM、文件系统细节
3. AI Orchestration所有“需要语义判断或上下文组织”的能力routing policy、plan enrichment、archivist reasoning、injection、skill matcher、context composer、rules selection、semantic review、memory digest不写任务状态，不直接 checkpoint
4. Capabilities / Assurance可独立调用、可返回结构化证据的确定性能力contract、registry/gateway、verifier、scope guard、review gate、code intel、command safety、acceptance proof、checkpoint、hook result gate、agent runner、doctor audit不 import Orchestration；只接收快照并返回结果
5. Infrastructure / Platform无领域决策的 IO 原语与仓储path/config/lock、JSON/state repositories、ledger store、backup store、snapshot store、git client/worktree primitive、OpenAI-compatible HTTP client不认识 task 完成规则、路由策略或 review 结论

特别调整：memory digest 留在 AI；hook-result-gate 和 review-findings 属于 Assurance；git-worktree 只能依赖纯 git/process 原语，不能从 gate 模块借用命令执行器。

五、依赖方向是硬约束

Interface
→
Orchestration
→
AI / Capabilities
同级、互不直连
→
Infrastructure
  • Interface 只进入 Orchestration。
  • Orchestration 可以调用 AI、Capabilities、Infrastructure。
  • AI 和 Capabilities 只能依赖 Infrastructure，彼此不直接 import。
  • Infrastructure 不依赖任何上层。
  • 所有 task.status、attempt、checkpoint 状态变更只能发生在 Orchestration；下层返回 evidence 或 state patch，不能就地改 task。

六、能力网关：保留，但收紧

第一版采用静态注册表，不做动态 import。显式注册更容易审计、测试和打包，也符合当前“无外部依赖、行为可追踪”的产品原则。

调用信封

{
  version: 1,
  requestId,
  capability: "verify",
  context: { rootDir, planId, taskId, attempt },
  input: { taskSnapshot, evidence },
  policy: { timeoutMs, allowedEffects }
}

统一结果

{
  version: 1,
  requestId,
  capability,
  outcome: "pass" | "fail" | "inconclusive" | "skipped",
  blocking: true,
  evidence: [],
  effects: [],
  data: {},
  error: null | { code, message, retryable }
}

outcome 不使用 status，避免与现有“运行时下一步动作”和持久化 task.status 冲突。预期中的执行失败返回结果；程序错误直接抛出。注册描述符必须在执行前声明 process、workspace read/write、runtime write、git、network 等效应。

七、真正的核心抽象：共享交付流水线

线性 worker
或并行 patch
→
WorkerEvidence
统一成果信封
→
Delivery Pipeline
verify → scope → review → proof
→
Orchestration 决策
retry / checkpoint / admit / rollback

线性 runtime 和 parallel admission 都只能调用这一条流水线。并行模块额外负责隔离、apply、rollback、release，但不得复制完成门。这才能确保任何新增 gate 同时作用于两条交付路径。

八、实施顺序

P0

Phase 0：冻结可信基线

  1. 确认并保护当前 27+7 个在途改动。
  2. 先修复 CLI 重复导入。
  3. 补 node bin/wildarrange.mjs help 等 CLI smoke test。
  4. 记录公共导出、CLI 输出、.wildarrange 状态格式与 95 个测试基线。
P0

Phase 1：契约与边界守卫

  1. 新增 capability contract 与静态 registry。
  2. 先只包装 verify，验证统一结果模型。
  3. 新增 import boundary 自动测试，禁止反向依赖。
P0

Phase 2：拆 Assurance

  1. 从 wildarrange-gates 拆 command runner、verifier、scope、checkpoint。
  2. 保留旧模块作为 re-export shim。
  3. 每拆一块跑对应测试和全量测试。
P0

Phase 3：统一交付流水线

  1. 建立 WorkerEvidence 与 delivery pipeline。
  2. 先迁线性 runtime，再迁 parallel admission。
  3. 新增线性/并行 gate parity 测试。
P1

Phase 4：拆 Hook 与 AI

  1. 宿主协议留 Interface。
  2. 生命周期协调进 Orchestration。
  3. 上下文、路由、注入与语义判断进 AI。
  4. 清除 AI 对 task 状态的写操作。
P1

Phase 5：逐区搬目录

  1. 一次只搬一个区域。
  2. 内部改为目标文件直接 import。
  3. 旧路径保留临时兼容 shim。
  4. 同步更新 AGENTS 与架构文档。
P2

Phase 6：清理底座

  1. 修复 git-worktree 对 gate 命令执行器的倒置依赖。
  2. foundation 先保留 facade，只按已验证的职责热点拆分。
  3. 不做一次性“大爆炸”重写。
P2

Phase 7：收口

  1. 决定兼容 shim 的长期策略。
  2. 全量测试、CLI smoke、语法检查。
  3. npm pack --dry-run 验证发布包。

九、验收标准

  • 现有 95 个测试与新增 contract、boundary、CLI、linear/parallel parity 测试全部通过。
  • node --check 覆盖所有 src/*.mjs 与 bin/wildarrange.mjs；CLI help 和 sample workflow 可运行。
  • 自动测试证明依赖矩阵无违规 import。
  • 任务状态只由 Orchestration 写入；Capability/AI 只返回结构化结果。
  • 线性执行与并行 admission 共用一套 delivery pipeline。
  • src/wildarrange-core.mjs 公共导出不丢失；现有旧模块路径在迁移期仍可 import。
  • .wildarrange 状态格式、ledger 语义、result status/task status 含义不变。
  • npm pack --dry-run --cache /private/tmp/wildarrange-npm-cache 通过，发布包不意外扩容或漏文件。

十、明确不做

  • 不借重构改变业务行为、任务状态语义或 gate 强度。
  • 不迁移 .wildarrange 数据格式。
  • 不一次性重写 foundation。
  • 不让动态注册、插件系统或新外部依赖扩大本轮范围。
  • 不在未确认当前工作区在途改动归属前大规模移动文件。

十一、待对齐的四个决定

  1. 目标架构：采用修正版五区，并把上述依赖方向设为自动测试硬约束。
  2. 核心抽象：能力网关使用静态注册与统一信封；共享 delivery pipeline 优先级高于目录搬迁。
  3. 迁移方式：先修可信基线，再逐模块抽取；保留 wildarrange-core 和旧路径兼容 shim。
  4. 兼容边界：本轮不改公共 API、CLI 语义和 .wildarrange 状态格式。

建议默认全部接受。对齐后从 Phase 0 开始，不直接进入文件搬迁。
