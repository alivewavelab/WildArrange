HelixFlow · M1 需求文档

主题：工作保险箱（Work Vault）· 别丢东西 ｜ 2026-06-09 ｜ brainstorm 产出（WHAT，HOW 交 ce-plan）
READY · 6 个开放问题已决 → 可进 ce-plan

M1 造一套产品中立的"工作保险箱"：Claude / Codex / Cursor 里任何在途工作都持续落地到 git——关 Agent、忘合并、分支乱都不丢一行，任意在途状态一键恢复；产物落地后格式统一可读；轻仓重仓按画像自动切隔离方式。

1 · 背景与问题

团队画像：同时做应用（仓库轻）和 Unity 游戏（仓库重）；混用 Claude Code / Codex / Cursor；多人协作。

为什么自建而非直接用 compound-engineering（已装）：核心驱动是全流程治理——要一条能跨三个产品、且按团队治理关注点（产品/架构/设计/PM）组织的完整链；compound-engineering 是 Claude-only、偏 Rails 工程口味，且不覆盖跨产品共享。

6 个真实痛点归为 3 个 job + 1 条贯穿飞轮：

Job对应痛点本质里程碑
A 别丢东西① 分支混乱丢代码、恢复痛　② 成果物/进度丢失（没合并、关了 Agent 没同步）工作会蒸发M1（本文档）
B 别糊弄④ AI 偷懒不自测漏 review　⑤ 实现不全（只做了材质槽位、模型槽位没做）交付不可信 + 自进化测试飞轮M2 / M3
C 产品/设计脑子③ 设计方案格式乱只在聊天里　⑥ 没产品思维（地编刷图无 Gizmo 显示范围）没人把关价值与体验后续
⚠️ 团队强调"自进化（不同项目积累的 BUG/测试，越用越强、越来越去人工）"是 MUST，未丢——但它依附测试/review 闭环（Job B），故排在 M1 之后。M1 先把地基（别丢东西）打牢，证明内核值不值。

2 · M1 要造什么

一套"工作保险箱"，按仓库画像自适应隔离，外加产物持续落地与一键恢复。核心机制全在 git 层 + 薄 MCP/CLI（+ hooks 可用时），所以三产品行为一致。

轻仓（应用）

worktree-per-task 物理隔离 + 自动 checkpoint + merge 收口编排。多车道并行，谁也覆盖不了谁。

重仓（Unity 游戏）

单副本 + 分支-per-task + 激进快照（不多开副本，省磁盘/Library 重建）+ 场景/资产锁约定。

3 · 需求（REQ）

SHALL=必须　SHOULD=应当（可让步）。下游 ce-plan/测试据此校验覆盖。

R1 · 仓库画像自适应隔离

R1.1 系统 SHALL 自动识别仓库画像（轻 / 重），并据此选择隔离策略。
Given 一个新仓库　When 首次接入　Then 系统判定画像并记录，无需人工每次指定
R1.2 轻仓 SHALL 对每个任务用独立 git worktree+分支隔离。
R1.3 重仓 SHALL 用单工作副本 + 分支-per-task，不强制多开 worktree 副本。
R1.4 引擎画像 SHALL 可追加：不绑定 Unity。引擎专属规则（标志文件、不可合并文件模式、引擎特定提示词）做成可追加层，初始内置 Unity / UE，其余（网游/自研引擎…）按需注册，不改内核。
Given 团队新接一个 UE 项目　When 注册 UE 引擎画像（*.uproject / *.uasset/*.umap / 引擎提示）　Then 隔离/锁/提示自动适配，无需改 M1 内核

R2 · 持续 checkpoint（别丢进度）

R2.1 系统 SHALL 持续自动把在途工作快照到 git，不依赖人手动提交。
R2.2 关闭 Agent / 崩溃 / 切换产品时，已产生的工作 MUST 不丢失。
Given Agent 正在改代码且未提交　When 用户误关 Agent / 进程崩溃　Then 重开后能从最近快照无损继续
R2.3 重仓的激进快照 SHOULD 存独立 ref、不污染主分支历史，并防仓库膨胀（按需配 LFS）。

R3 · 成果物落地 + 标准化可读（M1 新增·杀痛点 3 一半）

R3.1 设计 / spec / 计划 / state 等产物 SHALL 持续落地 git 中立目录，不只活在 Agent 聊天里。
Given 设计方案是通过和 Agent 聊天产生的　When 阶段产出　Then 自动落成结构化文件入 git，关了聊天也在
R3.2 产物 SHALL 用统一模板/格式，多人产物合在一起仍可读（杀"格式混乱无可读性"）。
R3.3 设计/方案类产物 SHOULD 输出 HTML 可视化（沿用团队既有规范）。

R4 · 一键恢复

R4.1 系统 SHALL 提供「在途工作总览」：列出所有 in-flight 任务 / 分支 / 快照及其归属。
R4.2 任意在途状态 SHALL 一步恢复，目标 < 1 分钟（杀"恢复非常痛苦"）。

R5 · merge 收口

R5.1 系统 SHALL 编排 merge 收口，检测"完成但未合并"的工作并提示 / 兜底（杀"没把代码合进去"）。

R6 · Unity 重仓并行安全

R6.1 系统 SHALL 对不可合并的二进制/序列化文件提供硬锁：基于 git lfs lock（行业标准），远端 ref 做仲裁，在 commit/push 边界 + Agent 编辑工具层强制拒绝未持锁写入。不做 OS 级写保护（引擎编辑器自身也写盘，拦不住）。不可合并文件模式按引擎画像可追加（Unity: *.unity/*.prefab；UE: *.uasset/*.umap；其它引擎按需注册）。
Given A 已锁定某场景文件　When B 的 Agent 试图改并提交该文件　Then 在 commit/push 边界被拒并提示"A 持锁"，B 不会覆盖 A

R7 · 跨产品一致

R7.1 行为 SHALL 在 Claude / Codex / Cursor 一致，依托 git 层 + 薄 MCP/CLI。
R7.2 hooks 不可用的产品（Codex/Cursor 较弱）SHALL 用 git 侧 pre-commit / 后台 daemon 兜底持续快照。

4 · 成功标准（可验证）

  • 零丢失：两周内 N 个真实任务，零工作丢失（关 Agent / 忘合并 / 分支乱均不丢）
  • 一键恢复：任意在途状态 < 1 分钟一步恢复
  • 双画像：在一个轻仓应用 + 一个重仓 Unity 项目各跑通
  • 三产品一致：Claude / Codex / Cursor 行为一致
  • 成果物可读：设计/计划等产物落地后格式统一、多人合在一起可读（你新增的硬指标）

5 · 范围边界

M1 做
  • R1–R7 全部
  • 按画像自适应隔离
  • 持续 checkpoint + 一键恢复
  • 产物落地 + 标准化可读
  • merge 收口 + Unity 场景锁
  • 三产品最小适配
M1 不做（后续插入·不返工）
  • Job B：spec 覆盖校验、强制测试/review 门
  • 自进化飞轮（依附 B）
  • Job C：产品/设计治理、Gizmo 类 checklist
  • 完整 9 阶段编排
  • 跨产品命令编译器（只做 M1 所需最小适配）

6 · 开放问题决议（已拍板，ce-plan 据此展开）

Q1 安全网机制 ✓ 后台 daemon（混合）：产品中立的轻量 watcher（监听文件变更→去抖→自动快照到 shadow ref）做底，辞 Claude/Codex/Cursor 都兼、连崩溃都兜；有 hooks 的产品（Claude）再叠任务标记。daemon 是"真不丢"的唯一可靠保证。
Q2 画像识别 ✓：先认引擎画像（可追加注册表）——Unity（ProjectSettings/、*.unity）、UE（*.uproject、*.uasset）、网游/自研引擎按需追加；命中引擎标志即判重仓，否则按工作树体积（>1.5GB 或 LFS 占比高）判重仓，其余轻仓。引擎类型+画像写 .helix/config 一次定、可手动覆盖。
Q3 快照防膨胀 ✓：快照写独立命名空间 refs/helix/snapshots/*（不进分支、可 GC）；尊重 .gitignore；LFS 资产只快照指针不存 blob；保留=每任务留最近 N 个 + 超 X 天 prune；git 内容寻址天然去重。
Q4 场景锁 ✓ 硬锁：基于 git lfs lock（行业标准），远端 ref 仲裁，commit/push 边界 + Agent 编辑工具层强制拒绝未持锁写入。不做 OS 级写保护。见 R6.1。
Q5 恢复载体 ✓：CLI（helix vault / helix restore，给人）+ MCP tool（给 Agent 会话内列出/恢复，保证 agent-native 对等）。M1 不做本地面板。
Q6 产物模板 ✓：两套——设计模板（问题/用户流/交互状态/组件槽位（杀痛点5）/验收/截图引用，借 BMAD story + HTML 规范）+ 任务记录模板（DAG + context_package + 区段写权限）。M1 至少落设计模板；字段在 ce-plan 细化。

8 · 研究输入（oh-my 生态，源码级）

关键差异化结论：调研 oh-my-claudecode（36k★）、oh-my-openagent（61k★）、claude-forge、以及 opencode 的 3 个 worktree 插件后确认——现有项目都触及 worktree，但没有一个做到"never lose work"级别的 auto-checkpoint + merge 编排。R2（持续 checkpoint）+ R5（merge 收口）正是生态空白，是 M1 的真正机会，而非重复造轮子。

近乎现成的蓝图：opencode-worktree-session

github.com/felixAnhalt/opencode-worktree-session 的生命周期几乎就是 M1 想要的（但只支持 opencode）：

它的做法对应 M1 需求
session 开始 → 建隔离 worktree、禁止在 main 分支运行、cwd 切进 worktreeR1.2 隔离
session.idle/退出 → git add -A → 调 API 自动生成 commit message → push → 移除 worktreeR2.1/R2.2 持续 checkpoint + R5.1 收口
opencode 原生 ctx.worktree 一等公民 + "snapshot": true 文件级变更追踪R1/R2 机制验证

HelixFlow M1 = 把它做成产品中立（Claude/Codex/Cursor）+ 画像自适应（轻/重仓）+ 补上它缺的 merge 编排与一键恢复。

开放问题得到的部分解答

  • Q1 hooks 兜底 → 证实路线：opencode 有 54+ 生命周期 hook（session.created/idle 等）很适合；Claude Code 有 hooks；Codex/Cursor 弱 → 用 git add -A + session.idle 类事件或 git 侧 pre-commit/daemon 兜底，三产品可统一到"会话空闲即快照"。
  • Q5 恢复视图 → 可借 oh-my-claudecode 的 agent-replay-*.jsonl：每任务记 {session_id, branch, worktree_path, start_commit}，恢复=按记录 checkout，天然支撑「在途总览+一键恢复」。
  • R2.2 防丢 → 借 Hashline Edit 思路（内容哈希锚定编辑，基准成功率 6.7%→68.3%）做写入校验层，防"行号偏移改坏文件"这类隐性丢失。

顺带验证的可插拔/工程模式（供后续里程碑）

  • 双作用域优先链（项目 .helix/ > 用户 ~/.helix/）+ HELIX_STATE_DIR 重定向 —— 状态目录设计直接抄
  • helix.local.json 本地覆盖（merge 到 helix.json 之上、gitignore）—— 解决"团队规范 vs 个人/IDE 定制"冲突
  • symlink 安装 + git pull 升级 —— 多产品零成本同步（claude-forge 模式）
  • Markdown-as-source → make generate 每产品原生格式（wshobson/agents 模式）—— 跨产品分发的工程实现
  • 关键词即接口（isolate/checkpoint/merge 嵌入任意 prompt 触发）—— 零命令记忆负担，三产品通吃
  • disabled_hooks 精准可关 + 模型能力类别路由（deep/quick/visual 抽象，不硬编码模型）—— 可插拔与跨产品解耦
