内置执行者模板方案（已执行）

2026-10-03 · 目标：用户不再自己写 Worker 握手、审查者、Worker 适配脚本 · 依据：2026-10-02 实机验证的 agent.mjs、本机 claude 2.1.287 / kimi 0.39.1 / cursor-agent 的命令行实测
执行结果（2026-10-03，真实 CLI）：全新项目 setup 后 doctor 报出握手与审查者未配置，并按本机 CLI 推荐 claude 握手 + kimi 审查（含 900 秒超时）；原样采用后：T001 由 claude Worker 实现、kimi 审查，83 秒完成并推送；T002 由 kimi Worker 实现、kimi（只读 plan 档案）审查，104 秒完成并推送。
实机暴露并修复：① kimi 不允许 -p 与 --yolo/--auto 同用，且 -p 本身自动批准全部工具——Worker 改用纯 -p，握手与审查改用内置只读 plan 档案（实测无法写文件）；② 线性 run 的 Worker 超时原为不可配置的 120 秒，kimi Worker 被杀——新增 executionReadiness.workerTimeoutMs，默认 30 分钟。
Cursor（登录后补测）：T001 由 cursor 握手、cursor Worker 实现、cursor 审查，100 秒完成并推送；doctor 给出"审查者与 Worker 同 CLI"告警。实测暴露：cursor 非交互不带 --trust 会停在工作区信任提示并退出——握手与审查加 --trust（只信任目录、不放开工具审批）；--mode ask 实测拒绝写文件；--sandbox enabled 实测拦不住 worktree 外的 Shell 写入，故未采用；一次 --force 运行回复 DONE 却未生成文件（复现时正常），由 verifier 兜底判定。
未单独实跑：claude 作为审查者（与 kimi、cursor 共用同一读包与 JSON 提取路径）。
现状问题：开工检查必须配 executionReadiness.workerProbe 与 review.responsibility.command，每张任务还要真实的 worker_command。仓库不带任何适配脚本，用户得自己写一个"读任务包 → 调模型 CLI → 回 JSON"的程序；而且刚 setup 完 doctor 不提示没配，第一次 run 才以 readiness_blocked 暴露。
方案：产品自带一条命令 wildarrange executor <probe|review|work> --cli <claude|kimi|cursor>，把实机验证过的适配逻辑做成正式能力；配置里直接写这条命令。doctor 在初始化阶段就提示缺失项，并给出可直接复制的推荐配置。

1. 验收标准

#标准证据
1新项目只改两行配置（workerProbe、review.responsibility.command）即可通过开工检查，不写任何脚本实机：真实 CLI 握手通过
2用内置 Worker 跑完一张真实任务：Worker 写代码 → verifier → 内置审查者 PASS → 完成并推送 task branch实机：run 返回 completed
3旧回执、超时、CLI 未安装、模型输出夹杂文字时，结果都是明确失败或正确解析，绝不误判为通过自动化测试（假 CLI）+ 实机超时
4刚 setup 完运行 doctor，会提示握手与审查命令未配置，并给出推荐命令doctor 输出
5审查者与 Worker 用同一个 CLI 时，doctor 给出"独立性不足"警告（不阻断）doctor 输出

2. 设计

三个角色

  • probe：读 WILDARRANGE_READINESS_PACKET，回 {ready, challenge, loadedSkills}
  • review：读 WILDARRANGE_REVIEW_PACKET（职责审计与项目审查步骤共用），按包内 instruction 回 JSON
  • work：读 WILDARRANGE_EXECUTION_CONTEXT 的任务、Skill 与可写路径，在任务 worktree 内改文件
探测与审查一律只读；包内容不进命令行参数（审查包可达数百 KB），claude/cursor 走 stdin，kimi 读包文件路径。

各 CLI 的调用方式（已实测）

  • claude：claude -p --output-format json；只读角色禁用 Bash/Edit/Write；Worker 用 acceptEdits，只开 Read/Write/Edit/Glob/Grep，不开 Shell
  • kimi：kimi -p … --add-dir <包目录>；输出带 • 前缀，需提取 JSON；实测握手约 23 秒，深度审查可超过 10 分钟
  • cursor：cursor-agent -p --mode ask --output-format json（只读）

稳健性

  • 从模型输出中提取第一个完整 JSON 对象，提取失败按失败处理
  • CLI 未安装、退出码非 0、超时：如实报错，交给现有门禁判定失败
  • 模型的 model 可选参数透传（--model）
  • 归属 src/capabilities/（原子能力），CLI 入口在 bin

3. 决定（2026-10-03 用户确认）

Worker：claude / kimi / cursor 都支持（实测：kimi 的 -p 本身自动批准全部工具且不允许与 --yolo 同用，因此 Worker 直接用 -p，握手与审查改用内置只读 plan 档案；cursor 以 --force 非交互改文件；成果仍过全部门禁）；审查者与 Worker 同 CLI：只警告不阻断；codex 本次不做。另：执行者启动的模型子会话带 WILDARRANGE_EXECUTOR_SESSION=1，宿主 Hook bridge 见到即放行，避免治理注入与续跑嵌套干扰执行者（claude 的 --bare 会跳过 OAuth 登录，不可用）。

以下为确认前的选项与推荐，留作记录。

问题推荐理由
Worker（改代码的那个）支持哪些 CLI只支持 claude（无 Shell 权限）kimi 非交互改文件必须开 --yolo（自动批准一切，含 Shell），cursor-agent 的打印模式默认带写入和 Shell 权限；两者都没有"只能改文件"的开关。Worker 在隔离 worktree 里跑、结果还要过全部门禁，但无约束的 Shell 仍可能碰到 worktree 之外的东西。探测与审查三种都支持。
codex本次不做本机未安装，无法按规范实机验证；等装好后按同一接口补上
审查者与 Worker 同一个 CLI只警告，不阻断同一模型自审独立性弱，但很多用户只有一个 CLI；审查进程只拿任务包、看不到 Worker 过程，仍有隔离

4. 范围外

  • Agent 绑定 Skill 调度外部 CLI 的"软路线"保持不变；本方案只服务硬门禁命令。
  • 不改任何门禁判定逻辑，只提供执行者命令和 doctor 提示。
  • 预计不需要改规范文档；若实现中发现需要，先回来确认。
