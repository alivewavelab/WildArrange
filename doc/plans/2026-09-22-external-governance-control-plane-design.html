外置治理控制面详细设计

决策：WildArrange 采用“客户代码仓库 + 独立治理仓库 + 本机运行状态”三仓面。WildArrange 生成的规则、任务、报告、状态和宿主适配文件默认不进入客户代码仓库；每次验收绑定项目 commit 与治理 commit。

本次明确不改：任何 AGENTS.md、AGENTS schema、允许路径清单或既有质量门顺序。

1. 目标与不可牺牲约束

  1. 客户仓库零污染：接管前后客户仓库不新增 WildArrange 文件，git status --porcelain 保持一致。
  2. 治理独立演进：质量门、测试目录、风险映射、验收规则和治理决定在独立治理仓库中版本化、评审和回滚。
  3. 产品测试不复制：单元、集成和端到端测试仍与产品代码同仓、同分支、同提交；治理仓库只登记测试路径、命令、风险、合格线和证据。
  4. Agent 不得自降门槛：功能 Agent 无权修改生效治理政策。新增、削弱或删除永久控制项必须成为独立治理任务并获人类批准。
  5. 不新增第二真源：task ledger 与现有交付链语义不变；外置只改变所有权和存储位置。

3. 路径、身份与安全

WorkspaceContext {
  projectRoot,
  governanceRoot,
  runtimeRoot,
  projectId,
  governanceId,
  projectWorkspaceId,
  mode: "external" | "legacy"
}

3.1 本机运行目录

Windows: %LOCALAPPDATA%\WildArrange\projects\<projectId>\
macOS:   ~/Library/Application Support/WildArrange/projects/<projectId>/
Linux:   $XDG_STATE_HOME/wildarrange/projects/<projectId>/

runtimeRoot 可由显式参数或 WILDARRANGE_STATE_HOME 覆盖。治理仓库必须显式连接，不向客户仓库写指针文件。

3.2 身份规则

  • Git 项目以 git rev-parse --git-common-dir 的真实路径生成本机 projectId；同一仓库多个 linked worktree 共用权威任务状态。
  • 独立 clone 默认拥有不同本机身份，避免跨 clone 共用锁。
  • 跨设备通过治理仓库合同与双 SHA 对账，不依赖本机绝对路径。
  • 非 Git 项目以项目真实路径生成本机身份，不自动 git init。

3.3 路径安全

  • 三根都执行绝对路径、realpath 和符号链接边界校验。
  • 外置模式拒绝 governanceRoot 或 runtimeRoot 位于 projectRoot 内。
  • 治理规则只能从已连接仓库的登记路径加载，prompt 不能指定任意磁盘路径。

4. 治理仓库合同

{

  "evidenceRequired": "exit_code_0",
  "owner": "orders",
  "executionCost": "medium",
  "retirementCondition": "订单模块删除或被新 suite 完整替代"
}

5. Agent 权限与双仓库任务

任务可写仓库内容批准
功能 / BUG / 重构仅项目仓库产品代码、产品测试、必要产品文档现有项目交付链
治理提案默认只读候选差异、风险和理由不产生生效治理 commit
治理变更仅治理仓库政策、门禁、验证目录、退出条件独立治理任务 + 人类批准
集成验收不直接修改任一仓库绑定项目 delivery SHA 与治理 SHA双 SHA 固定后运行

一个可写任务不得同时写项目仓库和治理仓库。

两边必须共同变化时，拆成项目任务、治理任务和只做联合验收的 integration task；分别拥有 branch/worktree 和证据。

6. 治理演进闭环

观察项目 → 发现缺口 → 候选治理提案 → 人类批准 → 治理 commit → 后续任务加载 → 统计效果 → 保留、修订或退休

  • 扫描、失败和 Review finding 只能产生候选风险，不能自动新增永久门禁。
  • 永久控制项必须包含风险、证据、范围、机制、负责人、执行成本和退休条件。
  • 功能 Agent 无治理仓库写权限，不能通过削弱规则完成自证。
  • 治理规则必须通过治理仓库自己的 review 和人类 merge；项目 checkpoint 不能代替。

7. CLI、兼容与宿主激活

# 目标接口；已在本设计分支实现
wildarrange project attach --project-root D:\Projects\game --governance-root D:\Governance\game-governance
wildarrange project show
wildarrange init
wildarrange state migrate --to external --dry-run
wildarrange doctor
  • 新增 --project-root、--governance-root、--runtime-root。
  • 旧 --control-root 在兼容期仅表示 legacy 单根模式；与新参数并用时拒绝。
  • 发现旧 .wildarrange 时继续 legacy 模式并提示迁移，不能静默创建第二 ledger。
  • Adapter 必须由用户显式安装到用户级或外部运行目录，不能静默改用户级配置。
  • Hook 根据工作目录识别连接项目，再从治理仓库和运行目录加载规则与状态。
  • 若宿主只能加载项目内 Hook，doctor 必须报告零污染模式未激活，不能生成 shim 后冒充完成。

8. 状态、配置与规则优先级

8.1 单一状态真源

显式 runtimeRoot
  → 外部项目 registry 映射
  → legacy projectRoot/.wildarrange（仅兼容）

任务状态仍只有一个权威 task ledger；计划、Markdown 和报告仍为派生物。

8.2 规则只叠加、不覆盖

WildArrange 内置不可削弱底线
  + governanceRoot/policy
  + projectRoot 中客户自己已有规则（只读输入）

冲突时停止并报告，不使用“后读覆盖前读”。WildArrange 不生成或改写客户项目中的 AGENTS.md。

8.3 配置职责

  • 团队共享治理配置进入治理仓库。
  • 设备路径、令牌、缓存和锁进入本机运行目录。
  • 客户项目已有产品配置保持原 owner，WildArrange 不搬运。

9. 迁移与回滚

  1. 冻结项目根、HEAD、旧状态和锁。
  2. 验证 task ledger、ledger hash 链和关键恢复文件。
  3. 复制到外置临时目录并生成关键文件 digest。
  4. 验证复制后的账本、proof、checkpoint、配置和 Prompt Pack。
  5. 原子写外部 registry，再以新根执行 doctor。
  6. 迁移成功后保留外置恢复包；旧目录仅在用户明确确认后删除。

任何失败都保持旧目录为唯一真源；不得出现两个可写 ledger。

11. 实施切片

  1. 基础路径：三根上下文、外部 registry、路径安全、legacy 检测；证明 init 不写客户仓库。
  2. 治理连接：治理合同、attach/show、外部政策安全加载与双 SHA 展示。
  3. 状态迁移：旧 .wildarrange 的验证、复制、切换和回滚；不自动删除。
  4. 宿主激活：外置 Adapter 生成与真实生命周期证明；不支持的宿主保持未激活。
  5. 双仓交付：任务单仓目标、治理 branch/worktree、integration 双 SHA 验收。
  6. 文档发布：README、架构文档、总图、包体和迁移指南。

每个切片都要有独立自动测试，不能用后一阶段的计划替代前一阶段验收。

12. 验收标准

类别必须证明
零污染attach/init 前后客户目录树和 Git 状态不新增 WildArrange 文件
身份同一 common-dir 的 worktree 共用 projectId；独立 clone 不共享锁
路径安全拒绝根目录嵌套、符号链接逃逸和未登记绝对路径
单真源legacy/external 不双写；迁移失败继续读取旧权威状态
规则外部政策可注入；客户规则只读；冲突停止；截断显式报告
Git项目 commit 不含治理文件；治理 commit 不含产品文件；均不移动 main
权限功能 Agent 无法修改治理仓库；治理变化要求独立批准
绑定验收同时保存并复核 project SHA 与 governance SHA
恢复复制中断、digest 不符、registry 切换失败都可恢复
宿主Codex/Cursor/Kimi 各自产生真实生命周期回执；生成文件不等于激活

交付门：相关测试 → npm test → npm run check:arch → npm pack --dry-run → git diff --check。

13. 排除项与完成定义

  • 不使用嵌套 Git、submodule、隐藏 orphan branch 或项目内 ignored 目录冒充独立治理。
  • 不复制产品测试源码，不建立第二任务状态表、第二完成链或第二审批事实。
  • 不自动创建、推送或合并客户 GitHub 仓库；治理远端创建和授权仍由人类完成。
  • 不因路径分离修改 AGENTS 规范、依赖白名单或质量门强度。

只有真实客户项目在零 WildArrange 生成文件的情况下完成连接、规则注入、任务执行、完整交付门和双 SHA 验收，并可从迁移失败恢复，才可称为完成。

静态映射、单元测试、Adapter 文件生成或单次 Hook 事件都不能单独证明完成。
