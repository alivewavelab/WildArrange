GameCopilot 解耦重构（维护者视角）

核心原则：改交互去前端、改流程去编排、改 AI 策略去 AI 编排、改具体功能去原子能力、改基础设施去服务——五个区，互不串门。

一、你的目标：五区模型

你想要的其实是这样一个心智模型——每个区只管自己那件事，区和区之间只靠"信封"（契约）对话：

① 前端
只管交互/展示
② 业务编排
工作流/先后/分支
③ AI 编排
理解意图/出计划
④ 原子能力
做一件具体的事
⑤ 服务/资源
被调度的基础设施
①

前端

画面、按钮、弹窗、列表。只接收"显示什么"的指令，发出"用户点了什么"的事件。

②

业务编排

决定"先做A、再做B、如果失败就C"。不知道 AI 怎么想的，不知道能力怎么实现。只管流程顺序和分支。

③

AI 编排

拿到目标和上下文，产出计划/建议。不拥有状态、不直接调能力——它只写"建议书"交给业务编排执行。

④

原子能力

一个能力只做一件事（截图识别 / 改配置 / 模拟按键）。有标准入参和出参。被业务编排调度。

⑤

服务/资源

数据库、文件存储、游戏进程、外部 API。被原子能力借用，但自己不决定何时做什么。

二、对照原图：哪些做对了、哪些搅在一起了

五区原图对应✅ 做对了⚠️ 搅在一起了
① 前端 Frontend / In-Game Panel / AI Conversation Panel 和后面分得比较开 AI Conversation Panel 是"前端"还是"AI编排的入口"？如果它直接调 AI 引擎而不经过业务编排，就破了层
② 业务编排 Business Workflow Engine + Execution Controller + Business Control Slots 有明确的编排层 Execution Controller 把路由/超时/重试/调度/状态推进全塞进一个组件——它应该只做"按业务编排指令去调能力"，其余是业务编排自己的事
③ AI 编排 AI Workflow Engine 概念上独立了 它和 Business Workflow Engine 共享 workflow 状态 → 谁是"真相源"说不清 → 改流程时不知道去哪改
④ 原子能力 Layer 5（Game/MOD/Vision/Input/Runtime/Localization…） 用 Capability Gateway 统一入口；契约意识很好 有 3 个能力（Game Capability、Input Automation、Runtime Modification）都 hook 同一个游戏进程，互不知道对方存在 → 隐式耦合
⑤ 服务/资源 Layer 6 + 7（本地存储/游戏进程/Tool & MCP Host） 本地与云端分离了 Trace/Ledger/Checkpoint 三套机制，如果格式不统一就是三份账本 → 排查时不知道看哪个

三、对上一版分析的修正

上一版哪里对：四条切缝 ABCD 的位置是对的；副作用分级（read / write-undoable / irreversible）这个设计很关键；六个耦合气味也都真实存在。

上一版哪里"过于程序员视角"了

  • 重构优先级应该以"维护者改什么最频繁"来排，不是以技术复杂度排。你最常改的是"工作流"和"具体功能"，所以 P0 应该是让"改工作流"和"改功能"这两件事各自独立、互不影响，而不是先冻结契约。
  • 统一事件 schema 这种事对你来说不紧急——三份账本格式不统一虽然不优雅，但不阻碍你日常维护。P2 即可。
  • "AI 引擎无状态化"从你的角度翻译成：AI 只产出"建议书"，不碰真正的进度表。这条原则对，但实操上只要保证"进度表在业务编排那里且只有一份"就够了，不需要用"纯函数"这类概念。

四、修正后的重构优先级（维护者视角）

改什么最频繁 → 就先把那个区隔干净

最先做

让"改工作流"只动一个地方

把 workflow 状态唯一归属到业务编排层。AI 引擎只提交"建议"，不持有任何进度。Execution Controller 只是个"跑腿的"——业务编排说调谁就调谁。

做完后的体感：改流程顺序/分支/重试逻辑 → 只去业务编排区改。不会牵连 AI 策略也不会牵连具体功能。

最先做

让"改功能"只动一个能力

① 冻结能力契约格式（入参/出参/副作用类型）；② 引入"游戏会话管理器"让多个能力共享同一个游戏进程连接而不互踩。

做完后的体感：改 OCR 识别逻辑 → 只动 Game Vision 能力。不会影响 Input Automation，也不会影响工作流。

第二步

让 AI 策略可换、可关

AI 编排是个"顾问"角色：有它时出智能计划，没它时业务编排照样走一个兜底的确定性流程。这样你测试/调试时可以先关掉 AI 看业务逻辑对不对。

做完后的体感：换 AI 模型 / 改 prompt 策略 → 只动 AI 编排区。业务流程不受影响。

第三步

前端只接收"显示指令"

前端不直接调 AI、不直接调能力。它只做两件事：① 收到"显示/刷新"指令就画；② 用户操作了就发一个"用户事件"给业务编排。

做完后的体感：改 UI 样式/交互 → 只动前端。完全不碰后面的逻辑。

最后做

服务/资源统一接口

存储、游戏进程、外部 API 各自一个标准接口。上面的能力只通过接口借用，不直接碰底层细节。

做完后的体感：换存储方案 / 适配新游戏引擎 → 只动对应的服务适配层。

随时做

三份账本合一

把 Trace / Ledger / Checkpoint 的格式统一成一种。日常不影响维护，但排错时一个地方查到底。

六、关键设计原则（非技术语言）

区和区之间只传"信封"

区与区之间不共享内部状态。业务编排不关心 AI 内部怎么推理，只看它交回来的"建议信封"。原子能力不关心谁在调它，只看收到的"任务信封"。

好处：改一个区的内部实现，只要信封格式没变，其他区完全不用动。

进度只有一份，在业务编排手里

整个系统"现在到哪一步了"只有业务编排知道。AI 编排不维护进度、前端不维护进度、能力不维护进度。

好处：排查"怎么卡住了"只需看一个地方。

AI 是顾问不是老板

AI 编排产出"建议"，业务编排决定"采不采纳"。没有 AI 或 AI 挂了，业务编排仍能走一条确定性兜底流程。

好处：调试时可以先关掉 AI，验证纯业务逻辑对不对。

能力标明"我有没有副作用"

每个能力注册时自己声明：我只看（read）、我改了但能撤（undoable）、我做了就收不回（irreversible）。编排根据这个决定要不要先备份或问用户确认。

好处：新加能力时只需填一个标签，编排自动知道怎么保护。

七、和原图的主要分歧

原图做法建议调整为什么
Execution Controller 承担路由 + 超时 + 重试 + 状态推进状态推进归还给业务编排；Controller 只负责"按指令去调能力、等结果回来"否则改流程时不知道是改编排还是改 Controller
AI Workflow Engine 和 Business Workflow Engine 都碰 workflow 状态AI 引擎不碰状态，只交"建议信封"否则进度有两个来源，排查时看不清
Business Control Slots 既注入上下文又能回写编排Slots 只能注入只读上下文；想改编排必须走"建议信封"否则扩展点变成后门，谁加了什么改动看不见
3 个能力各自 hook 游戏进程加一个 Game Session Manager，能力向它借连接否则改一个能力的 hook 方式可能影响另一个
计费/权益写在 Controller 或 Gateway 里外提成业务编排的策略插槽否则改计费逻辑要碰调度主干，风险大
一句话总结：让你的维护心智模型就是代码的物理结构——目录分五区、信封定格式、进度一份源、AI 只建议不做主。改任何东西前问自己"我要改的属于哪个区"，答案唯一就对了，答案模糊就是还没解耦干净。
