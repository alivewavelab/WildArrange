1. 一句话产品定义

用户运行“接管老项目”初始化后，WildArrange 全仓寻找现有门禁、测试、Runner 和 Hook，列出准备新增登记、修改接入、合并、归档或删除的每一项；把用途、理由、完成后的变化和最大风险讲清楚；用户判对后才执行，最后生成三份正式管理文件。

生活化解释：像请专业团队盘点旧工厂。先把每台设备为什么留、为什么搬、搬完怎样、最坏会怎样写成清单；老板签字后才施工，最后交付资产总账。

3. 每张变更卡必须讲清楚什么

这是什么

名称、类型、精确路径、Owner、真实执行入口。

先认清是哪件东西。

有什么作用

它保护哪个行为；失败时阻止什么问题。

说明它为什么存在。

谁在使用

直接消费者、Runner、CI、Hook 或生产调用点；证据和可信度。

确认还有没有人用。

为什么这样处理

为什么新增登记、修改、合并、归档或删除；为什么没有更短替代。

说清施工理由。

完成后会怎样

保留什么、移动什么、哪个入口成为真源、用户以后从哪里管理。

预先展示施工后的样子。

最大后果

若判断错误，最严重会失去哪层保护、哪条测试不再运行、哪个副作用可能失去拦截。

先讲最坏情况，不藏风险。

卡片还必须附带：精确变更路径、候选 diff、验证命令、未验证边界、恢复方式、扫描时间、HEAD/WIP 指纹。缺少“消费者、完成后状态、最大后果”任一项时，系统不得给出删除或合并按钮。

4. 六种处理动作

动作什么时候使用完成后的结果用户批准要求
新增登记仓库已有有效资产，但 WildArrange 尚未管理进入正确的 WildArrange 管理入口与 Registry普通项可批量批准
修改接入Owner、命令、路径或阻断位置已经失效或不合理真实入口与管理记录重新一致展示前后 diff
合并多个资产保护同一故障，执行和维护重复保留一个真实 Owner/入口，消费者逐个迁移，退役项默认归档逐项批准，不能一键全选
归档当前无消费者，但仍值得保留历史和恢复能力离开活跃执行面，保留墓碑和恢复材料逐项批准
删除确认无消费者、无独立保护价值，且归档也没有收益从仓库移除，但本次恢复包仍可还原精确文件单独确认；默认先推荐归档
暂缓动态加载、外部调用或证据不足保持原样，并进入最终 Inventory 的“待确认”区用户确认暂缓即可，不阻塞其他正确项

5. WildArrange 怎么判断“谁在用”

系统只采用入口级静态证据，不声称理解所有业务语义。

证据系统做法能否单独支持删除/合并
import / require / 已有依赖图建立模块到资产的直接调用边可以作为直接消费者证据
package scripts 调用链解析真实 script 名和直接调用的脚本/命令可以
测试 Runner 的 glob/exclude计算 Runner 与测试文件的真实交集可以
CI YAML / Hook 配置读取登记的精确命令、事件和目标路径可以
生产代码副作用前调用记录 Runtime Gate 的触发点、权威状态和拒绝分支可以登记；不能声称扫描穷尽
精确路径字符串标记为间接消费者，再核对上下文只支持“可能在用”，不能单独支持删除
文档、注释、普通关键词只作为调查线索不能
动态拼接、插件发现、外部系统标记未知消费者并说明缺失证据不能；动作降级为暂缓

失败规则：找不到消费者不等于没有消费者。只有发现面完整、直接消费者为零、Owner/入口事实可核对时，才允许提出归档；永久删除还必须证明归档没有收益。

6. “新增登记”具体接到哪里

发现的资产WildArrange 建议落点不会做什么
行为测试 Suite生成计划模板中的 verify_commands 候选；只有真实 Runner 执行到的范围才纳入不逐条登记 test case
静态工程检查优先映射到现有 standards_commands；现有 qualityGates 有精确同类字段时才建议该字段不为了接入新增通用 Gate 类型
独立复核入口映射到 review_commands不和 verifier 重复执行同一命令
Runtime Gate保留在原生产副作用前；在 Registry 登记实现位置、触发点和拒绝行为不搬进 verify_commands
宿主 Hook映射到对应 adapter/Hook 建议，说明 fail-open/fail-closed 和最终完成边界不把 Hook 当任务完成证明
现有字段无法承接卡片显示“需要产品扩展”，只允许暂缓不伪造 config 字段或写空入口

M1 扫描时就必须输出上述目标位置和候选 diff；用户批准的是一份真正可执行的接管计划，不是一句“以后再映射”。

近似映射不能静默通过：如果一个旧脚本同时承担 standards 与 review，或现有字段只能覆盖它的一部分语义，卡片必须同时展示“保留了什么、丢失了什么、为什么不能精确映射”。用户只能选择拆分建议或暂缓，系统不得为了填满字段擅自归入某一类。

7. 批准页面怎么用

默认页面

  1. 先显示“建议新增、修改、合并、归档、删除、暂缓”数量。
  2. 优先展示需要用户判断的卡片。
  3. 每张卡只有三个动作：批准、拒绝、暂缓。
  4. 展开后查看调用证据、diff、最大后果和恢复方式。

用户是在判方案对不对，不是在设计算法。

不能批量吞掉的内容

  • 删除。
  • 合并。
  • 修改 AGENTS、CI、build、Hook 或 Runtime。
  • 改变测试策略或阻断阶段。
  • 执行来源不明或可能有外部副作用的验证命令。

普通登记可以一批签字，拆线路必须单独确认。

暂缓不会卡死接管：最终三份文件可以生成，但每个暂缓项必须带 Owner、原因、缺失证据和后续处理提示，并在 Inventory 顶部持续显示。

M2 只实现一种批准交互：本地 Dashboard 是唯一可写的逐卡批准界面，复用现有 loopback/token 防护；CLI 只负责 adoption start/status/resume 和输出 Dashboard 地址，不再实现第二套交互式批准。Dashboard 之外的批准 API 不对外开放。

8. 执行获批变更时如何保护老项目

执行前

确认没有活动 task/admission → 短锁登记“接管维护中” → 使用独立 adoption lock → 复核 HEAD/WIP/消费者 → 建立通用恢复事务

先封施工现场并拍照。

→

执行中

一次只处理一张卡 → 只改批准路径 → 保存 preimage/postimage → 不扩大范围

一项一项施工，不拆全屋。

→

执行后

在隔离环境运行获批验证 → 通过才提交本卡 → 失败自动回滚 → 回滚失败停止并显示恢复入口

每项验收后再做下一项。

  • 不长时间持现有 15 秒全局任务锁；日常 run/admission 看到“接管维护中”应立即提示，而不是等待超时。
  • M2-0 前置任务：先提炼产品中立 recovery transaction。只允许泛化接口与内部公共原语，不改变现有 task archive 的返回、状态、恢复路径和测试，也不得触碰 admission 的 owner/base/main fence、已 push 成果不得回滚、回滚失败保持 ownership 等不变量。行为等价测试通过后，M2-1 adoption Apply 才能开工。
  • command-safety 只拦毁机级命令，不证明测试脚本无副作用。验证优先在隔离 worktree、禁网或受限环境运行；无法隔离时必须单独确认“运行此精确命令”。
  • 删除默认降级为可恢复归档；用户明确选择删除后也必须保留本次恢复包。

本机中断恢复：finalized 前的 adoption 会话不跨设备，但必须在 .wildarrange/ 内自包含保存 scan、卡片、逐卡批准、preimage/postimage、当前步骤和恢复事务；全部更新使用原子写。每次 adoption start/status/resume 先对账磁盘实际文件、恢复包和最后一条已提交卡片：一致则继续，不一致则进入 recovery_required，绝不靠内存猜进度。

9. 最终生成的三个文件

文件它回答什么生成时机
verification-registry.json现在有哪些 engineering gate、runtime gate 和 test suite；谁负责；真实入口在哪里获批变更执行并验证完成后先生成
bootstrap.json首次接管时，哪些资产已经在确定 Git commit 中真实存在用户确认包含 Registry 的 commit 后生成
verification-inventory.html给人看的总表：Baseline / Branch / WIP、变更、Owner、入口、盲区和暂缓项Bootstrap 成立后生成，以后结构变化时刷新

Bootstrap 和 Inventory 生成后会产生第二次待提交变更；向导明确提示用户完成第二次提交。WildArrange 不自动 commit、merge 或 push。

避免两次提交的循环锚定：Bootstrap 固定锚定“包含 Registry 的 commit A”。Inventory 不要求预知第二个 commit B，而是保存 baselineRef、Registry digest、Bootstrap digest，以及排除 Inventory 自身后的声明输入指纹。生成 Bootstrap/Inventory 后状态为 awaiting_final_commit；只有当前 HEAD 已包含这两个文件，且重新计算的声明输入指纹完全一致，状态才变为 finalized。A 与 B 之间任何影响 Registry、Runner、入口或发现范围的改动都会使 Inventory 过期，必须重新生成；不影响声明输入的普通业务变更不会制造假过期。

持续新鲜度：doctor 增加只读 registryFreshness 分项，status 复用其摘要。HEAD、Registry/Bootstrap digest 或声明输入指纹漂移时常驻黄灯，提示运行显式检查；绝不把过期 Inventory 显示为绿色。

路径不强加：产品内部使用逻辑角色 registryPath / bootstrapPath / inventoryPath。默认建议放在项目现有 tooling/docs 习惯能容纳的位置；项目没有相应目录时，扫描结果提出一个最小落点并让用户确认，不能把 Gamecopilot 的 tooling/verification-* 路径硬塞给所有项目。

10. 三份文件能“接管”到什么程度

能够接管

  • Gate、Suite 和 Runner 的资产目录。
  • Owner、执行入口、阻断位置和变更历史身份。
  • 测试入口是否真实覆盖登记范围。
  • 新增、失效、重复、暂缓和报告过期。
  • 结构变化时的中立 Review。

不会冒充

  • 每个测试用例的第二套管理系统。
  • 测试执行历史数据库。
  • 业务、实机、制品或 Provider 验收。
  • 对所有 Runtime Gate 的自动穷举。
  • 现有 delivery pipeline 的替代品。

Registry 的真实消费者

消费点什么时候读取负责什么
doctor.registryFreshness用户运行 doctor核对路径、digest、输入指纹和 Inventory 新鲜度；只读黄灯
status查看项目状态显示资产数量、暂缓项和 freshness 摘要，不做全仓扫描
Inventory generator用户显式生成/刷新从 Registry 与真实入口重建人类视图
verification-governance Skill用户要求接管、盘点，或结构变更任务明确匹配时显式调用产品检查命令并解释 diff

不在每次 run 或 plan import 前做全仓扫描，也不新增默认阻断门。长期防腐依靠 doctor/status 的廉价 freshness 检查，以及 Skill 对结构变化的显式完整检查。

11. 旧设计文档与任务怎么归档

发现内容默认建议历史保存方式
已被新真源替代、仍有决策价值的设计按目标项目现有规范归档；规范要求原位标记时不移动Git 保存全文；归档目录保留可读文件；历史索引记录替代关系
已经关闭的旧任务单和验收记录退出活动入口，进入项目已有任务档案记录任务身份、最终状态、证据、后继任务和恢复信息
完全重复且没有独有信息的文件先提议归档；只有用户确认归档无收益时才提议删除Git 与本次恢复包保留原文；历史索引保留墓碑
仍被引用或消费者不明的历史内容暂缓，保持原位Inventory 持续显示缺失证据和 Owner
当前有效设计和任务保留并登记为当前真源不移动、不复制第二份

不能按日期判断过期。系统必须找到新的当前真源、核对引用，并证明旧文件的独有信息已经迁移或明确保留，才允许提出归档。

历史不重复存全文。Git 保存完整历史；归档目录保存仍值得直接阅读的文件；WildArrange 只保存结构化索引：原路径、新路径、动作、原因、后继真源、内容 hash、批准人、恢复包和时间。Archivist/Memory 只接收清洗后的结论摘要，不摄入旧文档全文、raw diff 或完整命令输出。

归档路径服从目标项目。先读取项目现有规范和目录；有归档规则就沿用，要求原位标记就原位标记，没有规则才提出最小候选目录，用户批准后建立。不得给所有项目强塞统一 archive/。

最终 Inventory 增加四个视图：当前真源、历史档案、已删除墓碑、暂缓确认。这样 Agent 默认先看当前真源，需要追溯时再进入历史。

12. 这是一项重要 Skill，但不是只有 Skill

verification-governance Skill

负责识别触发场景、启动接管、解释变更卡、引导用户判对、调用产品命令、汇报未验证边界，并在以后 Gate/Suite 结构变化时继续维护库存。

它像项目经理：知道什么时候盘点、怎么向人说明、什么时候必须停下来确认。

WildArrange 五区能力

负责确定性扫描、消费者证据、路径与 Git 校验、锁、备份、Apply、回滚、Registry/Bootstrap/Inventory 生成。

它像施工机械和保险措施：不依赖某次对话记忆，也不会因换宿主而改变安全行为。

只保留一个长期 Skill：发布真源位于 packs/wildarrange-linear/skills/verification-governance.md，登记进 Prompt Pack manifest/routes 并随 WildArrange 发布；宿主需要项目 Skill 形态时，由现有 adapter 受控物化到 .agents/skills/verification-governance/SKILL.md。其中增加“首次接管”模式，不再创建第二个含义重叠的 onboarding Skill。

Skill 不能自行改文件、绕过批准或把 Inventory 绿灯冒充业务验收，所有副作用必须调用受控产品能力。Skill 的触发识别可以由 LLM/路由建议，但全仓扫描只能由 Skill 显式调用产品命令发起；Hook 不得静默扫描，避免性能损耗和非确定性副作用。

13. 单设备与多设备

一次初始化接管必须由一台设备从扫描做到三文件生成，避免被忽略的 .wildarrange/ 草案在设备间产生两个版本。界面必须明确显示“当前接管会话仅属于本机”。

三份正式文件完成两次 Git 提交后，才进入 WildArrange 现有 guarded 多设备协调范围。未来若要跨设备继续未完成的接管，需要单独设计可提交的 adoption plan、Owner、handoff 和 takeover；当前版本不假称已经支持。

14. 状态只服务于界面恢复

scanning 扫描中→ reviewing 等待判对→ ready 已形成可执行清单→ applying 执行获批项→ awaiting_registry_commit 等待 Registry 的 commit A→ awaiting_final_commit 等待 Bootstrap/Inventory 的 commit B→ finalized 三文件与声明输入一致

异常只用三个结果：needs_review（需要重新判对）、recovery_required（需要恢复）、cancelled（保持原项目）。每张卡独立记录 pending / approved / rejected / deferred / stale，因此“部分批准”不再伪装成一个全局 approved 状态。

这些是 adoption 自己的界面状态，不复用 task/admission 的状态字段，也不参与任务 completed。

Git、依赖图、路径、锁和通用恢复infra直接复用 dependency-graph.mjs 的词法 import、git-diff.mjs、path-match.mjs、runtime-store.mjs 与文件锁；复用 rule-scanner/repository-layout 的结果边界，不重写其职责；M2-0 提炼通用恢复原语
首次接管与持续治理入口单一 verification-governance Skill只负责编排说明和调用产品命令，不直接实现副作用
Registry、Bootstrap、Inventory目标项目内的可配置治理产物路径遵循目标项目习惯；Registry 是目录真源，HTML 只是视图

早期融合评估“不经 gateway、不进 runtime”的结论只适用于把 ZIP 当独立盘点脚本。用户现已明确要求完整接管产品，因此这是经过产品确认的范围升级；实现必须进入五区并遵守 gateway，而不是偷偷复制 ZIP 脚本。

16. 工程实施顺序，不改变用户的一条流程

里程碑内部先完成什么对外是否宣称完整接管
M1全仓只读扫描、消费者入口图、逐项变更卡、接入映射、历史归档候选和 Review 页面否，只能内部预览
M2-0提炼通用 recovery transaction；用等价测试钉死 task archive 行为和 admission 安全不变量不变否，只是 Apply 的前置地基
M2-1Dashboard 逐卡批准、现场指纹、维护互斥、自包含会话与启动对账、隔离 Apply 和验证否，需与 M3 联调
M3可配置三文件路径、Registry → commit → Bootstrap/Inventory、历史索引、单一 Skill 入口、最终结果与恢复入口完整验收后才对外开放 adoption start

用户不会收到半成品入口。M1/M2 是开发切片，不是让用户分别学习的三套产品。

17. 产品验收

看得懂

  • 每项都有“是什么、作用、为什么处理、完成后怎样、最大后果”。
  • 用户不填写 JSON、不选择架构层、不设计映射。
  • 默认只展示需要判断的内容，证据按需展开。

不误动

  • 扫描阶段业务文件零修改。
  • 消费者未知时没有删除/合并按钮。
  • 只执行获批路径；现场变化使卡片 stale。
  • 删除、合并和敏感治理变化必须逐项批准。

能恢复

  • 每张执行卡都有业务文件 preimage。
  • 失败时只回滚当前卡，不扩大影响。
  • 回滚失败立即停止并给出恢复入口。
  • 本机断电后可由自包含会话和磁盘对账确定性恢复。
  • M2-0 不改变现有 task archive/admission 行为。

真接管

  • 有效 Suite 映射到真实 Runner/命令。
  • Runtime Gate 保留在副作用前。
  • 暂缓项持续可见但不阻塞正确项。
  • 当前真源与历史档案分开，全文不重复入库。
  • 最终三文件与真实 commit、声明输入指纹一致。
  • doctor/status 能持续发现 Registry 或 Inventory 漂移。

18. 开工门

本设计复审通过后，才能写实现规划。设计批准仍不自动授权：

  • 修改 AGENTS、AGENTS Schema、允许路径或校验器；
  • 对当前 WildArrange 或任意真实老项目执行删除、合并、归档；
  • 修改 CI、build、Hook、Runtime 或测试策略；
  • 提交、合并或推送。

真正执行老项目接管时，每张敏感变更卡仍由用户现场批准。

证据基线

本设计以 2026-09-02 当前 WildArrange dirty 工作区、原始 Verification Governance ZIP、首次融合评估及三轮外部审核为依据。已确认：现有完成链仍为 verify → scope → review → acceptance-proof → checkpoint；.wildarrange/ 被 Git 忽略；现有任务锁默认等待 15 秒；approvePlan 不含内容指纹；现有 archive recovery 仍带 task 专属语义；command-safety 只覆盖高风险命令底线。以上限制均未被本设计冒充为现成能力。
