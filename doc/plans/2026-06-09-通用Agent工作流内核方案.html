通用 Agent 工作流内核 · HelixFlow

源码级调研 + 落地方案 ｜ 2026-06-09 ｜ 目标：一套全流程工作流（创意→UI→开发→Review→测试→部署），可装入任意 AI Agent 产品，多产品/多技术共享成果物且不冲突、可插拔。

0 · 一句话结论（先行）

核心判断

真正能跨 Claude Code / Codex / opencode / Cursor / Gemini CLI 共享、不冲突、可插拔的，只有三样东西：

① 指令层 — AGENTS.md

唯一被全部 5 个产品原生接受的"项目说明书"。必须瘦：只放高频规则 + 指向 skill/MCP 的路由，重逻辑下沉。

② 能力层 — SKILL.md

纯 Markdown 方法论 + YAML frontmatter。Anthropic 与 OpenAI 的 SKILL.md 字段一致、可互读。工作流封装成 skill，不是 slash command。

③ 工具层 — MCP server

写一次处处用。5/5 产品支持，Linux Foundation 治理。所有确定性动作/外部集成都封装成 MCP。

命令（Gemini 用 TOML、Codex 弃用 markdown prompts）、hooks、子 Agent 调用方式，是各产品分裂的部分——不能押在它们上面，只能由"每产品薄适配器"各投影一份。这个"中立内核 + 薄适配器"模式已被 obra/superpowers、OpenSkills、compound-engineering 转换器 在生产中验证，非假设。

用类比理解

USB 标准：不管什么设备都认的统一口子 = AGENTS.md + MCP 协议。

乐高底板：谁来都往同一块板上拼，不推倒重来 = git 中立产物目录。

插线板：随插随用、互不短路 = skill/MCP 的命名空间隔离 + 符号链接投影。

多车道施工：各开各的车道最后合流 = git worktree 隔离 + merge 收口，不用文件锁。

关键差异化结论（对 M1）

  • symlink 安装 + git pull 升级（呼应第 6 节适配器投影）
  • Markdown-as-source + 编译器（= 第 4 节 adapters/build.ts 的实证范本）
  • 关键词即接口（isolate/checkpoint/merge）降命令记忆负担
  • 模型能力类别路由 = 跨产品的 Tier 路由抽象层

3 · 架构：三层中立内核 + 薄适配器

这是整个方案的地基。把工作流拆成"一份权威源（中立内核）+ 每产品一个薄适配器"。重逻辑永远只有一份，适配器只做两件事：① 把中立文件投影到产品私有路径（symlink 或编译）；② 把 MCP server 注册进各产品各自的配置格式。

为什么是 .agent/skills/ 而非 .claude/skills/？

把共享技能塞进任何产品的私有目录（如 .claude/skills）会与该产品自带的 marketplace 插件重名冲突。OpenSkills 的踩坑结论：用中立目录 .agent/skills/（也是 Codex 原生路径之一），再 symlink 投影到各产品。

为什么 skill 不用 slash command？

命令是最分裂的扩展点：Gemini 用 TOML，Codex 的 markdown prompts 已弃用。skill（SKILL.md 纯 markdown）是唯一被各产品自动发现+调用的可移植能力单元。

为什么工具一律 MCP？

MCP 是真正"写一次处处用"的层（5/5 支持）。把所有确定性动作（跑测试、查 spec 覆盖、部署、审批门）写成 MCP server，唯一成本是注册入口要为每产品各写一份配置——这正是适配器的活。

5 · 多产品共享成果物"不冲突"的机制

成果物分两类，处理方式不同——这是不冲突的关键。

A 类 · 工作流定义（skills/指令/工具）

手段：单一真相源 + 符号链接投影。

  • 技能放 .agent/skills/，指令放 AGENTS.md —— 只此一份
  • CLAUDE.md → AGENTS.md、.claude/skills → .agent/skills 全部 symlink 回同源
  • 强制 hf- 命名空间前缀，避免撞各产品自带 skill
  • 改一处，全产品同步生效，零副本漂移

B 类 · 运行期产出物（spec/design/plan/state）

手段：git 乐观隔离，不用悲观锁。

  • 全部纯文本/HTML/MD，落 .workflow/ 中立目录，git diff 天然可合并
  • 对 spec 的修改走 Delta（增量），不同 agent 改的是不同 delta 文件，永不撞
  • 多 agent / 多产品并行 → 各自独立 git worktree 分支写文件，物理隔离
  • 收口用 merge；调研确认无任何产品提供跨工具文件锁，业界一致用 worktree
反模式警告： 不要做文件锁、不要把共享技能塞进产品私有目录、不要让两个 agent 直接写同一个 spec 主文件——这三件是冲突的根源，分别用 worktree、symlink、delta 化解。

6 · 可插拔机制（插 skill / 插 tool / 插角色）

插什么怎么插为什么不冲突
插一个 skill（新阶段/新能力）在 .agent/skills/ 放一个目录 + SKILL.md；运行 build 编译到各产品。各产品按约定自动扫描发现，无需注册表hf- 前缀命名空间 + description 内嵌触发条件（自动路由），不撞已有
插一个 tool（确定性动作/外部集成）写一个 MCP server 放 mcp/；适配器把它注册进各产品配置格式（.mcp.json/config.toml/opencode.json）MCP 协议跨产品统一，server 复用，只有注册入口分裂（已被适配器吸收）
插一个角色/persona在 .agent/agents/ 放一个 YAML-in-MD 文件；在编排 skill 的"角色选取段"加一行 + spawn gate 条件角色定义与编排选取解耦（CE 模式）：新增 persona 零改动其它角色
插一个质量门在 gates-server MCP 加一个 gate tool；在编排状态机加一个 GATE: STOP 断言门是状态机的一个节点，DAG 重排自动生效
拔掉某能力删目录 / 编排里去掉该步。纯文件系统操作，无系统级残留各能力松耦合，靠产物契约交接而非硬调用

本质：三个解耦让"插拔"成立 —— 指令源与分发目标解耦（编译器）、角色定义与编排选取解耦（前缀+集中声明）、知识存储与检索解耦（frontmatter 文件 + grep 召回）。

S1

创意讨论 → 需求

产品负责人 主导。把模糊想法逼成"做什么/为什么/验收什么"。

注入提示词要点
"你是坚信大道至简的产品合伙人。先给一个有力假设而非问一堆问题；只有真实歧义（两个方向导致截然不同结果）才停下来问。产出聚焦 WHAT & WHY，禁止写技术实现。每条需求标 SHALL/MUST/SHOULD + REQ-ID。"
skill hf-ideate（先调 hf-recall 召回同类历史决策）
tool 可选 web 调研 MCP（竞品/市场）
GATE：需求含 ≥3 条可验收 criteria 且无 [NEEDS CLARIFICATION] 残留，否则回炉。
产物 .workflow/specs/{f}/brief.md
S2

规格 Spec（约束源）

产品负责人 + 架构师 复核。spec 是约束所有下游的合同，不是文档。

注入提示词要点
"每条 requirement 配一个 Given/When/Then scenario，使其可测试。修改已有 spec 一律走 delta（ADDED/MODIFIED/REMOVED）写入 changes/，不得直接改主 spec。校验是否违反 constitution.md。"
skill hf-spec
tool artifacts-server：delta 合并、frontmatter 校验、spec 一致性检查
GATE：每条 SHALL/MUST 都有对应 scenario；constitution 合规；delta 无冲突。
产物 specs/{f}/spec.md + changes/{f}/specs/*.md(delta)
S3

UI / UX 设计

设计负责人 主导——这是与架构对称的"体验/视觉一致性"线（你的 L2 第四角色）。

注入提示词要点
"遵循设计系统 + 交互模式 + 视觉风格三条一致性。不要让用户思考、系统承担复杂性、渐进式展示、反馈引导行动。UI 变更必须在浏览器中查看最终效果并附截图证据。"

tool Playwright MCP（截图/视觉验证）、设计稿 MCP
GATE：关键页面有截图证据，对照设计系统无明显偏离。

计划编排（设计 → 可执行 DAG）

PM（编排） 主导：谁做、何时、什么次序、依赖。

注入提示词要点
"把 spec+架构拆成有序任务 DAG，独立任务标 [P] 最大化并行。为每个任务生成 context_package：从 sharded 架构里预提取技术栈/文件路径/API 签名/测试要求，附来源引用——下游执行 agent 禁止主动翻外部文档。标注每任务复杂度（deterministic/simple/complex）供执行端选模型。"

tool artifacts-server：DAG 校验（依赖正确性、无环）
GATE：docs/plans/ 真生成了 tasks 文件；每任务有 context_package；DAG 无环。
产物 plans/{f}/tasks.md（含 DAG + [P] + context_package）
S6

开发执行

开发 Agent（可多个并行）。纯执行角色，挂在编排循环上。

注入提示词要点
"task 文件的 context_package 已含全部必要信息，不得主动加载外部文档。只能修改 task 指派的区段。完成后 SendMessage 给 review 阶段。并行任务各自在独立 git worktree 写。always_load：coding-standards / tech-stack / source-tree。"
skill hf-work
tool 代码执行/文件 MCP；worktree 隔离
GATE：有文件改动；本任务 DoD checklist 自检通过。
产物 代码 + 更新 task 的 execution_record 区段（仅 dev 可写）
S7

代码 Review（四段管线）

多 reviewer persona 扇出 + 架构师抽检。直接抄 CE 最精密的部分。

四段管线
  • ① 扇出：always-on（正确性/测试/可维护性/项目规范）+ 按 diff 条件追加（security/performance/migration/前端竞态…）。每 reviewer 写全量 JSON 到 /tmp/{run_id}/，只回 compact JSON 省上下文。高风险三项用顶配模型，其余中配（Tier 路由）。
  • ② 去重：指纹 = 文件+行桶(±3)+标题；≥2 reviewer 命中 → 置信锚点升级。
  • ③ 置信门控（放最后）：抑制锚点<75 的 finding；但 P0 在锚点 50+ 仍保留（critical-but-uncertain 绝不静默丢）。
  • ④ per-finding 独立验证波：每个幸存 finding 派独立 validator 复核（绝不 batch——batch 会重现 persona 偏置），返回 {validated,reason}。
skill hf-review（机器交接 mode:agent 输出 JSON，人看输出 markdown 双轨）
tool gates-server.review_gate（硬门）
GATE：无未解决 P0/P1；交互模式可应用已验证的安全修复并 commit（永不 push）。残留 finding 兜底写进 PR body 或 docs/residual-review-findings/。
S8

测试

测试 Agent。遵守你的硬约束"未测试不交付/自测必须验功能"。

注入提示词要点
"从 spec 的 Given/When/Then scenario 自动生成测试用例骨架。必须实际运行并验证行为正确，不能只确认'不报错'。走完主路径 + 关键边界场景。UI 在浏览器查看最终效果。"
skill hf-test
tool gates-server.test_gate、Playwright MCP、覆盖率 MCP
GATE：覆盖所有 SHALL/MUST scenario；覆盖率达阈值；主路径+边界实跑通过。
产物 测试报告 + 更新 task test_record 区段
S9

部署上线

部署 Agent + PM 放行（HITL：上线是用户拥有的对外步骤）。

注入提示词要点
"对外/不可逆操作先确认。生成 Go/No-Go 检查单 + 回滚预案 + 监控计划。CI watch + autofix 循环（最多 3 轮直到绿），失败不静默。"
skill hf-deploy → hf-commit-push-pr
tool gates-server.deploy_gate、CI/部署 MCP（如 Vercel MCP）
GATE（HITL 硬门）：deploy_gate 必须人类拍板；CI 绿；回滚预案就位。

10 · 编排与数据结构（L4）

任务依赖 = DAG

tasks.md 里每任务声明 depends_on + [P] 并行标记。编排算法：拓扑排序保证依赖正确，同层 [P] 任务并发派发最大化并行、缩短周期。

阶段串联 = 带 GATE 的状态机

hf-run 把 9 阶段串成状态机，每步 GATE: STOP 断言式校验（如"验证 plans/ 真生成文件，否则重跑"），失败有兜底，不静默跳过。

产物流转 = 变量绑定

$outputs.{stage}.{artifact} 引用上游产物（claude-flow 式），解耦 agent 实现与编排逻辑。state.json 记录当前位置 + 各 gate 结果，崩溃可恢复。

重排 = 影响分析触发

spec/设计更新 → 重新生成 plan 和 tasks（spec-kit 式"再生输出"）。变更/返工触发"影响分析→重新规划"，只重跑受影响子图。

跨工具 dispatch 优雅降级（CE 偷来）： 编排 skill 正文写明"在 Claude 加 model:、Codex 用 spawn_agent、Pi 用 subagent、找不到 dispatch 参数就 omit——working review on parent model 胜过 broken dispatch"。skill 名跨产品 verbatim 匹配（有的列在插件命名空间下如 plugin:hf-plan）。

14 · 优势 / 劣势（诚实评估）

优势

  • 三层全部是已验证的最大公约数，不赌任何产品专有特性
  • 产物纯文件 + git，天然可版本化、可审计、可合并、可入飞书 wiki
  • 可插拔是结构性的（三个解耦），不是事后补的开关
  • 复利飞轮让工作流随用随强，边际成本递减
  • 每个阶段/能力可独立替换（如 UI 阶段挂现成设计 skill）

劣势 / 风险

  • 命令体验分裂：Gemini TOML、Codex 弃用 markdown prompt——slash 命令体验无法统一，只能靠 skill 自动路由弥补
  • 适配器维护成本：每新增产品要写一个 target；MCP 注册入口各产品一份
  • "自动路由"是软约定：依赖模型读 description 判断触发，跨模型版本有漂移风险（硬门用 MCP 兜底）
  • 认知负担：9 阶段 + 4 治理角色对小需求偏重——需提供"轻量档"（拔掉部分阶段）
  • MCP 子能力不齐：跨产品只能稳依赖 Tools，Resources/Prompts 各客户端支持度不一
