WildArrange 的真实 Loop、路由与 Hook

这里把三个容易混淆的东西分开：Hook 是宿主事件触发器，Router 是每次发言经过的分诊层；只有存在明确起点、终点和失败回边的完整工作生命周期，才称为 Loop。

Hook / Router = 门铃与分诊台

每次事件到来时启动一次，判断该找谁、走哪条路，然后退出；它们不是永远在后台运转的循环。

物理 Loop = 一张工单从开到关

例如整个 Plan、整个 Bug 修复或整个新需求；失败会回到前一步继续，满足关闭条件才真正结束。

系统自动 人类确认 强制质量门 持久结果 失败回环

物理 Loop B：整个开发计划从对话到关闭

一份开发计划包含多张工单。用户先和宿主大模型把目标谈清楚，再形成可执行计划；WildArrange 逐张推进，全部完成或明确暂停原因后，整个计划才结束。

B
用户对话

说清要解决的问题

用户与宿主大模型讨论新需求、Bug、重构目标和期望结果。

计划草稿

整理成 plan.json

宿主大模型根据当前对话填写任务、负责人、修改范围、测试和完成标准，写入专用草稿目录；人工也可直接提供已有文件。

用户确认

确认目标与边界

WildArrange 检查字段是否齐全；需要批准时，用户确认后才允许进入开发。

登记工单

写入全项目任务登记册

每张工单保留目标、依赖、负责人、允许修改范围、测试和当前状态。

分类与准备

确认负责人并准备 Skill

语义生成阶段把实际负责人写入每张工单的 task.owner；执行 Hook、任务领取和隔离运行都读取这个字段。分类只补充类别和 Skill，不建立第二套派工账。

逐张开发

运行单工单开发 Loop

选择当前可开发工单，走直接开发或隔离开发，再进行完成检查；失败就返工。

计划收口

全部完成或明确暂停

确认所有工单、遗留事项和用户决定都已处理，输出计划总结和恢复位置。

生成闭环：UserPromptSubmit 判断需要计划后，宿主大模型写入 .wildarrange/plan-drafts/*.json；语义生成计划必须由用户批准。
派工闭环：语义计划的可执行工单必须显式填写 Jiuwei 或 ZhuRong；DiJiang、BaiZe、LuWu 通过计划、复核、治理阶段参与，不进入 command worker。
看板方案：工单将按“需求待补齐、待开发、开发中、验收中、已完成、需要处理”六列展示。

活动 Plan 期间又收到一条新工作：先判断是否属于当前工单

这是防止“正在修 A，用户顺口提到 B，系统就把 B 塞进 A 的计划”的隔离线。当前计划生成、审批和 task.owner 已实现；自动新建宿主会话仍是待实现产品策略。

物理 Loop C：单张工单的开发与验收循环

每张工单先产出代码，再由独立检查确认能否完成。直接开发使用当前工作区；隔离开发先把代码留在独立 worktree，检查通过后才正式接纳。

待开发→ 开发中→ 验收中→ 已完成
领取工单读取目标、范围和负责人
选择开发方式当前工作区或独立 worktree
Worker 开发产出真实代码和执行回执
准备待验收代码隔离成果先临时应用；直接开发已在当前工作区
自动测试重新运行任务要求的测试
范围检查确认只改了允许路径
独立复核风险、质量和逐条完成标准
验收证明记录本轮全部通过证据
正式接纳或返工隔离路径此时才合入；失败则撤销并退回
测试、复核或完成标准失败 写清失败证据和下一步，工单回到待开发或需要处理；修正后重新检查，不沿用上一轮结果。
修改范围越界 要么撤销越界代码，要么由用户批准新的修改范围；批准后从头重新验收。
中断或完成记录没写成功 工单保持“验收中”，根据最新证据恢复；最终完成记录未安全写入前，不能显示为“已完成”。

业务级物理 Loop：从业务问题出现到业务问题关闭

这些是包住 Plan / Task Loop 的真实业务生命周期。它们的开始和结束标准不同，因此不能只用 intent 标签代替。

↻

整个新需求 / 新功能 Loop

结束条件：目标用户行为与产品验收通过，而不只是代码合并。

PHYSICAL LOOP
产品目标→用户旅程→验收设计→Plan Loop→多个 Task Loop→真实产品验收→发布 / 关闭
↩ 用户验收失败或需求变化 → ChangeRequest → 回到产品目标 / 验收设计 → 修订 Plan。

整个 Bug 修复 Loop

结束条件：原始症状消失、根因链成立、回归用例与真实表面验证通过。

PHYSICAL LOOP
Bug 报告→真实复现→互斥假设→根因证据→失败用例→修复 Task Loop→原场景复验→关闭 Bug
↩ 复验仍失败 → 回到“互斥假设”；禁止在未证明根因时继续叠补丁。

整个重构 Loop

结束条件：计划内重构单元全部完成，外部行为保持，前后基线证据一致。

PHYSICAL LOOP
重构目标→影响面 / callers→行为基线→拆分重构单元→每单元 Task Loop→全量行为复验→关闭重构
↩ 行为改变或范围外扩 → 回滚该单元 / ChangeRequest → 回到影响面与计划。

答疑 / 调查 / 一次性 Review：默认不是 Loop

它们是有界只读流程：给出证据化结论即结束；只有用户决定采取改动时才新建 Plan。

BOUNDED FLOW
限定问题→读取真实来源→收集证据→结论与限制→结束
若用户授权修改 → 形成新目标 → 进入 Plan Loop；不是在原 Review 中偷偷开工。

Loop 下方的责任架构

五区回答“代码归谁”，五个长期 Agent 回答“判断归谁”。Router 只分流，不成为第六个长期角色。
