WildArrange 多设备与多 Agent 开发方案

讨论范围：跨设备接力、多台设备同时开发、同一设备多个 Agent 并行。目标是避免覆盖、重复劳动和“本机状态正常、另一台机器完全不知道”的问题。

推荐结论

Git 管跨设备持久化，worktree 管本机隔离，任务所有权管并发；不是每次修改都 commit，而是每次跨设备交接必须 commit + push。

最短路径先做第一版 Git-only，不引入常驻协调服务器。一个任务同时只能有一个写入 owner；不同任务可以在不同设备、不同 Agent 上并行。

三类场景分别处理

跨设备接力

MacBook → Mac mini

同一个任务换设备继续。原设备必须生成任务 checkpoint commit 并 push；新设备只能从该远端 commit 恢复。

多设备并行

两台设备同时开发

只能并行不同任务；每个任务有独立远端分支和 owner。路径重叠的任务必须建立依赖或串行 admission。

本机多 Agent

一个设备并行多个 Agent

每个可写 Agent 使用独立 Git worktree。Agent 不直接合并主工作区，统一由 Jiuwei 串行 admission。

统一工作流

Claim

领取任务，锁定 owner、base commit、writable paths 和设备标识。

→

Isolated Work

在任务分支 + 独立 worktree 修改；其他 owner 不得同时修改同一任务。

→

Verify / Handoff

验证后 commit；跨设备时必须 push 并记录 commit SHA，合入时走 admission gates。

什么时候强制 Git 提交

动作CommitPush原因
同设备、同任务、在批准范围内继续编辑不强制不强制避免无意义碎片提交。
切换到另一台设备继续同一任务强制强制未 push 的 commit 对另一台设备不可见。
把任务交给另一 Agent / owner强制跨设备时强制明确交接基线，防止接手者读取半成品目录。
进入 review / admission强制远端协作时强制验证证据必须绑定不可变 commit SHA。
修改超出 writable_paths不能直接提交解决不能直接 push 解决先创建并批准 ChangeRequest，再扩展任务范围。

git stash 不算跨设备交接证据；它默认只存在本地，也没有稳定的任务、验证和 owner 元数据。

分支、worktree 与所有权

任务分支

wildarrange/task/<planId>/<taskId>

一个任务一个远端分支。分支 HEAD 是所有设备共同认可的最新持久状态。

本机 worktree

.helix/worktrees/<planId>/<taskId>/<agent>

每个可写 Agent 一份隔离目录；主工作区只承担计划、审查和 admission。

任务 owner

taskId + agent + deviceId + baseSha + remoteHeadSha + ownerEpoch

同一任务只能有一个有效写 owner。远端任务分支 HEAD 是所有权凭证；接力必须显式 transfer，不能靠“谁先 push 算谁的”。

并发规则

组合允许方式必须阻断
不同设备 + 不同任务 + 不重叠路径完全并行，各自 task branch/worktree。无。
不同设备 + 不同任务 + 路径重叠建立 blockedBy，或由 Jiuwei 排定 admission 顺序。两个任务同时修改并直接合主线。
不同设备 + 同一任务只允许显式 handoff 后接力。双 owner、双写、各自 force push。
同设备 + 多 Agent + 不同任务独立 worktree 并行，结果串行 admission。多个 Agent 共享同一可写 cwd。
同设备 + 多 Agent + 同一任务只读 Agent 可并行审查；写 Agent 只能一个。两个写 Agent 同时产出同一任务 patch。

建议的 Git checkpoint 合同

任务提交除普通标题外，写入机器可读 trailer：

feat(task): implement T012 parser

WildArrange-Plan: P20260731
WildArrange-Task: T012
WildArrange-Agent: ZhuRong
WildArrange-Device: macbook
WildArrange-Base: <baseSha>
WildArrange-Verify: pass
WildArrange-Next: review

新设备通过 commit SHA 和 trailer 重建任务上下文；`.helix/` 仍是本地运行态，不直接在多台设备间互相覆盖。

主分支集成规则

任意设备可集成

不指定一台常驻集成机器。Jiuwei 是逻辑集成者，不绑定 MacBook、Mac mini 或其他物理设备。

远端 SHA 乐观锁

admission 开始时记录远端 main SHA；验证完成后只允许向该预期 SHA 做普通快进 push，禁止 force push。

变化即重验

如果其他设备先合入导致远端 main 变化，本次集成返回 revalidation_required；拉取、重新应用任务成果并重跑全部 gates 后才能再次 push。

默认内置 + 可调强度

配置合同

能力内置在 WildArrange，不依赖 GitHub API 或额外服务器。默认使用 guarded：检测到 Git remote 时启用远端任务所有权与 worktree；普通本地目录或尚未配置 remote 的仓库继续可用，但必须明确提示已经降级为本地协调。

{
  "gitCoordination": {
    "mode": "guarded",
    "remote": "origin",
    "integrationBranch": "auto",
    "taskBranchPrefix": "wildarrange/task",
    "requireWorktreeForParallelWrites": true,
    "requireVerificationBeforeHandoff": false,
    "requireCleanHandoff": true,
    "requireTakeoverReason": true
  }
}
模式行为适用场景
off不启用跨设备 Git 协调；现有本地任务流保持不变。明确只在单目录、单写者环境运行。
manual提供 device、claim、handoff 命令，但不自动改变现有 task claim 与 parallel run 行为。逐步迁移或只在需要时跨设备交接。
guarded（默认）有 Git remote 时自动接入远端 claim，并让可写并行 Agent 使用 worktree；无 remote 时保留本地流程并显示降级证据。兼顾现有项目兼容性与默认安全。
strictGit 仓库、remote、远端 claim 和独立 worktree 缺一即拒绝执行；handoff 前必须完成验证。多设备、高并发或高风险仓库。

可以增强或减弱的是“何时自动启用、是否要求交接前验证、无 remote 时是否允许降级”。只要模式不是 off，以下底线不可配置关闭：同一任务只能有一个写 owner；不得 force push；跨设备 handoff 必须绑定已 push 的 commit SHA；远端集成分支 SHA 变化后必须返回 revalidation_required；takeover 必须显式执行并留下理由和证据。

第一版实施阶段

阶段能力放行证据
Phase 1稳定 deviceId、远端 task branch claim、单写 owner 与冲突拒绝。两台设备并发 claim 同一任务，只有一个成功。
Phase 2handoff prepare/push/accept、checkpoint commit、任务包与 ledger hash 接续。新设备可从远端 commit 重建本地任务；旧设备继续写时被拒绝。
Phase 3同设备多 Agent 默认 Git worktree；不同任务可并行，同任务只允许一个写实例。并行结果互不污染；重叠 writable paths 被阻断或串行化。
Phase 4任意设备 admission、远端 main SHA 乐观锁、变化后重新应用并重验。两台设备竞争集成时，一个成功，另一个返回 revalidation_required 且不能覆盖。
  1. handoff prepare --task T012 --to-device-id <uuid> --to-device-name mac-mini：用不可冒认的设备 UUID 绑定目标并校验 scope；仅在 strict 或开启 requireVerificationBeforeHandoff 时运行 verifier，随后生成 checkpoint commit。
  2. handoff push --task T012：推送任务分支，记录远端 commit SHA。
  3. handoff accept --task T012：新设备校验远端 SHA、owner transfer 和本地无冲突后恢复。
  4. team claim 增加 deviceId/baseSha/remoteHeadSha/ownerEpoch；创建远端任务分支时第一个成功 push 的 owner 获得写入权，第二个 claim 因非快进冲突而 fail-closed。
  5. parallel run 默认强制 Git worktree；同一设备的多个写 Agent 不再允许共享 run-dir 工作区。
  6. parallel admit 获取并绑定远端集成分支 SHA，校验当前工作目录包含该基线；全部 gates 和 acceptance proof 通过后生成集成 commit 并普通 push。远端 HEAD 变化或本地基线落后时必须重新应用并验证。
  7. 不做基于本机时间的自动 lease 过期：无中心时钟时无法可靠判断另一台离线设备是否仍在工作。陈旧 owner 只能显式 release、handoff 或由人确认后执行带证据的 takeover。

暂不做

  • 不在第一版引入中心服务器、数据库或常驻 Agent 集群。
  • 不自动 force push、自动解决 merge conflict 或静默接管其他设备的任务。
  • 不把整个 `.helix/` 提交到 Git；只同步任务代码、必要产物和 checkpoint 元数据。
  • 不允许 commit/push 绕过 ChangeRequest、scope、review 或 checkpoint。
已对齐

三个顶层产品决策已于 2026-07-31 确认，可以进入实现。

  1. 同一任务严格禁止两台设备同时写，只支持显式 handoff。
  2. 第一版以现有 Git remote 作为唯一跨设备协调面，暂不引入 GitHub API 或中心服务。
  3. 不设固定集成设备；任意设备可以集成，但必须绑定远端 main SHA，远端变化后重新运行全部 gates。
已实施

2026-07-31：Git-only M1 已按本方案接入默认运行时。

  • gitCoordination 四档配置、稳定设备 UUID、远端 task claim、UUID 绑定的 handoff prepare/push/accept 与显式 takeover 已落地。
  • 默认 guarded 在存在 remote 时为可写并行 Agent 强制 worktree，并用 parallel_run_claim 阻断同任务双写。
  • 并行 admission 在 gates 前及 acceptance proof 后复核任务 owner、工作目录基线、变更归属与远端集成分支 SHA；通过后真实生成集成 commit 并非强制 push。变化、基线落后或夹带无归属脏文件时只回滚本 run 路径并返回 revalidation_required。
  • 远端集成一旦已知成功，之后的 checkpoint/审计失败、main 继续前进、owner 变化或异常改写都保留同一 run 的所有权与集成意图；禁止回滚或释放，只能同 run 对账恢复或保持 recovery_required。
  • Handoff push 前复核 prepare 树指纹；push/accept/takeover 支持远端成功后的同设备幂等补账。parallel close 可按 runId 清理强制终止留下的空结果幽灵 claim。
  • 自动测试使用本地 bare Git remote 覆盖双设备 claim、UUID 冒认、已提交变更交接、prepare 后继续编辑、旧 owner 六个写入/质量入口、线性 run 中途 takeover、两设备集成竞争、主线中途变化、旧基线、无归属脏改动、幽灵 claim、部分批次失败、takeover 对账，以及 push 后 main 前进/owner 变化/历史改写的恢复。
