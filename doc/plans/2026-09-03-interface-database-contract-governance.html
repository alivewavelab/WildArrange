01. 它补上什么缺口

模块架构图

回答文件属于哪个模块、模块之间怎样依赖。

像商场楼层图，知道店铺在哪一层，但不知道每个柜台收什么材料。

接口与数据库契约台账

登记跨模块、跨进程、持久化或对外可依赖的 API、事件、表、字段和调用关系。

像办事窗口名册：窗口叫什么、收什么、交付什么、谁会来办。

验证治理登记册

登记哪些测试、门和证据能够证明这些契约没有被改坏。

像消防检查表。它证明窗口可安全使用，但不是窗口名册本身。

04. 台账登记什么：只存本体和引用，不复制别人的账

接口契约本体

  • 接口 ID、协议类型、方法与路径，或事件名 / 函数签名。
  • 输入、输出、错误结果、权限要求和生命周期。
  • 真实源码位置；既有 import 图只派生“模块级潜在调用方”，不能冒充某个具体导出的真实调用方。
  • moduleRef 指向 module-file-map.json 的模块 ID。
  • ownerRef 指向任务的 task.owner；它表示本次变更负责人，不冒充长期模块负责人。
  • verificationRefs 只保存 verification registry 的卡片 ID，不复制测试命令和证据。
窗口名册只写窗口自己的规则；楼层、经办人和检查报告都写“去哪个登记册查”。

数据库契约本体

  • 表 / 视图 ID、Schema 或 Migration 来源。
  • 字段名、类型、可空、默认值、主外键、唯一约束与索引。
  • 读写方、迁移步骤、兼容窗口、回滚方法和生命周期。
  • 同样只保存 moduleRef、ownerRef、verificationRefs。
柜子名册写清楚放什么、谁会读写、换柜时怎么办；归属和检查证明仍去原登记册查。

实现前必须裁决的唯一事实源

当前 module-file-map.json 只有模块路径和 designId，没有长期负责人字段。因此 V3 不在契约台账另造长期 owner。若未来确需长期模块负责人，应先决定唯一 owner 真相源，再让 ownerRef 引用；本方案不擅自修改 module map schema。

现有楼层图没有“店长”栏，就先登记本次经办人；不能偷偷再做一本店长名册。

05. 中间产物怎么退役

扫描快照

工作区只展示“最近一次扫描快照 + 已批准基线的引用与摘要”。新快照成功写入后，旧快照先移入 .wildarrange/contracts/archive/snapshots/，用于复核误报、漏报和覆盖漂移；只能按项目既有备份/清理政策删除，不直接覆盖丢弃。

桌面只摆最新清点表，旧表先装进档案柜，确认不再需要后才按统一制度清理。

待审核差异卡

30 天未处理只自动标记为 expired，并进入覆盖报告“待决策”；不自动批准、不自动删除。

过期申请会被标红提醒，但系统不能替你签字或扔掉。

已处理差异卡

已批准和已拒绝的卡都移入 .wildarrange/contracts/archive/，保留决定、理由和证据引用；只有项目既有备份/清理政策才能删除归档。

办完的申请进档案柜，拒绝件也保留，避免以后重复争论。

07. 自动发现必须诚实报告边界

已自动覆盖

列出发现器名称、版本、扫描根、来源类型和识别数量。

明确告诉你机器这次真正检查了哪些柜子。

需要人工申报

动态生成、源码字符串中的 SQL、运行时注册或尚无发现器的技术栈，进入人工申报清单。

机器看不懂的地方必须点名交给负责人，不能成为无声盲区。

未知或可疑

发现疑似契约却无法确认时标记 unknown，给出文件位置与下一步，不自动断言“无变化”。

墙里可能有管线时先贴警示，不能假装什么都没有。

08. 最短落地顺序

第一步：通用核心 + 人工申报 Skill

实现契约 JSON、引用字段、差异卡、覆盖状态、生命周期规则和申报入口；数据库契约首版允许完全人工申报。

先建官方名册和可靠的人工登记窗口。

第二步：一个 Node ESM 发现器

只扫描项目内 src/**/*.mjs 的静态命名导出、默认导出和再导出。复用 src/infra/dependency-graph.mjs 的词法 import 图，只能派生“哪个模块可能使用了另一个模块”；除非以后实现导入符号关联，否则不能登记为某个具体导出契约的真实调用方。动态 import 或无法解析的关系仍标记 unknown。它只产出“模块导出契约”，不冒充 HTTP API，也不推断请求字段、数据库结构或业务含义。

线路图只能看出 A 店接了 B 店的线，看不出 A 店具体使用了 B 店哪个窗口。

第三步：确认基线与覆盖范围

开发者确认稳定契约、本次任务负责人、人工申报项和未知区域，生成首版正式台账与 HTML。

批准名册时，连“哪些地方还没清点”也一起签字。

第四步：接入现有交付链

扩展既有 review 步骤：经 gateway 调用 repository-governance 的契约检查 lane，把能力信封传给 review-gate 并合入 reviewResult；失败沿用 review FAIL，acceptance-proof 沿用现有 review 证据检查。只阻断当前任务触及区域的漏登记与未获批准的破坏性变更。

监督检查成为原验收单中的一个检查项，失败仍从原窗口退回，不另建第二个大厅。

09. 本次产品决定

建议确认：通用核心保持技术栈中立；首版一个 Node ESM 发现器 + 一个治理 Skill/人工申报入口；契约台账只保存契约本体及外部 ID 引用；中间产物按明确生命周期处理；LuWu 复用现有 review/acceptance-proof。

明确不做：不承诺全仓自动发现，不删除数据库契约类别，不先建动态插件框架，不复制模块/负责人/验证登记册内容，不新增平行门禁，不把 HTML 当事实源。

系统必须同时告诉你“我发现了什么”“我不知道什么”“相关资料去哪里查”。
