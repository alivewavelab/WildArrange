HelixFlow 方案评审与修订建议

2026-06-10 ｜ 评审对象：通用Agent工作流内核方案 + M1工作保险箱需求 + PipelineAtlas 11 项目拆解 ｜ 评审基准：4 个核心目标
总判断：地基扎实，方向对，可以进 ce-plan；但有一个系统性遗漏 —— debug/fix 工作流。
调研确实做到源码级，各家精华（CommandRegistrar / Delta Spec / context_package / 四段评审 / MCP 硬门 / index.yml）都抓对了。 四个目标中：可插拔(3)、不丢不覆盖(4) 覆盖强；流程简洁(1)、自进化(2) 是当前短板，且两者的交点正是被漏掉的 debug 节点。

一 · 四目标对照评分

目标1 · 流程短 + 治理强 6/10

9 阶段 + 4 治理角色对日常小任务偏重，方案自己承认但「轻量档」只有一句话。门要硬、站要少：MCP 硬门保治理强度，流程长度按工作级别分流。

建议：复用文档规范已有的 任务/模块/专项 三级 —— 任务级走 work→review→test 短链；模块级加 spec/plan；专项级才跑全 9 阶段。SuperClaude 三维触发表已调研到，但只用于选模型，应同时用于选流程长度。

目标2 · 项目自进化 5/10

复利飞轮（召回前置+沉淀后置）载体正确，CE 双轨 schema 的 bug 轨（symptoms/root_cause）天然支持 debug 召回。但自进化被推迟到 M2/M3 且只有一句话，没有 hf-debug 节点承接。

建议：debug/fix 设为一等节点，内嵌两个自进化钩子 —— ① 修复后自动生成回归检查；② 按项目沉淀诊断 playbook（症状→根因映射），越修越快。

目标3 · 可插拔 9/10

三个解耦 + 插拔表是全方案最强部分，结构性可插拔成立。

小缺口：目前「拔」= 删目录/改编排。建议加项目级 helix.json 声明启用哪些 stage/gate/skill/MCP，裁剪变成配置而非删文件（disabled_hooks 模式已调研到，顺手采用）。

目标4 · 同步/共享/不覆盖/可追回 8/10

M1 工作保险箱正面命中且排序正确（先打地基）。worktree 隔离 + delta + 快照 + 硬锁覆盖「不覆盖、可追回」。

两个缺口：① 快照只落本地 refs/helix/snapshots，机器丢=工作丢、队友看不见 —— 快照需推远端（参考蓝图 opencode-worktree-session 本身就 push）；② R4 在途总览是单机视角，多人需互见 in-flight（只读即可）。

三 · 修订建议（按优先级）

P0 新增 hf-debug/fix 一等节点

位置：review 与 test 之间（对齐 lfg）。职责：承接 findings + 测试失败；内嵌自进化双钩子（bug→回归检查、bug 轨召回优先）。这是目标2 的落点，不应等到 M3 才有形态。

P0 流程三级分流写进 hf-run

任务级 3 站 / 模块级 5-6 站 / 专项级 9 站，门全部保留 MCP 硬门。分流判据可抄 SuperClaude 三维触发表（关键词+文件类型+复杂度）。

P1 M1 增补：快照推远端 + 团队在途互见

R2 加一条：快照 SHOULD 异步推 refs/helix/snapshots/* 到远端；R4 总览支持读远端 refs 展示队友 in-flight（只读）。

P1 helix.json 项目级插拔清单

每项目声明启用的 stage/gate/skill/MCP；拔=改配置。与双作用域优先链（项目>用户）合并设计。

P2 补拆 debug 线进 PipelineAtlas

ce-debug 本机即有，零成本；omc debug / SuperClaude troubleshoot / claude-forge build-error-resolver 各拆一节点目录。
