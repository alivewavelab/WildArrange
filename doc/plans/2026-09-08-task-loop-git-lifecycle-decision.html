状态：已定稿；task worktree / delivery commit / task-branch push / SHA 绑定与主线不移动已实现并由自动测试证明。Draft PR 创建与主线合并后的安全清理仍属于后续独立实现。

已定规则

  1. 一个可写任务对应一个 owner、一个独立 worktree 和一个独立 task branch；两个可写 worktree 不得共享同一分支。
  2. 开发与 BUG 修复默认从干净 commit 基线创建隔离 worktree。发现无归属改动时优先自动隔离；无法隔离、同文件冲突或所有权不明时才询问开发者。
  3. 禁止自动 stash、reset、clean、覆盖、提交或删除其他任务的改动。
  4. 任务分支允许多个中间 WIP commit；只有 verifier、scope、review 与 acceptance proof 全部通过的最终版本才能标记为 delivery commit。
  5. AI 或人类对任务代码做出的后续修复都必须形成新 commit，不用长期 dirty 工作区保存成果。
  6. Loop 自动创建本地 commit，并可自动 push 到该任务独占的远端 task branch；这不等于获准进入共享主线。
  7. 无实际文件变化时记录 no_change，不制造空 commit。
  8. 强耦合改动若不能独立验收，应放入同一任务联合交付；若可拆分，则使用两个任务、两个 worktree、两个 branch，再由独立 integration task 绑定双方 commit SHA 做联合验收。
  9. 实现任务不能自证完成。Verifier 与 Integrator 读取明确的 commit SHA，生成 acceptance proof 与 checkpoint。
  10. 任务处于等待验收、返工或 recovery_required 时保留 branch/worktree。确认目标主线包含任务 commit 后，先验证 worktree 干净并删除 worktree，再删除本地 branch；远端 branch 删除需人类确认。

已定流水线

clean base
  -> task branch + isolated worktree
  -> worker
  -> verifier
  -> scope
  -> independent review
  -> acceptance proof
  -> local commit
  -> push own remote task branch
  -> checkpoint bound to commit SHA
  -> await integration / rework

共享主线与 PR 定稿

  • 默认只有一个共享长期主分支 main；不默认创建 develop 或 production 分支。
  • 一个 task branch 通常对应一个持续更新的 PR；一个 PR 可以包含多个中间 commit。
  • 系统可以自动创建或更新 Draft PR；人类批准点是把通过检查的 PR merge 到 main。
  • Approve 与 Merge 是不同动作；进入 main 和部署到 production 也是两次独立授权。
  • development、staging、production 是部署环境；同一已验证 commit/tag 应按授权逐级部署。

术语

术语含义
commit保存在本地 Git 数据库中的代码快照。
push把本地 commit 同步到远端分支。
task branch只承载一个任务开发历史的短期分支。
worktree与任务分支绑定的临时施工目录，不作为长期档案。
merge把已验收任务的历史纳入共享目标分支。
