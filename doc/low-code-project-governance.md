# 低代码开发者项目掌控手册

> 面向「本人不读代码、由 AI 执行维护」的团队。本文定义人与 AI 的分工、项目必须具备的治理框架、测试纪律与日常工作流。  
> 架构分区与依赖边界细则见 [five-zone-decoupling-guidelines.md](./five-zone-decoupling-guidelines.md)；本文只补充**掌控层**方法论，不重复五区实现细节。

## 1. 适用对象与前提

### 1.1 谁该读这份手册

- **项目所有者**：不懂或不愿深入读代码，但需要持续交付与可控风险。
- **维护操作者（通常是 AI Agent）**：负责定位、修改、跑测试、提交证据。
- **框架搭建者**：为上述模式建设边界测试、契约文档与门控流水线的人（可以是 AI 辅助的一次性投入）。

### 1.2 核心定义

在本手册中：

- **可维护性** = AI 改一处后，能否向人**机器化证明**：没碰不该碰的模块、没破坏既有行为。
- **红绿灯** = 自动化测试、质量门（verify / scope / review 等）、边界扫描的 PASS/FAIL 汇总；人只看结果，不读 diff。
- **门** = 任何在合并或标记完成前必须通过的自动检查；人负责校准门是否太松或太紧，而不是逐行审代码。

**为什么**：把「懂代码才能管项目」换成「懂症状 + 懂证据链就能管项目」，才能规模化 AI 维护。  
**不做的后果**：人要么重新陷入读代码，要么在 AI 出错时只能凭感觉放行，风险不可见、不可复盘。

## 2. 角色重新定义

| 角色 | 职责 | 不做的事 |
| --- | --- | --- |
| **人（症状描述者）** | 用自然语言描述现象、复现步骤、期望行为；提供业务上下文 | 不逐文件审 diff、不手动改多处关联代码 |
| **人（红绿灯裁判）** | 看测试/门控 PASS/FAIL；FAIL 时把证据摘要转给 AI 返工 | 不凭「感觉对了」绕过红灯 |
| **人（门的校准者）** | 对每条拦截/放行标注「对了/错了/存疑」；按周期摘要收紧或放宽规则 | 不代替 AI 写修复、不口头 override 质量门 |
| **AI（定位者）** | 用错误码契约、模块边界、影响面分析把症状映射到**单区/单职责** | 不跨区顺手改「顺便优化」 |
| **AI（修复者）** | 在目录契约允许范围内改代码；先写复现测试再修 | 不自证完成、不跳过 scope/verify |
| **AI（证据提交者）** | 提交：改了哪些文件、跑了哪些测试、各门决策与证据路径 | 不提交「应该没问题」类口头结论 |

**为什么**：职责分离把「判断对不对」交给机器可重复的门，人只处理机器无法自洽的边界与框架调参。  
**不做的后果**：AI 既当运动员又当裁判，或人被迫读代码补位，整套模式名存实亡。

## 3. 框架要求清单

项目要支持上述工作方式，至少应逐步具备以下能力。与 [five-zone-decoupling-guidelines.md](./five-zone-decoupling-guidelines.md) 的关系：该文档管**代码怎么分区**；本节管**人怎么靠分区掌控项目**。

### 3.1 依赖边界强制测试

- **要求**：自动扫描 import/依赖方向，违规即 FAIL；禁止通过兼容层或 barrel 绕路。
- **为什么**：隔离修复的地基；AI 无法悄悄制造跨模块耦合而不被红灯抓住。
- **不做的后果**：改 A 牵动 B/C 无人知晓，全量测试偶发红、定位成本指数上升。

### 3.2 目录级契约文档（渐进式披露）

- **要求**：根规范写全局不变量；各稳定目录写局部 `AGENTS.md`（或等价文件）：本区职责、可写范围、交付前必跑检查。子目录只收紧、不放宽根级安全约束。
- **为什么**：AI 进入某目录时加载**刚好够用**的上下文，不必每次吞整库。
- **不做的后果**：AI 误改禁区或漏跑局部验收；人无法用「目录对不对」做粗粒度审计。

### 3.3 统一错误协议与契约表

- **要求**：对外/对运维暴露的错误结构固定（如 `{ code, module, paths?, next_action }`）；契约表进 `doc/contracts/` 并由测试钉死。
- **为什么**：症状 → 模块的映射可机器化；人看 code 即知下一步该跑哪条命令。
- **不做的后果**：同类故障多种字符串，AI 定位漂移，人无法建立「看到这个就做什么」的条件反射。

### 3.4 影响面分析

- **要求**：提供命令或脚本：给定改动文件 → 列出依赖方与建议测试集；修复前后各跑一次核对。
- **为什么**：把「可能波及范围」从 AI 直觉变成可核对清单；人可看一句话摘要（如「影响 3 文件，建议跑 zone-X + 全量」）。
- **不做的后果**：漏跑分区测试，合并后 CI 才暴露回归。

### 3.5 分区测试入口

- **要求**：除全量测试外，可按模块/区域/包跑子集（秒级反馈），再跑全量。
- **为什么**：AI 迭代时快速验证本区；全量留给交付前。
- **不做的后果**：每次小改都跑全量，反馈慢，AI 倾向于少测少改或跳过验证。

### 3.6 诊断面与门控面分离

- **要求**：报告、仪表盘、doctor、只读审计故障时**降级**，不得拖垮 verify/scope/checkpoint 等门控路径；各检查分项报告、独立失败。
- **为什么**：观察工具坏了不应等于「可以跳过质量门」。
- **不做的后果**：一次 dashboard 挂掉导致整链无法完成，或为了恢复而关闭门控。

### 3.7 决策留痕与可读投影

- **要求**：每次拦截/放行产出统一结构（时间、门名、决策、原因、命中规则、证据路径、关联任务 ID）；面向人的 CLI/面板投影，支持人对单条标注。
- **为什么**：框架替人做决定时，人必须能看见并校准；否则无法判断门太严还是太松。
- **不做的后果**：误拦/漏拦只能靠撞运气发现，框架无法迭代。

### 3.8 本地与 CI 同入口

- **要求**：开发者与 CI 跑同一套命令（如 `npm test` / `make check`），无「仅 CI 才跑」的隐藏步骤。
- **为什么**：消除「本地绿、远端红」的信任危机。
- **不做的后果**：人看到的绿灯不可信，只能等 CI，周期拉长。

### 3.9 完成链：Worker 不能自证完成

- **要求**：实现者提交 Done 后，仍须独立 verifier、scope、review（若启用）、成功判据、验收证明、checkpoint；顺序单点维护。
- **为什么**：与五区准则中的 delivery pipeline 一致；防止 AI「说完成即完成」。
- **不做的后果**：未验证变更直接入账，事后无法区分是代码错还是流程错。

## 4. 测试要求清单

### 4.1 复现测试先行（缺陷纪律）

- **要求**：修 bug 前先写（或补）失败测试，确认红灯，再改代码至绿灯。
- **为什么**：证明修的是真实问题，且未来同一类问题会再红。
- **不做的后果**：「修好了」无法证伪，回归重复出现。

### 4.2 边界测试

- **要求**：依赖方向、禁止环、网关唯一入口、shim 无逻辑等由自动化边界测试覆盖；新增跨区边必须先进白名单再写代码。
- **为什么**：架构约束若靠人工记忆，三个月必失效。
- **不做的后果**：结构腐化，影响面分析失真，隔离修复破产。

### 4.3 影响面对应测试

- **要求**：影响面命令列出的每个区域/测试集，交付前必须实际执行并通过；不得只跑「觉得相关」的子集。
- **为什么**：把静态分析结论与动态验证绑定。
- **不做的后果**：漏测依赖方，合并后才发现间接破坏。

### 4.4 对抗与恢复测试（进阶）

- **要求**：并发 claim、中断、回滚失败、证据复用等关键路径有回归测试。
- **为什么**：AI 维护高频触碰事务边界；无测试则只能生产踩坑。
- **不做的后果**：状态文件与工作区不一致，需人工救场且无法 scripted 恢复。

### 4.5 本地 = CI

- **要求**：见 §3.8；交付前本地必须跑完与 CI 等价的检查。
- **为什么**：人只看一次绿灯即可信任。
- **不做的后果**：双轨验证，人永远不知道信哪边。

## 5. 日常工作流

### 5.1 报修流程（人 → AI）

1. **描述症状**：现象、复现步骤、期望 vs 实际；附错误 code（若有）、环境、最近变更（若知）。
2. **AI 定位**：查错误契约表 → 模块/目录 → 读最近目录 `AGENTS.md`。
3. **AI 评估影响面**：列出将改文件与建议测试；若波及超单区，先拆任务或请人确认范围。
4. **人粗审范围（可选）**：仅看「动哪些目录、跑哪些测试」，不读实现。

**为什么**：结构化输入减少 AI 漫无目的搜索。  
**不做的后果**：同一症状多次修复、改错文件、范围蔓延。

### 5.2 修复验收流程（AI → 人）

1. AI 在契约范围内修改；缺陷先测后修。
2. 跑分区测试 → 影响面建议集 → 全量测试 / 质量门链。
3. 提交**证据包**：变更文件列表、测试摘要、各门 PASS/FAIL、决策记录链接。
4. 人看红绿灯：全绿则接受；有红则把失败摘要退回 AI，**不得**口头特批跳过。
5. 合并或标记完成仅发生在 checkpoint/等价步骤成功之后。

**为什么**：验收标准客观、可重复、可审计。  
**不做的后果**：「好像好了」上线，无 ledger 无法追责与复盘。

### 5.3 决策标注与调参流程

1. 框架拦截或放行时，人在决策投影中标注：对了 / 错了 / 存疑（可附一句话）。
2. 周期内汇总：误拦率、从未触发的规则、可疑放行。
3. 人据此调整配置（收紧/放宽/改规则），**不**通过关闭门来「省事」。
4. 可选：只读审查 Agent 产出四类清单（可疑放行、可疑拦截、门未触发、规则冲突），人只看摘要。

**为什么**：门替人做决定，人通过标注教门变准。  
**不做的后果**：门长期误拦或形同虚设，人重新依赖读代码或完全盲信。

### 5.4 周期健康检查

建议每周或每迭代一次：

| 检查项 | 通过标准 |
| --- | --- |
| 全量测试 + 边界测试 | CI 与本地同入口全绿 |
| 决策摘要 | 误拦标注趋势下降或已处理 |
| 契约漂移 | 错误码表、目录 AGENTS 与实现一致（可用 audit 命令） |
| 影响面工具 | 对近期改动文件跑 impact，与实跑测试集一致 |
| 诊断面 | doctor/报告可用；门控面不受诊断故障影响 |

**为什么**：框架与代码同步腐化是渐进的，周期扫描才能早发现。  
**不做的后果**：积累 silent drift，某次小改引发大面积不可控 FAIL。

## 6. 反模式清单

| 反模式 | 为什么有害 | 典型后果 |
| --- | --- | --- |
| 人读 diff 代替看灯 | 违背模式前提，不可扩展 | 成为瓶颈，AI 改多错多 |
| AI 自证完成、跳过 verifier | 无独立验证 | 未测变更入账 |
| 为空或删除 verify 命令求绿 | 削弱门控 | 假绿灯 |
| 扩大依赖白名单让测试变绿 | 架构约束名存实亡 | 跨区耦合蔓延 |
| 诊断与门控混在同一失败路径 | 观察故障阻断交付 | 关工具换过关 |
| 本地与 CI 不同脚本 | 双轨信任 | 「我这边过了」推诿 |
| 无决策留痕 | 无法校准框架 | 误拦/漏拦永远不知道 |
| 根规范堆一切、无目录契约 | 上下文爆炸或缺失 | AI 误改或漏检 |
| 先改后补测试（缺陷） | 无法证明修对 | 回归重复 |
| 口头 override 质量门 | 破坏客观验收 | 事故后无证据 |
| 为了少测只跑「相关」子集且无影响面命令 | 漏测依赖方 | 合并后 CI 红 |
| 兼容 shim 写业务逻辑 | 绕边界扫描 | 隐藏耦合 |

## 7. 采用成熟度分级

按团队资源分阶段落地；**每级必须满足该级全部项**才能宣称达到该级。

### L0 — 裸奔

- 有全量测试；主要依赖 AI 自觉与人抽查。
- **缺口**：无边界强制、无目录契约、无决策留痕。
- **适用**：原型、一次性脚本；**不适用**长期 AI 维护的产品。

### L1 — 可定位

最小落地集：

1. 根 + 关键目录 `AGENTS.md`（职责与禁写范围）。
2. 统一错误结构 + 契约表初版（哪怕仅覆盖 CLI 与核心 API）。
3. 缺陷先测后修写入维护纪律。
4. 本地与 CI 同一测试入口。

**标志**：人能把症状映射到目录；AI 修完有测试摘要可看。

### L2 — 可隔离修复

在 L1 基础上：

1. 依赖边界强制测试（至少：分层方向 + 无环 + 网关/禁止 shim 绕路）。
2. 影响面分析命令（静态 import 图 → 建议测试）。
3. 分区测试入口。
4. 独立 verifier/scope；worker 不得自证完成。
5. 决策记录 + CLI 级投影；支持人对决策标注。

**标志**：AI 改单区可机器证明未越界；人可校准门而不读代码。

### L3 — 全闭环

在 L2 基础上：

1. 诊断面与门控面硬分离 + 分项降级。
2. 完整 delivery pipeline（verify → scope → review → 成功判据 → 验收证明 → checkpoint）。
3. 异步审查 + 周期框架健康摘要。
4. 对抗/恢复测试覆盖关键事务。
5. 文档单一事实源 + audit 防漂移。

**标志**：人长期只做症状、看灯、标决策、周期调参；框架自证可信。

## 8. 与现有准则的衔接

```text
low-code-project-governance.md（本文）  →  人如何掌控、日常怎么跑
five-zone-decoupling-guidelines.md        →  代码如何分区、依赖怎么约束
doc/AGENTS.md                             →  文档放哪、何时同步
各目录 AGENTS.md                          →  AI 进入该目录时的行动契约
doc/contracts/                            →  错误码与 API 的机器可读真相
doc/plans/*.html                          →  需评审的方案与流程（单次决策证据）
```

- 五区是**推荐**分区模型，非唯一；小项目可用更粗粒度（如 `app/` / `lib/` / `infra/`），但须保留边界测试与目录契约。
- 落地顺序建议：L1 纪律与契约 → 边界测试 → 影响面与分区测 → 决策留痕 → L3 体验与审查。

## 9. 最小落地检查表（L2 目标）

启动或审计项目时，可用此表自检：

- [ ] 根 `AGENTS.md` 写清全局目标、测试入口、不可削弱的不变量。
- [ ] 各稳定模块目录有局部契约，且写清「交付前跑什么」。
- [ ] `doc/contracts/` 有错误码表，测试引用关键 code。
- [ ] 存在依赖边界测试，CI 必跑。
- [ ] 存在影响面分析工具，AI 修复流程文档化要求改前改后各跑一次。
- [ ] 存在分区测试命令；交付前跑全量。
- [ ] 本地与 CI 使用同一命令。
- [ ] 完成路径不绕过 verifier/scope；决策可查询、可标注。
- [ ] 缺陷流程明确要求先红灯后绿灯。
