一、架构合理性分析

1.1 分层架构

Layer 4: helix-workflow / helix-parallel-agents (顶层入口) ↓ Layer 3: helix-node-runtime (核心编排) ↓ Layer 2: helix-review / helix-routing / helix-agent-spawn / helix-git-worktree ↓ Layer 1: helix-plan / helix-team / helix-gates / helix-failure / helix-acceptance-proof ↓ Layer 0: helix-foundation (无内部依赖，纯基础设施) helix-core.mjs: 纯导出层，不属于分层

1.2 设计优点

设计模式说明评分
Evidence-Driven每一步都把结果 push 到 task.evidence[]，全链路可追溯优秀
Gate-Then-Checkpoint任何 checkpoint 前必须通过 verifier + scope + review + acceptance proof优秀
Fail-Safe Rollbackparallel admission 失败时自动回滚文件优秀
Dual-Format Reports所有报告同时输出 JSON (机器可读) + Markdown (人工可读)优秀
Hash-Chain Ledger所有关键事件写入不可篡改的 ledger.jsonl优秀
宿主中立核心状态机是产品中立的本地文件协议优秀

1.3 架构问题

问题风险建议
helix-foundation.mjs 超过 1000 行 中 拆分为基础工具、文件IO、配置管理、运行时初始化四个模块
helix-hooks.mjs 依赖 10 个模块 中 拆分为 scope、injection、context 三个子模块
3 个工具函数重复 27 次 高 创建 helix-utils.mjs 公共模块
架构评分：8.5/10
分层清晰，职责划分合理，无循环依赖。主要问题是基础模块过大和代码重复。

四、Agent 执行问题分析

4.1 高风险问题

问题风险影响建议
retryTaskNode 无限扩大 maxAttempts 高 死循环，任务永远不完成 加入硬上限（如 10 次）
runNextTask 长时间持锁 高 其他操作 15 秒超时 拆分锁粒度或改为 per-task 锁
advisory lock 非强制 高 外部操作可破坏一致性 在锁文件中加入 UUID 验证
快照与 tasks.json 可能不一致 高 恢复后状态错误 在 persistTaskState 后写快照
evidence 数组无限增长 高 内存膨胀、序列化变慢 截断 stdout/stderr，归档旧 evidence

4.2 中风险问题

问题风险影响建议
verifying 状态无回退路径 中 node 模式下任务卡死 失败后显式回退到 pending
persistTaskState 双写非原子 中 部分写入导致不一致 plan 文件改为延迟写入
并行 Agent ledger hash 链分叉 中 ledger 校验失败 给 appendLedger 加独立锁
超时子进程可能泄漏 中 文件描述符耗尽 加入 SIGKILL 后备
readLedgerLastHash 全文读取 中 ledger 越大越慢 反向读取文件末尾

4.3 状态机流程图

pending → in_progress → verifying → reviewing → checkpointing → completed ↑ ↓ ↓ ↓ └─────────┴───────────┴───────────┘ (失败回到 pending 或 failed) 问题：verifying 状态失败后，node 模式下可能卡在 verifying
执行健壮性评分：6.5/10
存在 5 个高风险问题，主要是死循环、长时间持锁、状态不一致等。需要优先修复这些问题才能保证生产环境的稳定性。
